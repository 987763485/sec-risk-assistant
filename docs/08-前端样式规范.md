# 08 · 前端样式规范

> 适用范围：`web/` 全部代码。
> 本文是**强制约定**，不是建议。改动 `web/src/styles/index.css`、`web/src/main.ts`、
> `web/plugins/vite-plugin-css-layer.ts`、`web/vite.config.ts` 之前必须读完。
> 新增 Element Plus 的**命令式 API**（`ElMessageBox` / `ElMessage` / `ElNotification`…）时
> 必读 §2.4 —— 它们的样式不会自动带上。

---

## 1. 这份规范解决什么问题

我们把 Element Plus 和 Tailwind CSS v4 放在同一个项目里。这两者的样式体系天然冲突：

| | Tailwind v4 | Element Plus |
|---|---|---|
| 样式所在层 | 全部在 `@layer utilities` 内 | **无层（unlayered）** |
| 定位 | 原子化工具类 | 完整组件样式 |

CSS 级联规则里有一条容易被忽略但极其关键的规定：

> **不在任何 `@layer` 内的样式，优先级永远高于 `@layer` 内的样式** ——
> 与选择器权重、源码顺序都无关。

于是 `<el-button class="w-full">` 里的 `w-full` **永远无法生效**，
因为 Element Plus 的 `.el-button { width: auto }` 是无层的。

`!important` 能解决单个点，但会引发新的优先级战争，且无法覆盖所有属性。
正确做法是**把 Element Plus 的样式也放进层里，并让它排在 utilities 之前**。

## 2. 核心机制

### 2.1 五个层

`web/src/styles/index.css` 第一行（必须是文件第一行）：

```css
@layer theme, base, el, components, utilities;
```

层优先级 **低 → 高**：

| 顺序 | 层名 | 放什么 | 来源 |
|---|---|---|---|
| 1（最低） | `theme` | 设计令牌（颜色、间距、字号变量） | `tailwindcss/theme.css` |
| 2 | `base` | 最小基础重置 | 本仓库 `@layer base` 段 |
| 3 | `el` | **Element Plus 全部样式** | 由插件自动包裹 |
| 4 | `components` | 业务自定义类（`.app-page` / `.app-panel`） | 本仓库 `@layer components` 段 |
| 5（最高） | `utilities` | Tailwind 工具类 | `tailwindcss/utilities.css` |

**`utilities` 排在 `el` 之后，是整套方案的支点。** 它保证了
`<el-button class="w-full">`、`<el-table class="mt-4">` 这类写法能正常工作。

### 2.2 谁把 Element Plus 包进 `@layer el`

`web/plugins/vite-plugin-css-layer.ts`，通过 `transform`（`order: 'pre'`）
在 Vite 处理之前，把 `node_modules/element-plus/**/*.css` 的源码整体包一层：

```css
@layer el {
  /* 原始 Element Plus CSS 原样放在这里 */
}
```

### 2.3 为什么刻意停用 preflight

`web/src/styles/index.css` 里这一行是**注释掉的**，请勿随手恢复：

```css
/* @import 'tailwindcss/preflight.css' layer(base); */
```

preflight 会用元素选择器重置原生元素：

```css
button { background-color: transparent; background-image: none; }
input  { border: 0; padding: 0; }
img, svg { display: block; }
h1, h2, ... { font-size: inherit; font-weight: inherit; }
```

而 Element Plus 的 `.el-button`、`.el-input__wrapper`、`.el-icon svg`
**恰恰依赖这些原生默认样式**。恢复 preflight 的典型症状：

- 按钮背景变透明、失去内边距
- 输入框边框消失
- 图标被块级化，把行高撑成两倍

需要的跨浏览器一致性处理已由 `@layer base` 段中的「最小基础重置」替代。

### 2.4 命令式 API 的样式必须显式引入

**按需引入只解析模板标签。** 这是本规范里最容易踩、也最难发现的一条。

| 用法 | 样式从哪来 | 写 `<el-dialog>` 那样能自动带上吗 |
|---|---|---|
| 模板标签 `<el-dialog>` | `unplugin-vue-components` + `ElementPlusResolver` | ✅ 会 |
| 函数调用 `ElMessageBox.confirm()` | **只能靠手写 import** | ❌ 不会 |
| 函数调用 `ElMessage.success()` | **只能靠手写 import** | ❌ 不会 |

为什么 resolver 不介入：`ElMessageBox` 是通过
`import { ElMessageBox } from 'element-plus'` 这条**普通具名导入**使用的。
`unplugin-auto-import` 的 `ElementPlusResolver` 虽然认识它，但只在标识符
**未被显式导入**时才注入 —— 代码里已经手写了 import，它就什么都不做，
样式 import 也就从来没有被生成。

> **佐证**：`web/src/types/auto-imports.d.ts`（由 `unplugin-auto-import` 生成）
> 里**一条 `element-plus` 记录都没有**，全是 `vue` / `vue-router` / `pinia`。
> 说明 resolver 在这条路径上一次都没生效过 —— 不是「生效了但被谁覆盖掉」。

#### 症状

**不报错、不告警、不白屏**，只是弹层/提示条拿到一堆**没有任何 CSS 规则**的类名：

| 组件 | 实际看到的样子 |
|---|---|
| `ElMessageBox` | 只有一层灰色遮罩（`.el-overlay` 恰好被 `el-dialog` 顺带引入），弹层本体与两个按钮是裸 DOM，挤在遮罩左上角 |
| `ElMessage` | 一条没有背景、没有圆角、没有阴影的普通文字 |

最容易漏掉的原因：**模板组件全都正常**。项目上百个页面用了几十个 `el-dialog`、
`el-table` 都好好的，只有「退出登录确认框」这类命令式调用是坏的 ——
于是很容易被当成偶发问题放过去。

#### 落点：`web/src/main.ts`

```ts
// ⚠️ 这两行是命令式 API 样式的唯一来源，删掉即静默退化
import 'element-plus/es/components/message/style/css'
import 'element-plus/es/components/message-box/style/css'
```

放在 `main.ts` 而不是各个视图里：样式来源集中一处，
与层顺序声明（`import './styles/index.css'`）相邻，改动时不容易漏掉另一处。

这两条路径落在 `node_modules/element-plus/` 下，因此**同样会被
`plugins/vite-plugin-css-layer.ts` 包进 `@layer el`** —— 和其它组件样式同层、
同样受 Tailwind 工具类覆盖，行为完全一致。

#### 新增命令式 API 时的清单

用到一个新的函数式 API（`ElNotification`、`ElLoading` 的服务式用法……），
必须同步补一行样式 import：

| 标识符 | 需要补的 import |
|---|---|
| `ElMessage` | `element-plus/es/components/message/style/css` |
| `ElMessageBox` | `element-plus/es/components/message-box/style/css` |
| `ElNotification` | `element-plus/es/components/notification/style/css` |
| `ElLoading`（服务式） | `element-plus/es/components/loading/style/css` |

**这一步漏了不会立刻被发现** —— 所以有下面两道守门：`verify:css` 从源码里
扫出实际用到的标识符，逐一对产物做断言（构建期拦住）；
`/dev/style-check` 第 ④ 项真的弹一个 `ElMessageBox` 出来量计算样式
（浏览器里拦住）。详见 §4.4 与 §5。

## 3. 必须遵守的写法

### 3.1 工具类：只用于布局，不用于组件外观

| 用途 | 允许的类 | 说明 |
|---|---|---|
| ✅ 布局 | `flex` `grid` `gap-*` `items-*` `justify-*` | 给容器用 |
| ✅ 间距 | `m-*` `p-*` `mt-*` `mb-*` | 给容器/包装用 |
| ✅ 尺寸 | `w-full` `max-w-*` `h-*` | 见下方例外 |
| ✅ 响应式 | `md:` `lg:` 等断点前缀 | — |
| ✅ 显隐 | `hidden` `block` | — |
| ✅ 文字层级 | `text-sm` `text-gray-500` `font-semibold` | 用于**纯文本**元素 |
| ❌ 组件外观 | `rounded` `border` `shadow` `bg-blue-500` 加在 `el-*` 上 | 会与组件自身样式打架，且不可预期 |
| ❌ 全局 `!important` | 任何位置 | 需要时应重新审视层顺序 |

### 3.2 需要调整 Element Plus 组件外观时

**优先用 CSS 变量** —— Element Plus 的样式全部基于一套 CSS 变量，
改变量不会与组件样式冲突：

```css
:root {
  --el-color-primary: #2563eb;
  --el-border-radius-base: 4px;
  --el-font-size-base: 14px;
}
```

改完**必须**重新运行守门验证（见第 5 节）。

**其次用 `:deep()`** —— 只在单个组件内修改，且必须限定作用域：

```vue
<style scoped>
/* ✅ 作用域内、目标明确 */
:deep(.el-table__header th) {
  background-color: var(--el-fill-color-light);
}
</style>
```

```css
/* ❌ 禁止：全局无作用域地改组件内部结构，升级组件库时必然踩坑 */
.el-table__header th { background-color: red; }
```

### 3.3 需要让自己的样式压过 Element Plus 时

写进 `@layer components`（本仓库约定），或在自己的 `<style scoped>` 里写 ——
scoped 样式带 `[data-v-xxx]` 属性选择器，权重足够，且不受层顺序影响。

**不要**把样式写在 `@layer utilities` 里 —— 那是 Tailwind 的层，
手写类混进去会让「这个类哪来的」变得难以排查。

## 4. 层顺序声明：最容易翻车的地方

### 4.1 层优先级由「层名**首次出现**的顺序」决定

假设 Element Plus 的 CSS 先于层顺序声明被解析：

1. `@layer el { ... }` 先出现 → `el` 成为**第 1 个**（最低优先级）层
2. 随后 `@layer theme, base, el, components, utilities;` 里，
   `theme` / `base` 是新层名 → 被**追加到 `el` 之后**
3. 实际层顺序变成 `el, theme, base, components, utilities` —— 完全错乱

**症状**：`npm run dev` 一切正常，`npm run build` 出来的页面上
Tailwind 工具类大面积失效。这类问题排查成本极高。

### 4.2 因此本项目的处理方式

`web/plugins/vite-plugin-css-layer.ts` 在两个阶段分别注入：

| 时机 | 手段 | 目的 |
|---|---|---|
| 开发 | `transformIndexHtml`（`order: 'pre'`） | 在 `<head>` 首位插一个 `<style data-secrisk-css-layer-order>`，保证最先被解析 |
| 构建 | **`generateBundle`（`order: 'post'`）** | 向每个最终 `.css` 产物的**首行**写入层顺序声明 |

### 4.3 为什么构建期必须在 `generateBundle`，不能放 `transform`

这是踩过的坑，记录在此以免后人重蹈：

- 构建器的 CSS 合并会**拆层重组**
- 压缩阶段会**直接丢弃**层顺序声明（认为它是重复声明）

放在 `transform` 阶段注入的声明，最终产物里根本不存在。
只有在 `generateBundle` —— 产物已经定型、即将写入磁盘的时刻 ——
注入才能保留下来。

### 4.4 自动化校验

```bash
cd web && npm run verify:css
```

`web/scripts/verify-css-layer.mjs` 对 `dist/assets/*.css` 做四项静态断言：

1. 每个 CSS 产物**首行**是 `@layer theme, base, el, components, utilities;`
2. 产物中出现的 Element Plus 选择器（`.el-*`）**全部位于 `@layer el` 之内**
3. 层顺序中 `utilities` 排在 `el` 之后
4. 源码里用到的**命令式 API** 的样式在产物里（见 §2.4）

第 4 项的取材方式是关键：它**不是**写死一份「必须存在的类名清单」，而是先
`grep` 出 `src/**/*.{ts,vue}` 里所有 `from 'element-plus'` 的具名导入，
再拿其中的命令式标识符去对照产物。

```js
// web/scripts/verify-css-layer.mjs
const IMPERATIVE_APIS = {
  ElMessage:     { marker: '.el-message__content',     style: '.../message/style/css' },
  ElMessageBox:  { marker: '.el-message-box__content', style: '.../message-box/style/css' },
  ElNotification:{ marker: '.el-notification__content',style: '.../notification/style/css' },
  ElLoading:     { marker: '.el-loading-mask',         style: '.../loading/style/css' },
}
```

写死清单的校验器挡不住新坑：将来有人开始用 `ElNotification` 却忘了引样式，
清单里没有它，校验器一声不吭 —— 同一个陷阱再踩一遍。从**实际用法**推导，
则「用了但没引样式」会当场失败，并直接打印出该补哪一行。

marker 的选法也有讲究：必须是**只可能由该组件 CSS 产生**的类名。反例是用
`.el-message` 当 marker —— `.el-message-box` 的产物字符串会把它一并命中，
于是「`ElMessage` 样式丢失」被判成通过，而它恰恰是最该被抓住的那一种。

该脚本已挂进 `npm run build`（`build` = `vue-tsc && vite build && verify:css`），
**校验不过则构建失败**，不会带着错版上线。

#### 第 2 项的写法经过一次修正，值得记下来

初版写的是「每个产物都必须包含 `@layer el` 块」。它在按路由分包出现之前
一直通过，因为那时每个 chunk 恰好都捎带了 Element Plus 样式。
P1 引入登录页等异步路由后立刻误报：

```
✖ LoginView-C2x30iCr.css：未找到 @layer el，Element Plus 样式可能未进层
```

而事实是——该文件里**一个 `.el-` 选择器都没有**。Element Plus 的样式被构建器
提升到了共享 chunk，这个 chunk 只剩业务自己的 scoped 样式。规则把「正常」
判成了「错误」。

| | 初版（过严） | 现版 |
|---|---|---|
| 问题 | 这个 chunk 里有没有 `@layer el`？ | **有没有漏在层外的** EP 选择器？ |
| 依赖 | chunk 的拆分方式（构建器行为，会变） | 只依赖失效模式本身 |
| 结果 | 分包方式一改就误报 | 不受分包影响 |

这类修正的通用教训：**校验规则要针对失效模式问，不要针对实现细节问**。
前者稳定，后者会随构建器版本、代码分割策略、依赖提升而变化。

#### 为什么判据是 `.el-` 类选择器而不是 `--el-` CSS 变量

业务代码经常以 `var(--el-text-color-primary, #303133)` 的形式复用 Element Plus
的设计变量（本项目的 `base` 层就是这么写的）。那属于正常用法，
不该被判成「EP 样式漏在层外」。`--el-` 与 `.el-` 只差一个字符，
但一个指的是 CSS 变量、一个指的是组件类名，语义完全不同。

#### 这项检查是可证伪的

```bash
# ① 造一个漏在层外的 EP 规则，校验必须失败
printf '@layer theme, base, el, components, utilities;\n.el-button{color:red}\n' \
  > web/dist/assets/__probe.css
cd web && npm run verify:css        # 期望：退出码非 0
rm web/dist/assets/__probe.css

# ② 把命令式 API 的样式规则从产物里抹掉，第 ④ 项必须失败
#    （模拟「有人删掉了 main.ts 里那两行 import」）
cp web/dist/assets/$(ls web/dist/assets | grep '\.css$' | head -1) /tmp/_bak.css
sed -i '' 's/\.el-message-box__content/_el-message-box__content/g' \
  web/dist/assets/$(ls web/dist/assets | grep '\.css$' | head -1)
cd web && npm run verify:css        # 期望：报「ElMessageBox 的样式不在产物中」
```

一个永远不会失败的校验器等于没有校验器。改动规则后请顺手做一次这个负向验证。

## 5. 守门验证（改样式后必跑）

### 5.1 页面

启动 dev server 后访问：

```
http://localhost:5173/dev/style-check
```

这个页面注册在 `constantRoutes` 里，**不需要登录**（自检页，不读任何用户数据）。
放在 `businessRoutes` 会出问题：业务路由要等登录后才动态挂载，未登录的无头
浏览器只会拿到被守卫重定向的登录页 —— §5.2 的脚本在 P1 引入认证后就曾因此
**静默失效**（断言抓不到结果，但报错只说「页面中未找到结果快照」）。
生产构建下由路由守卫的 ⓪ 号分支一律重定向到 404（`meta.devOnly`）。

`web/src/views/dev/StyleCheckView.vue` 用**运行时断言**代替肉眼看 ——
直接读 `getComputedStyle` / `getBoundingClientRect` 的真实计算结果。
它覆盖 10 项断言：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | `el-button` 背景不透明 | `background-color` ≠ 透明，且 `padding-left` ≥ 8px |
| 2 | **Tailwind preflight 已关闭** | 未被类修饰的原生 `<h1>`：`font-size` ≥ 24px 且 `font-weight` ≥ 700 |
| 3 | `el-input` 边框正常 | `box-shadow` 或 `border` 至少其一可见 |
| 4 | `el-icon` 行内布局正常 | 段落保持单行，图标落在行框内，svg 为正方形 |
| 5 | `el-icon` 垂直居中 | svg 为正方形，上下间隙差 < 1.5px |
| 6 | **`el-button class="w-full"` 生效** | 按钮宽度 = 父容器内容宽度（误差 < 2px） |
| 7 | `flex` / `gap-4` 生效 | `display: flex`，`column-gap: 16px` |
| 8 | `p-4` 生效 | `padding-top: 16px` |
| 9 | 层顺序声明已注入 | 存在以 `@layer theme, base, el, ...` 开头的声明 |
| 10 | **命令式 API 的样式已生效** | 真的弹一个 `ElMessageBox`，量到背景不透明且尺寸 ≥ 200×50px |

**第 2、6、10 项是整套方案的关键判据：**

- 第 2 项直接检出 preflight 是否被误开启。选原生 `<h1>` 是因为：
  preflight 会把 `h1` 重置为 `font-size: inherit; font-weight: inherit`，
  而未受影响时浏览器默认是 `2em` / `bold`（body 14px → 28px）。对比极明显。
- 第 6 项直接检出层优先级是否正确。如果 Element Plus 没进 `@layer el`，
  按钮宽度会被 `.el-button` 的无层样式锁死，与父容器宽度差距会非常明显。
- 第 10 项检出命令式 API 的样式有没有被引入（见 §2.4）。它**必须真的弹一个
  `ElMessageBox`**：模板里的 `<el-dialog>` 走的是另一条样式引入路径，
  它正常恰恰证明不了命令式 API 正常 —— 这正是该故障能长期漏过的原因。

> 第 10 项测的是 `offsetWidth` / `offsetHeight` 而不是
> `getBoundingClientRect()`：后者返回**变换后**的尺寸，弹出动画（scale）
> 进行中会让宽度读数偏小，产生随机失败。`offset*` 是布局尺寸，不受 transform 影响。
> 断言完成后在 `finally` 里 `ElMessageBox.close()` —— 它挂在 `<body>` 上，
> 不收起会留一层遮罩，让后续断言与截图一起失真。

### 5.2 命令行自动断言

```bash
bash scripts/verify-style-check.sh
```

用无头 Chrome 加载该页，从隐藏的 `<pre data-testid="style-check-report">`
里提取机器可读的 JSON 结果并断言。

脚本**不碰开发库**：自建临时库 `sec_risk_style_e2e` 并把后端指过去，退出时
整体 `DROP`（另挂 INT/TERM 兜底，Ctrl-C 也收干净）。API 端口用 **18083** 而不是
8080 —— 8080 是本机 dev server 的端口，而脚本自己要起一个后端，撞上去只会得到
bind 失败，报错却是「进程提前退出」，看不出是端口冲突。前端 dev server 走 5174。

输出形如：

```
样式共存守门验证全部通过 ✅ —— 通过 10/10 项
```

### 5.3 断言设计的四个坑（写测试时注意）

1. **`ElInput` 会把 `$attrs` 透传到内层 `<input>`**，不是根节点。
   所以 `data-check` 挂不到 `.el-input` 上 —— 必须用外层容器做锚点，
   选择器写成 `[data-check="input-box"] .el-input__wrapper`。
2. **不能用「svg 的 `display` 是不是 `block`」判断 preflight**。
   svg 是 `.el-icon`（`display: inline-flex`）的 flex item，
   其 `inline` 会被 CSS 规范块化成 `block` —— Element Plus 的图标永远是 `block`。
3. **不要用 `requestAnimationFrame` 等待布局稳定**。
   无头浏览器（以及被切到后台的标签页）会节流甚至完全不触发 rAF，
   断言会永远卡在等待里，表现为「页面正常但结果为空」。
   本项目统一用 `setTimeout`。
4. **量尺寸用 `offsetWidth` / `offsetHeight`，不用 `getBoundingClientRect()`**。
   后者返回的是**变换后**的尺寸：弹出动画（scale / zoom）进行中读数会偏小，
   于是同一个页面时而通过时而失败。`offset*` 是布局尺寸，不受 `transform` 影响。
   （第 10 项断言就是因为这条才稳定的。）

## 6. 代码风格约定

**格式、类型、静态检查三者职责严格分离，不重叠：**

| 关注点 | 工具 | 命令 |
|---|---|---|
| 代码格式 | Prettier | `npm run format` / `npm run format:check` |
| 类型正确性 | vue-tsc | `npm run typecheck` |
| 明显错误 | ESLint | `npm run lint` |

### 6.1 为什么 ESLint 不负责格式

`eslint-plugin-vue` 的 `flat/recommended` 自带 20+ 条**纯排版**规则
（`vue/max-attributes-per-line`、`vue/singleline-html-element-content-newline` …）。
它们和 Prettier 对「一行放几个属性」的答案不一致，结果是
`npm run format` 刚改完，`npm run lint` 立刻报错，来回推翻。

实测数据：修好环境变量声明后，剩余 99 个 warning 里有 **94 个**属于这类冲突。

因此 `web/eslint.config.js` 铺了一层 `eslint-config-prettier`
关闭全部纯格式规则，只按需重新打开少数几条（`vue/attributes-order`、
`vue/multi-word-component-names`、`vue/attribute-hyphenation`、
`vue/html-self-closing`）。

> ⚠️ `vue/html-self-closing` 的取值刻意与 Prettier 的输出对齐：
> `void: 'always'`（`<img />`）、`normal: 'never'`（`<div></div>`）、
> `component: 'always'`（`<MyComp />`）。改成别的值会让
> `eslint --fix` 与 `prettier --write` 互相推翻。

### 6.2 ESLint 全局变量必须显式声明

ESLint 9 起的扁平配置**移除了 `env` 推导**。不声明就会出现
`document` / `console` / `HTMLElement` 全被报成未定义变量
（本项目实测 24 个 error）。

配置按「文件实际运行在哪一侧」分别注入：

| 文件范围 | 环境 |
|---|---|
| `vite.config.ts`、`plugins/**`、`scripts/**` | Node |
| `src/**` | Browser |

同时 `src/**/*.{ts,vue}` 关闭 `no-undef` —— 这是 typescript-eslint 的官方建议：
TS 自己就会报「找不到名称」，而且它能正确理解**只在类型空间存在**的全局名
（如 `env.d.ts` 里 `declare` 的 `__APP_VERSION__`），而 ESLint 的 `no-undef`
只认运行时的值，对这类名字会大面积误报。

### 6.3 配置顺序陷阱

ESLint 扁平配置是**后面的同名规则覆盖前面的**。因此：

- 无 `files` 的通配块必须放在**最后**，否则会把早于它声明的豁免重新盖掉
- 本项目中「命令行脚本允许 `console.log`」这条豁免就专门放在配置最末尾，
  因为它是无差别覆盖需求的对立面（见 `eslint.config.js` 第 ⑥ 段注释）

## 7. 故障排查

| 现象 | 最可能的原因 | 处理 |
|---|---|---|
| `w-full` / `mt-4` 加在 `el-*` 上无效 | Element Plus 未进 `@layer el` | 检查 `vite.config.ts` 里 `viteCssLayerPlugin` 是否在 `vue()` / `tailwindcss()` **之后** |
| **退出登录 / 删除确认框只剩一层灰遮罩，内容与按钮没样式** | 命令式 API 的样式没被引入 | 检查 `web/src/main.ts` 里的 `message-box/style/css` 与 `message/style/css` 两行是否还在（见 §2.4）；`npm run verify:css` 的第 ④ 项会直接报出来 |
| **`ElMessage` 提示条没有背景、圆角、阴影** | 同上 | 同上 |
| 开发正常，构建后样式错乱 | 层顺序声明未被注入到产物 | `npm run verify:css` 看首行；确认插件注入在 `generateBundle` 而非 `transform` |
| 按钮背景透明 / 输入框无边框 | preflight 被开启 | 检查 `index.css` 中 `@import 'tailwindcss/preflight.css'` 是否被取消注释 |
| 图标把行高撑成两倍 | preflight 生效，`svg { display: block }` | 同上 |
| 层顺序变成 `el, theme, base, ...` | 层顺序声明晚于 Element Plus 的 CSS 被解析 | 确认 `transformIndexHtml` 的注入位置是 `head-prepend` |
| ESLint 报大量「未定义变量」 | `globals` 未声明或未安装 | `eslint.config.js` 第 ③④ 段；`globals` 必须是直接依赖 |
| `format` 与 `lint` 来回改 | 纯格式规则未被关闭 | 确认 `prettierConfig` 排在自定义规则**之前** |

## 8. 变更触发条件

出现以下任一情况时，**本文档与守门验证页必须同步更新**：

- 层顺序、层名发生变化
- `web/plugins/vite-plugin-css-layer.ts` 的注入时机变化
- 引入新的 UI 库（需要评估它是否 unlayered，是否需要额外包层）
- Tailwind 大版本升级（v4 的 `@import` 与 `@layer` 语义可能与 v3 不同）
- 恢复或移除 preflight
- **新增 Element Plus 的命令式 API**（`ElNotification`、服务式 `ElLoading` 等）
  → 必须同步补一条 `style/css` import，并更新 §2.4 的清单与守门脚本的映射表

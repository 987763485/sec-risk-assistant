# 03 · 认证、授权与接口契约

> 本文描述 P1 的安全设计与它的**理由**。接口字段以 `docs/openapi.yaml` 为准  
> （那是唯一真相源），本文只解释「为什么是这样」。

---

## 1. 认证：Cookie 会话 + 双提交 CSRF

### 1.1 为什么不把令牌放 `localStorage` + `Authorization` 头

`localStorage` 对任何一段在页面上执行的 JS 都是可读的。一次 XSS  
（哪怕来自第三方依赖、一条用户输入的富文本）就能把令牌整个搬走，  
而令牌搬走后攻击者不需要再回到这个站。

本方案改为三枚 Cookie：

| Cookie    | HttpOnly | Path            | 有效期   | 作用              |
| --------- | -------- | --------------- | ----- | --------------- |
| `sr_at`   | ✅        | `/`             | 15 分钟 | 访问令牌（JWT HS256） |
| `sr_rt`   | ✅        | **`/api/auth`** | 7 天   | 刷新令牌（不透明随机串）    |
| `sr_csrf` | ❌        | `/`             | 7 天   | 双提交 CSRF 令牌     |

三个设计点：

1. **HttpOnly**：JS 读不到令牌，XSS 拿不走会话。代价是前端无法判断  
   「我是否已登录」，只能问后端（`GET /api/auth/me`）——这个代价可以接受，  
   因为守卫本来就要做这件事来拿权限码。
2. **刷新令牌限定 `Path=/api/auth`**：浏览器只在访问 `/api/auth/*` 时携带它。  
   业务请求即使被注入也无法顺带泄露刷新令牌。攻击者要拿它，  
   必须主动请求刷新接口——而那会触发重放检测。
3. **`sr_csrf` 刻意非 HttpOnly**：前端必须能读到它才能回填到请求头，  
   这正是「双提交」能成立的前提。它的安全性**不来自保密**，  
   而来自「攻击者跨站时读不到本域 Cookie」。

### 1.2 为什么需要 CSRF 防护

Cookie 是浏览器**自动携带**的。这意味着一个第三方站点可以让用户的浏览器  
带着有效 Cookie 向本服务发出请求。`SameSite=Lax` 挡掉了大部分场景，  
但不足以覆盖所有浏览器与部署形态，因此再加一层双提交：

- 写请求必须同时满足：`X-CSRF-Token` 头 == `sr_csrf` Cookie
- 且 `Origin` 在服务端白名单内（**缺失 `Origin` 的跨站请求按拒绝处理**）

攻击者可以让浏览器自动带上 Cookie，但**无法读取** Cookie 的值去构造请求头，  
也**无法伪造** `Origin`。两条同时要求，纵深足够。

> 实测记录：e2e 冒烟验证第一次跑时，登录被 403 拦下，  
> 原因是预览服务的源 `http://127.0.0.1:4173` 不在白名单里。  
> 这说明 Origin 校验是真在生效的，而不是写着好看。

### 1.3 令牌里**不**放权限码

JWT 只承载身份（`sub` / `iat` / `iat_ms` / `exp`），不放角色与权限。  
权限在**每个请求**上现查一次数据库（`users` + `user_roles` 两次索引查询）。

这个交换非常划算：

|         | 权限放 JWT      | 权限每请求现查（本方案）             |
| ------- | ------------ | ------------------------ |
| 禁用账号    | 最长 15 分钟后才生效 | **立即生效**                 |
| 撤销角色    | 最长 15 分钟后才生效 | **立即生效**                 |
| 改密码后旧会话 | 需要额外机制       | **立即生效**                 |
| 每请求成本   | 0            | 约 2 次主键/外键索引查询（本地 < 1ms） |

对一个「风险评估」类系统来说，「撤权之后还能继续操作 15 分钟」  
是不可接受的；而每请求 < 1ms 的成本可以忽略。**先保证正确性，再谈优化。**

## 2. 令牌生命周期

```
登录 ──► 签发 [access 15m] + [refresh 7d, 链 family_id]
              │
              │ access 过期
              ▼
         401 AUTH_TOKEN_EXPIRED
              │
              │ 前端单飞刷新（并发请求共享同一次刷新）
              ▼
         POST /api/auth/refresh
              ├─ 旧 refresh 标记 used_at，签发新的（轮换）
              └─ 若旧 refresh 已被用过 ──► 判定重放
                                          └─► 吊销整条 family_id
                                              审计 auth.token_reuse_detected
```

### 2.1 登出为什么必须写 `token_not_before`

JWT 无法撤回。若不额外处理，用户点了登出之后，那枚访问令牌  
仍能被继续使用直到自然过期——**用户以为安全了，实际没有**。

因此登出会：

1. 吊销整条会话链（登出的语义是「结束这次登录」，不是「作废这一个令牌」）
2. 把 `users.token_not_before` 推到当前时刻 → 该账号此前签发的**所有**访问令牌立即失效

「禁用账号」「重置密码」走同一条机制，因此也都即时生效。

### 2.2 前端为什么必须「单飞刷新」

`web/src/api/http.ts` 里的 `refreshInFlight` 不是性能优化，是**正确性要求**：  
并发的两个请求各自刷新，第二个会带着已使用的令牌到达后端，  
被判定为重放 → 整链吊销 → 用户被自己的页面踢下线。

前后端这两处是成对设计，改一处必须同时看另一处。

## 3. 授权：权限码体系

### 3.1 权限码形式

`<资源>:<动作>`，动作只有 `read` / `write` 两档。当前 21 个：

```
user:read/write        role:read/write        audit:read
asset:read/write       dictionary:read/write  file:read/write
vulnerability:read/write  assessment:read/write
remediation:read/write    report:read/write
system:read/write
```

只有两档是刻意的最小化：

- 档位一多，每个接口都要回答「这算 read 还是 operate？」，评审成本急剧上升
- 真正的细粒度控制需求出现时，再引入 `<资源>:<动作>:<范围>` 这样的三段式，  
  而不是提前把复杂度铺开

### 3.2 内置三角色

|                       | admin                    | assessor    | auditor      |
| --------------------- | ------------------------ | ----------- | ------------ |
| 用户管理                  | `user:read` `user:write` | `user:read` | `user:read`  |
| 业务全流程（资产/漏洞/评估/整改/报告） | ✅ 读写                     | ✅ 读写        | 只读           |
| 审计日志                  | `audit:read`             | ❌           | `audit:read` |
| 系统配置                  | 读写                       | ❌           | ❌            |

`auditor` 的权限集是从 `readOnlyPermissions()` **派生**出来的，  
不是手写一份。手写的话，将来新增资源时很容易忘记同步，  
表现为「审计员看不到新模块」——而审计员看不到的东西，等于没被审计。

启动时会跑 `CheckPermissionRegistry()` 自检：新增权限码若忘了登记进  
`allPermissions`，进程直接启动失败。这是防止「加了权限码但忘了授权」的护栏。

### 3.3 权限码也不下发「角色 → 权限」映射

`GET /api/roles` 只给角色本身，不给每个角色有哪些权限。

理由：前端一旦拿到映射，就会有人写出 `if (角色是 admin) 显示这个按钮`，  
于是前端出现第二份权限表。两份表必然逐渐失配，而失配的表现是  
「菜单里有的点进去 403」或「有权限却看不到入口」——这类缺陷很难定位。

前端只用 `GET /api/auth/me` 下发的 `permissions` 数组做判断，单一来源。

## 4. 中间件链

顺序不可随意调整，每一处都有具体原因：

```
engine : RequestID → Recovery → AccessLog → SecurityHeaders → CORS
/api   : CSRF → Audit
受保护 : Authn → RequirePasswordChanged → RequirePermission
```

| 约束                             | 原因                                         |
| ------------------------------ | ------------------------------------------ |
| `RequestID` 必须最前               | 后续所有中间件的日志都要带上它                            |
| `Recovery` 早于 `AccessLog`      | 否则 panic 的请求产不出访问日志                        |
| `Audit` 早于 `Authn` 注册          | 它在 `c.Next()` 返回后才读标注，此时 `Authn` 已把主体写进上下文 |
| `CSRF` 早于 `Authn`              | 跨站请求不该消耗数据库查询                              |
| `Authn` 早于 `RequirePermission` | 权限判断需要主体                                   |

### 4.1 `RequirePasswordChanged` 用白名单而非黑名单

```go
var mustChangePasswordAllowlist = map[string]struct{}{
    "/api/auth/me": {}, "/api/auth/csrf": {}, "/api/auth/password": {},
    "/api/auth/logout": {}, "/api/auth/refresh": {},
}
```

白名单的含义是：**新增接口若忘记登记，默认被拦下**（安全侧失败），  
而不是默认放行（危险侧失败）。默认值的方向决定了忘记时会发生什么。

### 4.2 审计标注是强制的

写请求若成功却没有标注审计信息，中间件会打 `Warn`：  
「写操作未标注审计信息，本次操作不会留下审计记录」。

不做「按 方法+路径 自动推导」的原因：自动推导只能得到  
`POST /api/users` 这种机器可读、人不可读的信息，  
无法区分「新建用户」与「重置密码」，更拿不到变更前后的值。  
审计的价值恰恰在后者。

### 4.3 审计写入失败**不改变**业务结果

调用到写审计这一步时，业务写操作通常已经提交。若此时把请求改判为失败，  
用户会以为操作没生效而重复提交——由此产生的重复数据，  
比丢掉一条审计记录严重得多。因此只记 Error 日志，由告警链路兜住。

**代价说清楚**：极端情况下（审计表写入持续失败）会出现「有业务、无审计」。  
这是权衡后的取舍，不是疏忽。

## 5. 防滥用

| 机制    | 防的是      | 实现                                              |
| ----- | -------- | ----------------------------------------------- |
| 账号锁定  | 盯着一个账号猛试 | 连续失败 ≥ 5 次 → 锁定 15 分钟                           |
| IP 限流 | 换着用户名轮着试 | 同一来源 15 分钟内 ≤ 20 次登录                            |
| 统一错误码 | 账号枚举     | 用户名不存在与密码错误返回同一个 `AUTH_INVALID_CREDENTIALS`     |
| 等耗时比较 | 计时侧信道    | 用户名不存在时仍执行一次 argon2id 校验（`burnPasswordCompare`） |

### 5.1 两个必须记住的实现细节

**① `RecordLoginFailure` 的字段顺序**

MySQL 的 `UPDATE` 赋值**从左到右求值**。若把  
`failed_login_attempts = failed_login_attempts + 1` 写在 `locked_until` 之前，  
那么判断「是否达到阈值」时读到的还是**自增前**的值，锁定会提前一轮触发。

同时不能用 GORM 的 `Updates(map[string]any{...})`——它会按键名排序，  
把顺序控制权交给了一个排序算法。

**② 可信代理必须显式配置**

gin 的默认值是「信任所有代理」。那意味着 `X-Forwarded-For` 可被客户端  
任意伪造，后果有两层：

- **绕过限流**：每次请求换一个伪造 IP，限流形同虚设
- **污染审计**：审计日志里的操作人 IP 可以指向任意地址，追责链断掉

因此 `SR_SERVER_TRUSTED_PROXIES` 只应填**反向代理真实所在**的网段。  
配置非法时路由层会降级为「不信任任何代理」并打 Warn，而不是静默使用不安全默认值。

## 6. 接口契约的单一真相源

### 6.1 手写 spec，而不是从注解生成

`docs/openapi.yaml` 是**手写**的，不是 swag 之类的工具从 handler 注释生成的。

理由是「真相源放在哪里」这个选择：

|       | 注解生成（swag 等）               | 手写 spec（本方案）        |
| ----- | -------------------------- | ------------------- |
| 真相源   | handler 的注释                | `docs/openapi.yaml` |
| 注释写错  | 编译不报错、lint 不管              | `make api-check` 失败 |
| 与实现脱节 | 注释不会因为编译失败而报错，必然慢慢腐烂       | 双向比对，任何一侧多/少端点都变红   |
| 最终状态  | 「文档」和「实现」各说各话，而工具只保证两者都能生成 | 契约与代码被强制对齐          |

### 6.2 双向一致性校验

`server/internal/router/openapi_test.go` 把契约与 gin **真实路由表**逐条比对：

```
① 路由有、spec 没有  → 新接口悄悄上线，前端与调用方无从知晓
② spec 有、路由没有  → 接口删了或改名了，契约残留成幽灵端点
```

单向检查只能发现一半问题，两个方向各自代表一类事故，因此都查。

同一组测试还断言了：

- 每条受保护路由都在契约里声明了 `SessionCookie` 要求
- 每个写请求都在契约里声明了 `CSRFToken` 要求
- 契约里的公开端点集合与 `router.PublicRoute` 白名单完全一致

### 6.3 前端类型由契约生成

```
docs/openapi.yaml ──(openapi-typescript)──► web/src/api/generated/schema.d.ts
                  ──(按 JSON Pointer 校验 $ref/operationId/路径参数)──► 结构自检
```

`make api` 重新生成，`make api-check` 校验是否已过期，后者已挂进 `make lint`。

于是流程被固定为：**改契约 → 重新生成类型 → 跑 `make api-check`**。  
忘了中间任何一步都会失败，而不是「等到联调才发现」。

生成的类型还顺带带来两个好处：

- `PermissionCode` 是字符串联合类型，`can('user:raed')` 这类拼写错误  
  **在编译期**就被拦下（权限码拼错的表现为「菜单莫名消失」，运行时很难查）
- `ErrorCode` 是联合类型，前端 `switch` 可以做穷尽性检查

### 6.4 契约里没有 `nullable`

OpenAPI 3.0 用 `nullable: true`，3.1 用 `type: [string, "null"]`。  
两者生成出的 TypeScript 类型完全不同（一个是 `string`，一个允许 `null`）。  
契约校验器**显式禁止** `nullable`，并把版本钉在 `3.1.x`，  
避免两种写法混用产生「看起来对、生成出来的类型却是错的」这类最难查的问题。

### 6.5 对外字段风格由接口层显式定义

`model` 层结构体**不加 json tag**，对外视图在 handler 里单独定义  
（`auditLogView` / `roleView` / `UserView`）。

这不是啰嗦，而是两个具体问题的修复：

- `model.AuditLog` 无 tag → 直接序列化输出 `ID` / `Action` / `StatusCode`  
  这类 Go 风格字段名，与全局 snake_case 不一致
- `model.Role` 同样问题 → `/api/roles` 返回 `Code` / `IsBuiltin`

前者已修，后者在 P1 契约化阶段被发现并修掉，并补了回归断言  
（`verify-auth.sh` 会检查 `is_builtin` 存在、`IsBuiltin` 不存在）。

## 7. 前端权限驱动

### 7.1 动态路由：未授权的路由**不存在**

业务路由不在应用启动时注册，而是在守卫里确认登录态后，  
按当前用户实际持有的权限码逐条 `router.addRoute`。

带来两个性质：

1. 未登录时路由表里没有任何业务页面，手敲 URL 只会落到 404
2. 权限不足的页面同样如此，因&#x6B64;**「前端忘记隐藏入口」也不会造成访问**

守卫里有一个容易踩的点：`router.addRoute` 之后当前这次导航是在旧路由表上  
解析出来的，结果不可信。必须用原目标地址**重新导航一次**：

```ts
if (dynamicDisposers.length === 0) {
  registerBusinessRoutes()
  return { path: to.path, query: to.query, hash: to.hash, replace: true }
}
```

少了这一步，典型表现是「刷新页面白屏」。

### 7.2 菜单是路由表的投影

菜单由路由表推导（`router/menu.ts`），不单独维护一份菜单配置。  
两份配置意味着「新增页面时改了一处忘了另一处」，表现为页面能访问但菜单没入口——  
这类缺陷不报错，只会被用户当成功能没做。

### 7.3 前端权限判断只是体验层

**真正的访问控制在后端**。前端隐藏菜单与按钮，是为了不让人点进去吃 403，  
不是安全边界。任何一处后端接口都必须自己挂 `RequirePermission`，  
`TestProtectedRoutesRejectAnonymous` 会用匿名请求遍历真实路由表来兜住这一点。

## 8. 验证矩阵

| 验证            | 命令                 | 规模                            | 覆盖                                                                    |
| ------------- | ------------------ | ----------------------------- | --------------------------------------------------------------------- |
| 契约结构 + 路由双向对齐 | `make api-check`   | 17 端点                         | 悬空 `$ref`、漏写 `operationId`、路径参数未声明、安全方案名字错、`nullable` 误用、未被引用的 schema |
| 后端授权规则        | `make verify-auth` | **74 项断言**                    | CSRF、Cookie 属性、三角色权限矩阵、管理员自保护、禁用即时失效、刷新轮换与重放、登录锁定、审计留痕、登出             |
| 后端单元测试        | `go test ./...`    | auth 21 / middleware / router | 含 `alg=none` 拒绝（alg confusion 安全回归）、角色矩阵锁定                            |
| 前端端到端         | `make verify-web`  | **24 项断言**                    | 守卫重定向、强制改密链路、登录、顶栏身份与 `/auth/me` 逐字对账、权限驱动菜单、动态路由缺失导致 404、用户列表取数、CSS 分层生效                   |

前端 e2e 使用系统 Chrome（无需下载 Chromium），并跑在**隔离的临时数据库**上——  
不复用开发库，因为引导管理员的口令只在账号不存在时生效，且冒烟过程会创建账号。

## 9. 已知取舍与后续

| 项                          | 现状                | 备注                                    |
| -------------------------- | ----------------- | ------------------------------------- |
| 无「记住我」                     | 访问 15 分钟 / 刷新 7 天 | 需要时通过延长 refresh TTL 实现，不应动 access TTL |
| 无 MFA                      | 未实现               | 引入时须同步考虑「MFA 未完成」这一中间态在守卫里的表达         |
| 无限流之外的防爬                   | 未实现               | 上线前若暴露公网，需在 Nginx 层补全局限流              |
| 审计日志无归档                    | 单表增长              | `created_at` 已有索引，随时可加归档任务            |
| `token_not_before` 粒度是整个账号 | 登出会踢掉该账号所有设备      | 若需「只登出当前设备」，需改为按 `family_id` 记录已吊销链   |

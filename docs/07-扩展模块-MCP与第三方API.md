## 1. 范围

**做**：

1. **情报源的接入配置**：建 / 读 / 改 / 停用。凭据只存「环境变量名」；**没有删除接口**（§2.8）。
2. **拉取编排**：一次拉取 = 取目标 CVE 列表 → 逐个向适配器取数 → 归一化 → upsert 快照 → 回写运行态 → 留审计。
3. **出站安全约束**：`base_url` 是用户可控的出站目标，SSRF 是 P7 的头号风险（§6）。
4. **两个适配器**：`nvd`（真实实现，走 NVD REST API 2.0）+ `local`（离线驱动，不访问网络）。
5. **前端**：系统管理下的集成配置页；漏洞详情里的情报快照区与拉取对话框。
6. **MCP Server 骨架**：stdio 传输，复用后端账号与 RBAC（§11）。

**不做**（每一条都是刻意的边界，不是「还没做」）：

| 不做 | 理由 |
|---|---|
| 定时 / 批量同步、订阅推送 | 拉取一律由人或模型**显式触发**。定时任务一停，库里的情报就静默变旧而没有任何地方报警（同 `docs/13` D4「逾期不落库」的同一条理由） |
| 拉取历史表 | 审计的 `integration.fetch` 已经承载「谁、何时、拉了哪条、成败」。再建一张表就是同一事实的第二个落点（§2.2） |
| 凭据入库 / 界面直接填密钥 | 只允许 `SR_INTEL_` 前缀的环境变量名 —— 放开自由度等于开出一个「读取进程内任意环境变量」的原语（§2.3） |
| 第二个真实情报源 | 骨架期只有 `nvd` / `local`。新增一个源 = 一个文件 + 注册表一行（§8），而不是一堆散落改动 |
| MCP 自建身份体系 | 复用后端账号，权限严格等于该账号的权限（§11.1） |
| 集成配置的删除 | 它是审计记录指向的对象（§2.8） |
| 情报参与风险打分 | 快照只展示。`riskengine` 是纯函数、输入只有资产与漏洞，混入随时可变的外部数据会让「同一次评估的结果可复现」这条性质失效 |

## 2. 八项决策与理由

编号 D1–D8 在本文件、迁移 `000008` 的头部注释与 `service/integration.go` 的注释里被引用；**改动实现时必须同步改这里的理由**，否则「为什么这么写」会失去唯一落点。

### 2.1 D1 —— 情报接在**漏洞层**，不接整改单层

外键指向 `vulnerabilities`，不指向 `remediations`。

整改单的粒度是 `(asset_id, vuln_id)` 这一个组合（见 `docs/13` §2.1），而情报描述的是**漏洞本身**（某条 CVE 的 CVSS 分、描述、参考链接），与「哪台机器上有它」无关。挂在整改单上会导致同一条 CVE 在 N 台资产上被拉 N 次、存 N 份，且其中任意一份更新都不会传到其余 N-1 份。

接在漏洞层之后，一次拉取的结果对该漏洞的**所有**整改单可见。

### 2.2 D2 —— 两张表分工；**拉取历史不建表**

| 表 | 角色 | 唯一键 |
|---|---|---|
| `integrations` | 接入**配置** + 最近一次运行态 | `uk_integrations_name (name)` |
| `vuln_intel` | 按漏洞聚合的情报**快照** | `uk_vuln_intel_identity (vuln_id, source, cve_id)` |

拉取历史刻意不建表：审计日志已用 `integration.fetch` 承载「谁在什么时候拉了哪条 CVE、成功还是失败」。再建一张 run 表，两处必然漂移 —— 审计写入失败不回滚业务，历史表清理又不影响审计。

代价是 `integrations` 里只保留**最近一次**运行态（`last_run_at` / `last_status` / `last_error` / `last_latency_ms`），列表页够用；要查历史就去审计页按 `action=integration.fetch` 过滤。

### 2.3 D3 —— 凭据永不入库，只存 `SR_INTEL_` 前缀的环境变量名

表里只有 `credential_env`（**变量名**），没有 `credential_value`。

⚠️ **`SR_INTEL_` 前缀是安全边界，不是命名规范。** 若允许任意变量名，任何能改集成配置的人都能填入 `SR_AUTH_JWT_SECRET` 再触发一次拉取，把一个「拉取情报」的动作变成「把 JWT 密钥原样发到我的服务器」。服务层的 `credentialEnvAllowed` 与 `credentialEnvPattern` 是同一约束的两种表达，必须同步。

配套的两件事：

- 视图里给出 `credential_present`（该变量当前是否已设置且非空）。它只回答「有没有」，**绝不回答「是什么」**。这一位专治最常见的运维疏漏：配了名字却忘了设变量，症状是「一拉就失败：401」，排查方向会被引向「API Key 是不是失效了」。
- 出口处 `sanitizeFailureMessage` 把凭据明文替换成 `***` 兜底 —— 但**不写进去永远比写了再擦可靠**，兜底不是防线。

### 2.4 D4 —— SSRF 两层防护，缺一不可

详见 §6。一句话：**第一层**在保存时与拉取前解析域名后逐个校验 IP；**第二层**在 `net.Dialer.Control` 里于 `connect(2)` 之前复核实际 `sockaddr`。

### 2.5 D5 —— 权限三分工：建改 / 读 / 拉取挂**三个不同的**权限码

| 动作 | 权限码 | 谁有 |
|---|---|---|
| 读配置（列表 / 单条 / 看情报） | `integration:read` | admin、assessor、auditor |
| 拉取情报 | `integration:write` | admin、assessor |
| 建 / 改配置（含 `base_url`、凭据指向、启停） | **`system:write`** | **只有 admin** |

`system:write` 与 `integration:write` 的分界是这条决策的**全部要点**：`base_url` 与凭据指向决定「服务器下一步向哪里发请求」。若把建改也挂在 `integration:write` 上，那么「给评估员开拉取这个动作」就等于顺带把「让他改出站目标」也给了出去 —— 而后者才是 SSRF 的真正入口。

`auditor` 由 `readOnlyPermissions()` 自动获得 `integration:read`（凡是 `:read` 后缀都收），因此审计岗能看见配置与运行态，但既不能改也不能拉。

### 2.6 D6 —— 拉取接口**恒定 200**，唯一例外是出站被拒

`POST /api/integrations/:id/fetch` 在**全部失败**的情况下也返回 200，结果对象里用 `succeeded` / `failed` / `errors` 区分成败。

理由：拉取天生是「部分成功」的 —— 一次拉 3 条 CVE，其中 1 条上游未收录，另外 2 条**已经写进库了**。只回一个 502 会让调用方以为什么都没发生，从而重复点击。把它做成 200 + 结构化结果，调用方的正确写法就只有一种：读 `succeeded`。

唯一的例外是出站目标被安全策略拒绝 → **400 `INTEGRATION_ENDPOINT_BLOCKED`**。这不是「拉取失败」，而是「这个配置不允许发请求」，用户的下一步动作是改配置而不是重试 —— 混进 `failed` 里会让它看起来像一次偶发的网络问题。

> 前端与 MCP 工具描述里都写明了这一条。这是 P7 里唯一一处「HTTP 状态码不含全部语义」的接口。

### 2.7 D7 —— 快照的两条「只在此处回答」的规则

**① 严重度入库时归一化一次，读取时不重算。**

`severity` 在写库前由 `NormalizeSeverity(raw, cvssScore)` 归一化到五个取值之一，之后不再重算。刻意**不**在读取时按 `cvss_score` 现算档位 —— 那会让「上游标 `high` 但我们算出 6.5」在同一行里给出两个互相矛盾的答案。情报表的定位是**快照**，快照的本分是「记下当时上游说的是什么」。

上游文案不统一（NVD 给大写的 `CRITICAL`，别的源可能给 `严重` / `Moderate` / 空串），无法识别时退回按 CVSS 分推导，两者都没有才落到 `unknown`。**刻意不用「默认 medium」**：把未知当中间值会在统计图里凭空造出一批「中危」。

**② `source` 存适配器**类型**，不存 `integrations.id`。**

类型是适配器的不变量，而集成配置可以被停用、改名、将来还可能被重建。若存 id，删掉配置会让历史情报变成指向一个不存在配置的行（同 `docs/13` D1 的教训：业务身份不能建在会被重算或删除的表上）。

这条约束只体现在 DDL 与一次 upsert 的比较里，用接口行为**很难**测出来，因此守门脚本直接查 `information_schema`（§12 第 8 节）。

### 2.8 D8 —— 没有 DELETE；「不再使用」由 `enabled=false` 表达

`DELETE /api/integrations/:id` **未注册**（gin 默认 404）。

集成配置是审计记录指向的对象 —— `integration.fetch` 的明细里记着 `integration_id` / `integration_name` / `base_url` / `type`。允许删除会让历史审计变成指向空地址的记录，于是「三个月前是谁把这个地址配上、又向它发了多少次请求」再也无法回答。停用足够覆盖「不再使用」这个需求，而且**停用本身也被审计**。

守门脚本用两条断言把这个立场钉住：`DELETE` 返回 404；停用后拉取返回 409 `INTEGRATION_DISABLED`。

## 3. 数据模型

完整 DDL 与字段语义见 `docs/02` §12；迁移文件头部的七条设计约束是 DDL 的一部分，改动前请先读完。

### 3.1 `integrations`（接入配置 + 最近一次运行态）

配置列：`name`（唯一）、`type`、`base_url`、`credential_env`、`enabled`、`timeout_ms`。
运行态列：`last_run_at` / `last_status` / `last_error` / `last_latency_ms`。

三条容易踩的约束：

| 约束 | 说明 |
|---|---|
| 名称唯一由**数据库**兜底 | `uk_integrations_name`。服务层的「先查后插」在并发下有竞态窗口，两个人同时提交同名集成会双双通过（同 `docs/13` D2 的教训） |
| `timeout_ms` 越界**收敛**而不报错 | 收敛到 `[1000, 30000]`。一个不合理的超时不值得打断一次用户发起的拉取，但也绝不能让它穿透到网络层 |
| `updated_at` 是**行**更新时间 | 运行态与配置同表，所以一次拉取也会刷新它。界面**不得**把这一列呈现为「配置最后修改时间」 |

### 3.2 `vuln_intel`（情报快照）

唯一键 `(vuln_id, source, cve_id)` —— **必须含 `cve_id`**。`vulnerabilities.cve_ids` 是逗号分隔串（一条漏洞可挂多个 CVE），一次拉取会对每个 CVE 各落一条；唯一键只有 `(vuln_id, source)` 时，第二条 CVE 的情报会**覆盖**第一条，表现为「拉了两个 CVE，库里只剩一个」，且不报错。

外键 `fk_vuln_intel_vuln` 用 **`ON DELETE CASCADE`**，与 `vulnerabilities.source_file_id` 的 `RESTRICT` 形成刻意的对照，判据是**谁是主体**：

- 情报是漏洞的**派生属性** —— 漏洞没了，情报没有独立存在意义 → CASCADE；
- 漏洞是扫描文件的**业务事实** —— 文件删了，漏洞记录仍要解释「它从哪来」 → RESTRICT + 服务层 409 引导。

`display_title` **不是列**，是视图层的回退值（`title` 为空时退回 `cve_id`）。回退放在后端：否则每个展示点都要记得写一次 `|| cveId`，漏掉的那一处会渲染成一片空白。

## 4. 接口契约

| # | 方法 + 路径 | 权限码 | CSRF | 审计 |
|---|---|---|---|---|
| 71 | `GET /api/integrations` | `integration:read` | 否 | — |
| 72 | `POST /api/integrations` | `system:write` | **是** | `integration.update` |
| 73 | `GET /api/integrations/{id}` | `integration:read` | 否 | — |
| 74 | `PATCH /api/integrations/{id}` | `system:write` | **是** | `integration.update` |
| 75 | `POST /api/integrations/{id}/fetch` | `integration:write` | **是** | `integration.fetch` |

（编号接 `docs/01` §5.1，累计 **75 个操作 / 53 条路径**；本节新增 5 个操作 / 3 条路径。）

**列表不分页。** 集成配置的数量级是「几个」，`IntegrationListView` 里没有 `total` / `page` 字段。这是本系统里唯一一个不分页的业务列表，与 `docs/02` 的分页纪律的区别是刻意的：分页的存在意义是「结果集可能很大」，而这里不可能。

**`PATCH` 按合并后的最终值整体校验**，不是「只校验本次传入的字段」。只把 `type` 从 `local` 改成 `nvd` 时，地址也要重新过一遍 SSRF 校验 —— 否则库里会留下一个「`nvd`（需要地址）却带着被改坏地址」的配置。

**写操作只有 5 个语义状态**，映射关系：

| HTTP | 错误码 | 触发条件 |
|---|---|---|
| 400 | `INVALID_PARAM` | 名称为空 / 空 PATCH / `vuln_id` 缺失 / CVE 编号格式非法 / 该漏洞没登记这条 CVE / 漏洞无 CVE / 单次超 5 条 |
| 400 | `INTEGRATION_TYPE_UNKNOWN` | 建时类型未知；或库里类型对应的适配器已不存在 |
| 400 | `INTEGRATION_ENDPOINT_BLOCKED` | 出站目标被拒（保存时或拉取前） |
| 400 | `INTEGRATION_CREDENTIAL_INVALID` | 变量名不以 `SR_INTEL_` 开头或不符 `^SR_INTEL_[A-Z0-9_]{1,48}$` |
| 404 | `INTEGRATION_NOT_FOUND` / `VULN_NOT_FOUND` | 对象不存在 |
| 409 | `INTEGRATION_NAME_TAKEN` | 名称重复 |
| 409 | `INTEGRATION_DISABLED` | 对已停用的集成发起拉取 |
| 409 | `INTEGRATION_CREDENTIAL_MISSING` | 登记了变量名，但服务进程里没有这个变量 |

**「请求本身不合法 → 400」与「请求没毛病但当前状态不允许 → 409」的分界**沿用既有纪律（见项目 MEMORY 的陷阱 #8）：所以「停用」「重名」「凭据缺失」是 409 而不是 400。

### 4.1 目标 CVE 的三条解析规则

`resolveTargetCVEs(vulnCVEIDs, requested)`：

1. 显式给了 `cve_id` → 它必须**属于该漏洞登记的列表**，否则 400（不是去上游碰运气）；
2. 没给 → 拉该漏洞登记的**全部** CVE；
3. 结果超过 **5 条** → 拒绝整批，提示「请指定要拉取的 cve_id」。

第 3 条是照 NVD 的限流（约 5 次/30 秒）定的。不设上限意味着用户点一次「拉取」会连发几十个请求，必然全部撞上限流，然后他看到的是一片红 —— 与其如此，不如让他先明确指定。

### 4.2 执行顺序：先校验 → 再取凭据 → 最后才发请求

这个顺序本身是一条安全约束：若反了，一次「凭据缺失」的拉取会先向 `base_url` 发出真实请求才报错。守门脚本第 6 节第 ⑦ 条专门证明这一点（凭据缺失时不出网）。

## 5. 权限模型

```
                    integration:read   integration:write   system:write
admin                     ✅                 ✅                ✅
assessor                  ✅                 ✅                ❌     ← 能拉取，不能改出站目标
auditor                   ✅                 ❌                ❌     ← 只读（readOnlyPermissions 自动派生）
```

守门脚本用三档角色逐个验证，手法是**用「404 而不是 403」证明闸门通过**：评估员对不存在的集成发起拉取，若拿到 404 说明他已经过了权限判断、进入了业务层；拿到 403 说明被拦在权限层。这样能把「权限配错了」与「对象不存在」彻底分开。

## 6. SSRF 两层防护

> 迁移 `000008` 约束 3 指向本节。改动 `pkg/intelfeed` 的出站逻辑前请先读完本节。

### 6.1 为什么这是 P7 的头号风险

`base_url` 是用户在界面上填的，也就是说：**谁能改集成配置，谁就能决定这台服务器下一步向哪里发起请求**。一个能填任意地址的「拉取」按钮，等价于给攻击者一个「让内网服务器替我发请求」的原语：

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/   云元数据（拿临时凭据）
http://127.0.0.1:3306/                                               用响应时间探测内网端口
http://10.0.0.5:8080/admin                                           带着服务器的网络身份访问内网管理面
```

SSRF 的价值恰恰来自这种**不对称**：攻击者用自己的机器连不上 `10.0.0.5`，但让这台服务器去连就能连上，而且带着服务器的网络身份与信任关系。

### 6.2 第一层：`CheckEndpoint` —— 校验**解析后的 IP**，不是字符串

```go
addrs := resolveHost(ctx, host)        // 字面量 IP 与域名走同一条路径
for _, a := range addrs { if isBlockedAddr(a) { return blocked } }
```

**为什么必须按解析结果判。** 同一台主机有无数种写法：

| 写法 | 等价于 |
|---|---|
| `127.0.0.1` | 点分十进制 |
| `0x7f.1` / `0x7f000001` | 混合进制 / 十六进制整数 |
| `2130706433` | 十进制整数 |
| `[::ffff:127.0.0.1]` | IPv4-mapped IPv6 |
| `127.1` | 省略段 |

任何基于字符串匹配的黑名单都能被绕过，而基于**解析结果**的判定只需要覆盖一次网段列表。这五条写法在守门脚本第 4 节的 20 条矩阵里逐条重放。

**必须解析出全部地址，不能只取第一个。** 一个域名可以同时解析出公网 A 记录与内网 AAAA 记录，后者会被连接时选中 —— 「只检查第一个」的实现在这里失守。

**`isBlockedAddr` 先 `Unmap()` 再判。** `::ffff:127.0.0.1` 是合法的、能连到本机回环的 IPv6 写法；不还原成 IPv4 就不会命中任何 IPv4 段，会被当成「一个普通的公网 IPv6」放过去。

禁止出站的网段清单（`blockedPrefixes`，22 条）判据不是「看起来危险」，而是「**这台服务器能访问而外部用户访问不到的**」：

- IPv4（15 段）：`0.0.0.0/8`、`10/8`、`100.64/10`（CGNAT）、`127/8`、`169.254/16`（含云元数据）、`172.16/12`、`192.0.0/24`、`192.0.2/24`、`192.88.99/24`、`192.168/16`、`198.18/15`、`198.51.100/24`、`203.0.113/24`、`224/4`、`240/4`
- IPv6（7 段）：`::/128`、`::1/128`、`fc00::/7`（ULA）、`fe80::/10`、`ff00::/8`、`64:ff9b::/96`（NAT64）、`2002::/16`（6to4）

> **只在 IPv4 上做过滤是最常见的漏法。** `http://[::1]:8080/` 与 `http://[fd00::1]/` 都能直达内网，而很多实现只看 `net.ParseIP().To4()`，对纯 IPv6 返回 `nil` 就当「不是内网」放过去了。NAT64 与 6to4 单列是因为它们能把 IPv4 内网地址**嵌在 IPv6 里**。

`CheckEndpoint` 另有三条与「内网」无关但同属出站面收紧的规则：

- 只允许 `http` / `https`（拦掉 `file://` `gopher://` `dict://` —— 它们绕开 HTTP 语义却能读本地文件或与任意 TCP 服务对话）；
- 拒绝 URL 内嵌凭据（`http://user:pass@host/` 会把凭据写进 URL，而 URL 会出现在错误信息与访问日志里）；
- 空串是**合法**输入（`local` 这类适配器不需要地址），由调用方判断「该类型是否要求非空」。

### 6.3 第二层：`net.Dialer.Control` —— 在 `connect(2)` 之前复核

第一层与真正 `connect` 之间存在时间差，攻击者可以让 DNS 在这之间返回不同答案（**DNS rebinding / TOCTOU**）：先返回公网地址通过检查，再返回 `127.0.0.1` 完成连接。

`Control` 回调拿到的是**真正要连的那个 `sockaddr`**，不受 DNS 影响。

⚠️ **两层各由谁覆盖，不能混为一谈**（P7 收口时改正了一处标错的断言）：

| 场景 | 拦住它的是 | 覆盖处 |
|---|---|---|
| 保存时填了内网地址 | 第一层 | 守门脚本 §4（20 条矩阵） |
| 有人**直接改库**把地址换成内网 | 第一层（拉取路径上重跑一次） | 守门脚本 §6 ⑧ |
| 预检通过后 DNS 变脸（rebinding / TOCTOU） | **第二层** | `pkg/intelfeed` 单测 `TestGuardedClientBlocksAtDialTime` |

守门脚本 §6 ⑧ 原本的标签是「第二层防护」，**那是错的** —— 那条路径上地址本来就在内网，
第一层就先拒了，根本走不到 `connect`。标错的代价不是「红变绿」，而是**第二层从此没人再测**，
而它恰恰是「预检通过之后 DNS 变脸」的唯一防线。真正的第二层改由单测覆盖：
直接让客户端去连一个受限字面量地址（`CheckEndpoint` 不在这条路径上），
断言拒绝来自 `Control` 而**不是**「端口没人监听」的 `connection refused`。

> 这条单测做过负向验证：把 `Control` 的函数体改成 `return nil` 之后，
> 它立刻失败并打出 `dial tcp 127.0.0.1:9: connect: connection refused` ——
> 这正是「只断言报错」会漏掉的那种失败。

两层用不同的哨兵错误区分：第一层被拒是「用户配错了地址」（400 引导他改），第二层被拒是「DNS 在两次解析之间变了」（可疑行为，要记日志）。

### 6.4 三个配套约束

| 约束 | 不这么做会怎样 |
|---|---|
| **禁跟随重定向**（`http.ErrUseLastResponse`） | 一个位于公网的善意地址可以 302 到 `http://169.254.169.254/`，跟随重定向等于把第一层的全部判定作废 |
| **`Proxy: nil`** | `HTTP_PROXY` 环境变量会让请求经由代理发出，而代理侧的解析与连接完全在我们看不到的地方发生。置零而不是依赖「没设这个变量」—— 部署环境的变量不由我们决定 |
| **`DisableKeepAlives: true`** | 上游不可能复用同一条连接（每次都是独立请求）；关掉连接池也就关掉了「池里那条连接当时连的是谁」这类隐性状态 |

### 6.5 资源上限写成常量，不写成配置项

| 常量 | 值 | 理由 |
|---|---|---|
| `MaxBodyBytes` | 2 MiB | 用 `io.LimitReader` 截断，**不信任 `Content-Length`**：上游可以不给这个头，也可以给一个远小于实际流的假值 |
| `MinTimeout` / `MaxTimeout` | 1s / 30s | 上限与 `server.write_timeout` 是同一条理由：一个配置成 10 分钟的超时会把一个 HTTP 请求连同它的数据库连接一起占住十分钟，而用户早已离开 |
| `DefaultTimeout` | 10s | 配置里没写时的取值 |

它们是**安全上限**，不是「部署时可调的参数」。放成配置项意味着一次误配就能把「响应体上限 2 MB」改成 2 GB，而失败模式是进程 OOM。

### 6.6 正例对照 —— 只断言「内网被拒」的守门是假绿的

若有人把校验误改成「一律拒绝」，只断言拒绝的脚本会**全绿**，而那会让整个功能不可用。因此第 4 节的矩阵里每条拒绝断言旁边都有正例：`https://1.1.1.1` 必须 **201**，并且真的把这条配置读回来比对。

同一条纪律也适用于 `DefaultBaseURL`：**默认值不会被当作「可信地址」跳过校验**。把它当白名单是一个典型的降级路径 —— 用户只要把地址改回默认值再配一个同名 hosts 记录就能绕过。

## 7. 凭据处理

完整流程（`resolveCredential`）：

1. `credential_env` 为空串 → 无凭据，直接返回空（**不报错**：`local` 这类源本来就不需要）；
2. 非空 → `os.LookupEnv`；查不到或为空 → `errIntegrationCredentialMissing`，文案点名那个变量，并说明「变量的**值**不会、也不应写进系统里」；
3. 取到的明文只沿 `intelfeed.Request.Credential` 传递，适配器**不读环境变量**（读环境变量是 service 层的动作，那里才做前缀白名单判定）。这样适配器可以被纯 Go 测试直接驱动，无须污染进程环境。

**出口兜底**：`sanitizeFailureMessage` 在错误信息离开服务层之前把凭据明文替换成 `***`。

> **为什么仍要有前缀白名单。** 兜底是「写了再擦」；前缀白名单是「根本不写进去」。两者的可靠性不在一个量级，而且白名单顺带把「读取任意环境变量」这个原语整个关掉了。

守门脚本用**已知的凭据值**做反向断言（`srv` 进程以 `SR_INTEL_E2E_KEY=<好认的串>` 启动），逐处检查这个串**不得出现**在：① 拉取响应体、② 集成列表响应、③ 拉取审计明细、④ 整张 `audit_logs` 表、⑤ 整张 `integrations` 表。同时正向断言审计与列表里**如实给出了变量名**。

> 没有这样一个已知值，「不含凭据」这条断言就只能写成「不含 `password` 字样」—— 而那与真的没泄漏是两回事。

## 8. 适配器与 `local` 离线驱动

### 8.1 接口只有两个方法

```go
type Feed interface {
	Type() string
	Fetch(ctx context.Context, req Request) (*Record, error)
}
```

批量、缓存、落库、限流全部不在适配器职责内 —— 它们要么属于 service 层（批量编排），要么属于「P7 明确不做」的范畴（定时同步）。

`Request.Credential` 是**已解析好的凭据明文**；`Record` 与 `model.VulnIntel` 字段一一对应但**不引用它** —— `pkg/intelfeed` 不依赖领域模型，它只回答「上游说了什么」，「这句话在我们的库里怎么存」是 service 层的事。

### 8.2 注册表：新增一个源 = 一个文件 + 一行注册

```go
var registry = map[string]func() Feed{
	TypeNVD:   func() Feed { return nvdFeed{} },
	TypeLocal: func() Feed { return localFeed{} },
}
```

用包级 map 而不是 `switch`：「哪些源受支持」这件事**只在这一个地方回答**。`Supported()` 返回的顺序即界面下拉框顺序。

`TypeNVD` / `TypeLocal` 与 `Severity*` 是本包导出的常量，数据库列与契约枚举都指向它们，**不存在第二份字面量**。因此 `model` 里只声明「这个字段是字符串」，不再重复一份取值列表 —— 两份定义的分叉不会报错，只会在某次比较里静默不相等。

### 8.3 错误语义：`ErrNotFound` 必须与「网络失败」分开

| 错误 | 含义 | 用户的下一步 |
|---|---|---|
| `ErrNotFound` | 上游**明确回答**「没有这条 CVE」 | 编号可能拼错了；再点一百次也是同一个答案 |
| `ErrEndpointBlocked` | 出站目标被拒 | 改配置 |
| 其它 | 网络 / 上游故障 | 重试 |

合成一个「拉取失败」会让用户对着一个再也不会变的答案反复点。

### 8.4 `local` 离线驱动为什么不是「测试脚手架」

它存在的理由不是「测试方便」，而是让**验收标志与外部可达性解耦**：

守门脚本必须能在没有外网、没有 API Key 的环境里跑出全绿，否则 CI 一断网守门就失效 —— 而**失效的守门比没有守门更糟，因为它会让人相信「系统是好的」**。

因此验收标志（「配置后能拉取一条 CVE 信息」）由 `local` 驱动证明，走的是**同一条** service 编排、同一张表、同一套审计、同一套运行态回写，只有「取数」这一步不落网。验收标志要断的是「配置 → 拉取 → 落库 → 可读」这条链路，不是公网本身。

公网路径的正确性由两处各自负责，都不需要真连外网：

- `pkg/intelfeed` 单测覆盖 NVD 响应解析与全部错误分支；
- 守门脚本第 4 / 6 节覆盖「地址不被允许」。

守门脚本另有一条**真连公网的正例对照**（`https://1.1.1.1` 必须 201）：它断的是「公网地址不会被误判成内网」，不依赖任何业务响应。`services.nvd.nist.gov` 那一条允许「201」或「400 且原因为解析到非公网段」两种情况，并把这句说明写进了断言，因为它取决于跑脚本那台机器的 DNS。

## 9. 审计

| 动作码 | 覆盖 | 明细字段 |
|---|---|---|
| `integration.update` | 建与改**共用** | `name` / `type` / `base_url` / `credential_env`（**变量名**）/ `enabled` |
| `integration.fetch` | 每一次拉取（含全部失败） | `integration_id` / `integration_name` / `base_url` / `type` / `vuln_id` / `cve_ids` / `succeeded` / `failed` / `latency_ms` |

两条设计取舍：

1. **建与改共用一个动作码。** 它们改的是同一组字段、同一个对象，且审计记录了变更后的完整配置快照（不是 diff）。分开会让「改配置」这件事在审计页里分成两个动作，而用户的心智里只有一件事。
2. **明细里记 `base_url`。** 它回答的是「服务器**实际**去向哪里发起了请求」—— 只在配置页看当前值是不够的，因为配置可以被改。这也是 D8 拒绝删除接口的原因。

**失败的拉取也写审计**：拉取失败往往是排障的起点，而这正是最需要「当时到底发了什么请求」的时刻。

**被拒的请求不留审计**：400 / 404 / 409 由中间件层承担，不进 service 的审计路径。守门脚本对此有正反两条断言（失败的拉取有记录 / 被拒的拉取没有记录），并要求后端日志里**既不出现**「写操作未留审计」的告警**也不出现**「审计日志写入失败」。

`service.FetchIntel` 成功路径走 `reqctx.MarkAuditRecorded(c)` 声明已自行落库，因此中间件不会再记一条重复的 —— 守门脚本按 `(request_id, action)` 唯一性断言没有重复记录。

## 10. 前端

### 10.1 集成配置页 `/system/integrations`

| 项 | 值 |
|---|---|
| 路由 name | `system-integrations` |
| 菜单元 | 系统管理 / `menuOrder: 24` / 图标 `Connection` |
| 权限 | **`integration:read`**（不是 `system:read`） |

⚠️ 权限刻意挂 `integration:read`：评估员与整改员要能进这一页看「这条情报来自哪个源」，而配置的**改动**按钮由页面内的 `auth.can('system:write')` 控制显示。菜单是路由表的投影，页面内按钮是第二层区分 —— 两者都不能替代后端的权限闸门。

页面要点：

- 类型下拉由后端下发的 `supported_types` 渲染（`label` / `default_base_url` / `credential_recommended` 都来自后端）。**前端不硬编码类型列表**：新增适配器时下拉框自动多出一项，而硬编码的界面里根本选不到它。表单的 `type` 字段刻意是 `string` 而非契约联合类型，提交前用 `resolveType(raw)` 对照后端下发的列表收敛。
- 切换类型时预填默认地址：只在「字段空着」或「还等于上一个类型的默认值」时才覆盖 —— 用户手填过的地址不会被悄悄改掉。
- 凭据输入是**三态**：不改（`undefined`）/ 清空（`null`）/ 设新值（字符串）。
- 「记录更新时间」列带 tooltip 说明它含运行态写入（§3.1 第三条约束），否则用户会问「我没改配置，时间怎么变了」。
- 页面内两条 `el-alert` 提醒「凭据永不入库」与「拉取入口在漏洞详情」，页脚写明**本页没有删除**及原因。

### 10.2 漏洞详情里的情报区

配置页只回答「配了什么」，拉取入口放在**用得上它的地方** —— 漏洞详情抽屉。

- 情报快照表格：来源 / CVE 编号 / **`display_title`**（不是 `title`）/ 严重度 / CVSS / 抓取时间；展开行给出 CVSS 向量、上游发布时间、描述、参考链接（`target="_blank" rel="noopener noreferrer"`）。
- 「拉取情报」对话框只在 `auth.can('integration:write')` 时出现；情报源下拉只列 `enabled` 的集成；CVE 下拉的选项来自该漏洞的 `cve_ids`。
- 结果处理按 D6：读 `res.failed` 判成败，成功后重新加载详情与列表；`catch` 分支**只对应 400 出站被拒**这一种失败。

> 复用点：漏洞详情接口本身就内嵌 `intel`（`docs/openapi.yaml` 的 `VulnerabilityDetail`），因此列表页不需要为情报多发一次请求。`get_vulnerability` 这个 MCP 工具也直接拿到它。

## 11. MCP Server

### 11.1 定位：薄客户端，不是第二套后端

`mcp/` 是一个 Node 进程，用 stdio 讲 MCP，所有数据来自主服务的 REST 接口，用一个**真实的**服务账号走登录流程（`/api/auth/csrf` → `/api/auth/login`）。

因此认证、授权、审计三件事完全复用既有实现 —— **MCP 不是一条绕过权限的后门**：越权会拿到后端真实的 403，并被记进审计日志（责任人就是配置里的服务账号）。

这同时决定了它的能力边界：**MCP 能做的事严格等于那个账号能做的事**。想限制模型只能读不能写，正解是把服务账号配成 `auditor` 这样的只读角色，而**不是**在这里加判断 —— 这里的判断改一行就失效，而后端的 RBAC 不会。

### 11.2 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `SR_MCP_API_BASE` | `http://127.0.0.1:8080` | 后端基址。只允许 http/https，末尾斜杠会被归一化掉 |
| `SR_MCP_USERNAME` | 必填 | 服务账号登录名 |
| `SR_MCP_PASSWORD` | 必填 | 服务账号密码 |
| `SR_MCP_ALLOW_WRITE` | **关** | 只有 `true` / `1` / `yes` / `on`（忽略大小写）才开启写工具 |
| `SR_MCP_TIMEOUT_MS` | `15000` | 收敛到 `[1000, 60000]` |

**没有任何配置文件**：MCP 客户端都是用 `env` 字段传值的，多一份配置文件就多一处「界面里配了不生效」的来源。

**校验在进程启动时做，失败即非零退出**：一个连不上后端的 MCP Server 表现为「每个工具都报错」，而那看起来像工具本身有问题。宁可起不来，也不要起一个只会报错的壳。

> ⚠️ 退出用 `process.exitCode = 1` 而**不是** `process.exit()`：后者会**截断尚未落盘的 stderr**，于是「快速失败」只剩下一半 —— 进程确实挂了，但运维看不到原因。这个坑是守门脚本抓出来的（见 `docs/01` §17.3）。

### 11.3 工具集合（8 只读 + 1 写）

**默认暴露的 8 个只读工具**（`annotations` 全为 `readOnlyHint: true` / `destructiveHint: false` / `idempotentHint: true` / `openWorldHint: false`）：

| 工具 | 对应接口 | 需要的权限码 |
|---|---|---|
| `get_dashboard_summary` | `GET /api/dashboard/summary` | 任一（见 `docs/13` §8.1） |
| `list_assets` | `GET /api/assets` | `asset:read` |
| `list_vulnerabilities` | `GET /api/vulnerabilities` | `vulnerability:read` |
| `get_vulnerability` | `GET /api/vulnerabilities/{id}`（含 `intel`） | `vulnerability:read` |
| `list_assessments` | `GET /api/assessments` | `assessment:read` |
| `list_risk_items` | `GET /api/assessments/{id}/risk-items` | `assessment:read` |
| `list_remediations` | `GET /api/remediations` | `remediation:read` |
| `list_integrations` | `GET /api/integrations` | `integration:read` |

**写工具 `fetch_vuln_intel`**（`readOnlyHint: false` / `destructiveHint: false` / `idempotentHint: true` / **`openWorldHint: true`**）：入参 `integration_id` / `vuln_id` / `cve_id?`。

它是 P7 验收标志的**无界面入口** —— 没有它，自动化流程要验证「配置是否真的能拉通」就只能开浏览器。描述里写明了三件事：会**真的**向外发请求、接口恒定 200 成败要看结果字段、它是幂等的。

### 11.4 三条工具设计立场

1. **工具是接口的投影，不是新的接口。** 入参直接对应后端已发布的查询参数，不加工、不聚合、不重命名。加一层「方便模型调用」的转换层等于造出第二份契约：后端改了参数名，工具照旧收旧参数，表现为「某个筛选条件永远不生效」。
2. **默认只读。** 唯一的写工具必须由部署方显式开启。理由：同一个能力经网页触发时，点按钮的是人；经 MCP 触发时，决定是否调用的是模型 —— 而模型看不见「这个动作会真的发出站请求」。
3. **不做权限判断。** 工具描述里写清「需要哪个权限码」是给人和模型看的**说明**，不是拦截。

### 11.5 会话与 CSRF

`client.js` 里有一个极简 `CookieJar` 与单飞（in-flight）登录：

- `sr_at` / `sr_rt` / `sr_csrf` 三个 Cookie 全部按 `Set-Cookie` 原样吸收；
- 发请求时**按 `Path` 前缀过滤 `sr_rt`** —— 刷新令牌的 Cookie 只对 `/api/auth/` 有效（`docs/03`），把 `Path` 忽略掉的实现**功能上照样能跑**，因此这类错误不会被测出来，只能靠实现时写对；
- 401 且错误码命中 `REAUTH_CODES` 时，先 refresh、失败再重新登录，然后**只重试一次**；
- `AbortSignal.timeout` + `redirect: 'error'`（不跟随重定向）。

**异常转成工具结果而不是抛出**：抛出的异常在 MCP 里表现为「服务器出错」，模型拿不到原因只能重试；而业务失败（403 / 404 / 参数不合法）是模型能理解并据此改变策略的信息，必须原样交到它手上。

## 12. 守门脚本覆盖（`scripts/verify-integration.sh`）

**256 项断言 / 0 失败，实测约 2 分 53 秒**（2026-10-12）。隔离库 `sec_risk_integration_e2e` + 端口 18088，**不依赖 docgen 与 gotenberg**（P7 不渲染任何文件）。

| 节 | 内容 | 关键设计 |
|---|---|---|
| 0 | 环境准备 | 临时建库、`DROP DATABASE` 兜底、端口清理 |
| 1 | 启动后端 + 迁移台账 | 以 `SR_INTEL_E2E_KEY=<已知串>` 启动（凭据反向断言的来源）；查 `schema_migrations` version=8、两表存在、FK 为 CASCADE |
| 2 | 权限面 | 三档角色逐个验证；**用「404 而不是 403」证明闸门通过** |
| 3 | 配置 CRUD 与校验 | 唯一名 409、未知类型 400、凭据前缀与字符合法性、`credential_env: null` 清空、空 PATCH、**改类型时整体校验**、超时收敛、停用、DELETE 404、列表不分页（条数与库里行数对齐） |
| 4 | **SSRF 矩阵 20 条 + 公网正例** | 逐条走真实 `POST /api/integrations`（证明校验**真的挂在保存路径上**，而不只是单测里的 `CheckEndpoint` 实现）；**被拒的一条都没落库**；正例 201 且读回比对 |
| 5 | **验收标志** | `local` 驱动拉 `CVE-2021-44228`，逐字段核对 + 落库交叉核对 + 详情内嵌 + 幂等 + 多 CVE 批量 + 指定小写 `cve_id` + 评估员拉取 |
| 6 | 十二条拒绝路径 | 含「有人直接改库把地址换掉」后的复核、适配器已移除、凭据缺失（并证明**不出网**）。⚠️ **第二层防护不在这里**，由 `pkg/intelfeed` 单测覆盖，见 §6.3 |
| 7 | 运行态回写 | 先自己跑一次全成功再断言 `success`（运行态记的是**最后一次**，不是历史累计）；部分失败记 `failed`；`updated_at` 被拉取刷新但配置列不变 |
| 8 | 情报与漏洞 | 唯一键三列有序（查 `information_schema`）、`source` 存类型而非集成 id、CASCADE 删除、空情报返回 `[]` 而非 `null` |
| 9 | 审计 | 两个动作码、明细字段齐、**凭据值不出现**在五处、失败请求不留痕、无重复审计、无告警 |
| 10 | MCP | 真跑 `mcp-smoke.mjs` 并**逐节核对日志内容**（不只信退出码 —— 一个什么都没测的空脚本同样返回 0）；错误凭据反向对照必须非 0；MCP 触发的调用留下审计；后端日志无 ERROR |

### 12.1 脚本自身的三处「假绿」防线

1. **反向断言必须有已知值。** 见 §7。没有 `SR_INTEL_E2E_KEY` 这个好认的串，「不含凭据」就只能断言「不含 `password` 字样」。
2. **断言数量要与库里的事实对齐，不能写死魔法数字。** 第 3 节的「列表不分页」原本写死「条数 ≥ 5」，而那一节实际只建了 4 个集成 → **红在了一个与「分不分页」毫无关系的原因上**。已改为「条数 == 库里行数 且 > 1」：一条会因无关改动变红的断言，作用只是训练人忽略红色。
3. **断言的标签必须与它真的测到的东西一致。** §6 ⑧ 原本标成「第二层防护」，实际测的是第一层在拉取路径上的第二次调用。**标错的代价不是「红变绿」，而是被标错的那一层从此没人再测。** 改正的同时给第二层补了单测与负向验证（§6.3）。

## 13. 已知边界与后续

**P7 交付的是骨架，以下是明确留给后续的：**

| 项 | 现状 | 接入方式 |
|---|---|---|
| 第二个真实情报源 | 只有 `nvd`（真实）+ `local`（离线） | 加一个文件实现 `Feed` + 注册表一行；`Supported()` 顺序即下拉框顺序 |
| 定时同步 / 订阅 | 无 | 前提是先解决「任务停了库里的情报会静默变旧」—— 届时需要一个可见的陈旧度指标 |
| 拉取历史 | 只有审计 | 审计页按 `action=integration.fetch` 过滤 |
| 情报参与打分 | 不参与 | 若要做，必须先回答「同一次评估是否可复现」 |
| MCP 生产部署 | 只有 `make mcp-smoke` 与守门脚本第 10 节 | 客户端配置方式见 §11.2；账号角色决定能力边界 |

**两处刻意留下的「不优雅」**：

1. `integrations.updated_at` 混着配置时间与运行态时间。拆表可以消除它，但 P7 不做拉取历史，为一行运行态去 JOIN 不划算 —— 代价写进了 §3.1 与界面 tooltip。
2. `local` 适配器带着一份内置数据在源码里。它不影响任何生产路径（生产不会配 `local`），但它是「验收标志与外部可达性解耦」的实现手段，删掉它等于把守门脚本重新绑回公网可达性。

## 1. 资产字段：标准字段 + 三态更新

### 1.1 为什么是这 14 个字段

资产表的对外字段（不含 `id` 与时间戳）：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `name` | string | 必填，≤128 字 | 显示名称 |
| `asset_no` | string? | **可空**，全局唯一，≤64 字 | 业务编号，字符集 `[A-Za-z0-9_./-]`，须以字母或数字开头 |
| `asset_type` | string | 必填，存字典 `code` | 见 §3 |
| `group_id` | uint64? | 可空，外键 | 见 §2 |
| `ip_address` | string | ≤64 字 | 接受 IPv4 / IPv6 / CIDR / 主机名 |
| `port` | uint16? | 可空 | 见 §1.4 |
| `hostname` / `os_type` | string | ≤128 / ≤64 字 | 自由文本 |
| `importance` | uint8 | 1–5，缺省 3 | 对应风险模型的资产价值 A |
| `owner` / `department` | string | ≤64 字 | 责任归属 |
| `status` | enum | 四值，缺省 `in_use` | `in_use` / `idle` / `offline` / `scrapped` |
| `tags` | string | ≤255 字 | 见 §1.5 |
| `description` | string | ≤512 字 | 自由文本 |

两条刻意的取舍：

- **`importance` 缺省是中档 3，不是最低档 1。** 不填就等于 1 会让资产被系统性
  低估——而风险值 `R = f(A, T, V)`，A 被低估会一路传导到评估结论。
  「未填写」应当表达为「我不知道」，而不是「它不重要」。
- **`status` 用字符串而不是整数枚举。** 运维直接看库就能读懂，而整数枚举
  需要一份对照表，那份对照表迟早会和代码漂移。（与 `users.status` 一致。）

### 1.2 `PATCH` 的三态语义

`PATCH /api/assets/{id}` 的请求体里，「字段不存在」「字段是 `null`」
「字段有值」是三件不同的事：

| JSON | 语义 | 实现 |
|---|---|---|
| 键不存在 | **不修改** | `optional.Value[T]{Set: false}` |
| `"port": null` | **清空** | `{Set: true, Value: nil}` |
| `"port": 443` | **设值** | `{Set: true, Value: &443}` |

为什么需要它：`PATCH` 的常见语义就是「只改我提到的字段」。如果「不传」与
「传 null」不可区分，前端就无法表达「把备注清空」——只能传空串，而空串与
`NULL` 在数据库里是两个不同的值，于是「清空备注」和「备注是一个空串」
会混成一件事。

**踩过的坑（GORM）**：用 `struct` 做 `Updates` 时 GORM 会跳过零值字段，
`""` / `0` / `false` 全都改不动。所以仓储层的 `Update` 一律用 `map[string]any`
（`repository/asset.go`）。用 struct 的症状是「保存成功了，但那个字段没变」，
而且只在想把它改成零值时才出现——非常难联想到 ORM。

> 前端的对应写法：`AssetListView.vue` 的 `handleSubmit` 里 `group_id` /
> `port` 显式传 `null`，而其它未填字段**不放进 payload**。把 `undefined`
> 和 `null` 搞混会让「编辑资产时顺手把备注清空」。

### 1.3 `asset_no` 可空 + 单列唯一索引

数据库上是 `asset_no VARCHAR(64) NULL` + `UNIQUE KEY uk_assets_asset_no`。

- **可空**，因为很多资产在录入时还没有正式编号。MySQL 的唯一索引把多个
  `NULL` 视为**互不相同**，所以「未编号」的资产可以有很多条。
- 如果改用空串当「未编号」，第二条未编号资产就会撞唯一索引——这是同一类
  陷阱的另一种形态（与 `users.email`、`asset_groups.parent_id` 一致）。
- 非空时**全局唯一**，冲突报 409 `ASSET_NO_TAKEN`。

守门脚本实测：连续创建两条不传 `asset_no` 的资产都成功；
回读时 `asset_no` 是空串（`model.Asset.AssetNoValue()` 负责这个转换）。

### 1.4 端口的「未填写」用 NULL，不用 0

`port` 是 `*uint16`。0 不是合法端口，所以它**不能**当哨兵值——否则
「未填写」和「填了 0」不可区分，而后者会在导出/报表里显示成
`host:0`。

对外 JSON 上，`port` 缺失时返回 `0`（`Asset.PortValue()`），因为这个 0
只用于展示层（前端显示「—」）。**注释里明确写了它不能回写数据库**：
前端 `openEdit` 把 `port === 0` 换回 `null`，就是这条约定的落点。

### 1.5 标签存逗号分隔串，不建关联表

`tags VARCHAR(255)`，存 `"核心,生产"`。

理由：标签目前只用于筛选与展示，**没有任何按标签聚合的查询**。为此建
一张 `asset_tags` 关联表要付出连接开销、多一张表的迁移维护，换来的
「规范化」在当下没有消费者。

代价要说清楚：**无法用索引高效做「包含某标签」的查询**，也没有标签
去重表（同一个标签的多种写法会共存）。当出现「按标签统计资产分布」
这类需求时，这里必须改成关联表——那是一次有明确触发条件的重构，
而不是一个模糊的 TODO。

标签的解析收得很宽：`,` `，` `;` `；` `、` 都当分隔符。用户从别处
粘贴过来的标签什么分隔符都可能带，只认一种只会让他看到「标签不合法」
却看不出原因。校验上限是 10 个、单个 ≤32 字、且不含逗号。

## 2. 资产分组：物化路径

### 2.1 为什么不是邻接表递归，也不是闭包表

| 方案 | 子树查询 | 移动子树 | 结论 |
|---|---|---|---|
| 邻接表 + 递归 CTE | 每次递归，MySQL 8 支持但写法重 | 改一行 | ✅ 可读，但子树查询是高频操作 |
| **物化路径** | `WHERE path LIKE '/1/4/%'` 一次索引扫描 | 一条 UPDATE 重写整棵子树 | ✅ **采用** |
| 闭包表 | 一次 join | 插 N 行 | 多一张表 + 多一倍写放大 |

资产列表的默认行为就是「按分组筛选**含子树**」（§2.6），子树查询是
热度最高的那条路径，值得为它优化；而移动分组是低频管理操作，
一次重写整棵子树完全可以接受。

`AssetGroup` 里同时保留了 `parent_id`（邻接表）——**物化路径不是替代它，
而是它的索引**。`parent_id` 负责「谁是直接父节点」（构建树、面包屑、
成环判断），`path` 负责「整棵子树是谁」。

### 2.2 路径形态

`path` 存**完整祖先链**，带首尾斜杠、**包含自身**：

```
根组「总部」          →  /1/
  子组「华东区」      →  /1/4/
    子组「机房A」     →  /1/4/9/
```

- 末尾斜杠的作用：让 `/1/4/` 不会命中 `/1/41/`。少了它，`LIKE '/1/4%'`
  会把 ID 为 41 的兄弟节点一起捞进来。
- 前缀用 `LIKE <path>%` 时，`%` 能匹配空串，所以**组自身也在结果里**。
  这一点是「含子树」语义需要的，不是巧合。
- `depth` 是 0 基的（根组 0、第二层 1），与「几层」的日常说法差 1。
  上限 `MaxAssetGroupDepth = 8`，即最多 8 层。

### 2.3 ⚠️ 一个真实踩过的坑：用 ID 拼前缀

**症状（两个，都不会指向物化路径）：**

1. 「按分组筛选」对任何**非根组**静默返回 0 条。
2. 「删除仍有资产的组」不返回可读的 409，而是一路走到数据库外键上
   失败 → 500 `INTERNAL_ERROR`。

**根因：** 子树查询的前缀从前是拿 ID 拼出来的：

```go
// 曾经的写法（已删除）
prefix := escapeLike("/" + strconv.FormatUint(id, 10) + "/") + "%"
```

`path` 里存的是**完整祖先链**。对一个路径为 `/1/4/` 的子组，`id = 4`，
拼出来的前缀是 `/4/%` —— 而库里没有任何一行以 `/4/` 开头，于是
**匹配 0 行**。只有根组（`/1/` 与 `id = 1` 恰好同形）能工作，
所以在根组上测试是通的。

**为什么排查成本极高：** 它不报错、不 panic，只是安静地返回空集。症状
「筛选返回 0 条」看起来像前端筛选条件没传对；症状「删不掉还 500」看起来
像外键约束或事务问题。两条线索都不指向「物化路径」。

**修法：** 改签名为 `SubtreeIDsByPath(ctx, groupPath string)`，**强制调用方
传该组自己的物化路径**，把 ID 拼前缀这条路从类型上堵死：

```go
func (r *AssetGroupRepository) SubtreeIDsByPath(
    ctx context.Context, groupPath string,
) ([]uint64, error) {
    if groupPath == "" {
        return []uint64{}, nil
    }
    var ids []uint64
    err := r.db.WithContext(ctx).Model(&model.AssetGroup{}).
        Where("path LIKE ?", escapeLike(groupPath)+"%").
        Order("id ASC").Pluck("id", &ids).Error
    ...
}
```

两处调用点改为传 `current.Path`（`Delete` 与 `ResolveGroupFilter` 都先
`FindByID` 拿到了 `current`）。`MoveSubtree` / `MaxDepthInSubtree` 本来
就收路径，无需改动。

**教训（值得单独记下来）：** 「一个 ID 恰好等于它在路径里的片段」这种
巧合，会让测试在根节点上通过、在深层节点上失败。凡是拿主键去拼
结构位置的地方，都该先问一句「这个等式在所有层级都成立吗」。

### 2.4 同层重名：生成列 `parent_key`

约束是「同一个父组下不允许同名」，数据库上落在唯一索引
`uk_asset_groups_parent_name (parent_key, name)`。

问题在于根组的 `parent_id` 是 `NULL`，而 MySQL 的唯一索引把多个 `NULL`
视为互不相同——**直接对 `parent_id` 建索引拦不住根组重名**。

解法是一个生成列：

```sql
parent_key BIGINT UNSIGNED GENERATED ALWAYS AS (IFNULL(parent_id, 0)) STORED
```

`NULL → 0`，于是根组之间也会互相冲突。选 `STORED` 而不是 `VIRTUAL`：
唯一索引需要物化。

注意**不存在的 ID 0** 被当成「根的父节点」这个哨兵值。它的合法性来自
「自增主键不从 0 开始」，不需要额外约束。

服务层在插入前还会查一次 `ExistsNameUnderParent`，为的是给出 409
`ASSET_GROUP_NAME_TAKEN` 这个可读错误，而不是把唯一索引的报错透出去。
两者是「友好提示 + 数据库兜底」的关系，不是重复。

### 2.5 移动子树是一条 UPDATE

`POST /api/asset-groups/{id}/move` 是**独立端点**，不是 `PATCH` 里的一个
字段。理由很实际：`PATCH` 里 `parent_id` 缺失与 `parent_id: null`
在 JSON 上要靠三态去区分，而「移到根」与「不移动」正是这两种形态——
独立端点让语义没有歧义。

移动的实现是一条语句，不做递归：

```sql
UPDATE asset_groups
SET path  = CONCAT(?, SUBSTRING(path, CHAR_LENGTH(?) + 1)),
    depth = depth + ?
WHERE path LIKE ?
```

以「`/1/4/` 搬到 `/1/7/4/`」为例：

- `/1/4/9/` 去掉旧前缀 `/1/4/` 之后的剩余部分是 `9/`，新路径即 `/1/7/4/9/`；
- 组自身的 `/1/4/` 剩余部分是空串，新路径即 `/1/7/4/`。

**自身与后代被同一条语句处理掉，不需要特殊分支。** 层级差是常数，
所以 `depth` 用一次加法即可。

三道前置检查：

1. **成环**：目标父节点在当前子树的路径前缀之内 → 400 `ASSET_GROUP_CYCLE`。
   移到自身同样命中这一条。
2. **层级上限**：目标深度 + 子树的最大相对深度 > 8 → 400
   `ASSET_GROUP_DEPTH_EXCEEDED`。用 `MaxDepthInSubtree` 取一个
   `MAX(depth)` 就够了——合法性只取决于这一个数。
3. **事务**：检查与重写必须在同一个事务里，否则并发移动会让检查失效。

### 2.6 「含子树」筛选在后端

`GET /api/assets?group_id=4` 默认返回**该组及其所有后代**的资产，加
`include_children=false` 才只返回直挂的。

这一点**必须**在后端实现：前端拿不到完整的父子关系（树可以懒加载），
而且「选中华东区想看到下面所有机房」是用户的默认预期。

`ResolveGroupFilter` 会先 `FindByID` 确认组存在。**不确认的话，一个不存在
的 `group_id` 会静默返回空列表**，用户看到「没有数据」会去怀疑筛选条件，
而真正的问题是组不存在。守门脚本对这条有专门断言。

删除分组的两道拦截，**顺序不能反**：先看子组（`ASSET_GROUP_HAS_CHILDREN`），
再看资产（`ASSET_GROUP_HAS_ASSETS`）。反过来的话，一个既有子组又有资产的
组会报「里面还有资产」，用户把资产移走后仍然删不掉——多一轮无效往返。

## 3. 字典：存「码」而不是主键 ID

### 3.1 四类字典共用一张表

`dictionaries` 表用 `category` 区分四类：`asset_type` / `threat` /
`vulnerability` / `measure`。

四类除 `weight` 的语义外，结构与增删改查行为完全一致，合成一张表让
「字典维护」页只需要一套 CRUD。**代价是 `weight` 一列承载四种语义**：

| category | weight 语义 |
|---|---|
| `asset_type` | **不参与风险计算**，恒为 1 |
| `threat` | 威胁发生可能性 T（1–5） |
| `vulnerability` | 脆弱性严重程度 V（1–5） |
| `measure` | 防护有效性（1–5，越大越好） |

这个代价必须有明确的对冲，否则半年后没人知道这一列到底是什么意思。
对冲有三处：`model/dictionary.go` 的包注释、本文档、以及
`DictionaryCategory.ParticipatesInRiskCalculation()` ——最后的这个
方法让服务层能**用代码**决定「是否对权重做区间校验」，而不是靠注释。
前端的表现是：资产类型的编辑对话框里**不显示**权重滑块。

> `threat` / `vulnerability` / `measure` 三类在 P2 只做维护，真正的
> 使用在 P4 风险计算。现在就把它们放进字典表，是为了让「评估字典」
> 有一个统一的维护入口，而不是等到 P4 再补一次迁移 + 一次前端。

### 3.2 资产表存 `code`，代价是 code 不可变

`assets.asset_type` 存的是 `dictionaries.code`（如 `server`），
**不是** `dictionaries.id`。

收益：
- 历史资产不会因为字典行被重排/重建而指向别的类型；
- 资产表能脱离字典表被单独读懂（直接看库就能理解 `asset_type`）；
- 导入文件里写码或写中文名都能解析（见 §4.6）。

代价：**`code` 创建后不可变**，改它会让历史资产指不到东西。所以
`PATCH /api/dictionaries/{id}` 收到不同的 `code` 时直接拒掉：
400 `DICTIONARY_CODE_IMMUTABLE`。

> 为什么不「级联更新所有引用它的资产」？因为那是**一次不可逆的全表写**，
> 且在任何一次部分失败之后都留下半改状态。而用户改 `code` 的真实需求
> 通常是「名字取得不好」——那是 `name` 该管的事。

### 3.3 「停用」优于「删除」

`enabled = false` 之后：

- 该字典项**不再出现在新建/编辑表单的下拉里**（`GET /dictionaries?enabled_only=true`）；
- 但**历史数据引用它时仍然能翻译出中文名**——`Resolve` **不过滤**
  `enabled`。

守门脚本实测：把内置类型 `network_device` 停用后，回读已有资产时
`asset_type_name` 仍然是「网络设备」，且**已停用类型的资产仍可编辑**
（改备注不会被「类型已停用」挡住），但**改成已停用的类型**
会被拒（400 `ASSET_TYPE_UNKNOWN`）。

为什么要有「停用」而不只有「删除」：字典项是**历史数据的解释**。
删掉一个类型会让一批资产的 `asset_type` 变成悬空指针——它还在库里，
但没人知道它是什么意思了。停用表达了正确的意思：「以后别用新的了，
但过去用它记的东西还是那个东西」。

因此删除有两道保护：

| 情况 | 状态码 | 错误码 |
|---|---|---|
| 内置项（`is_builtin = true`） | 409 | `DICTIONARY_BUILTIN_READONLY` |
| 仍被资产引用的资产类型 | 409 | `DICTIONARY_IN_USE`（`message` 带引用条数） |

**状态码用 409 而不是 400**：请求本身没毛病，是「当前状态不允许」。
与 `ASSET_NO_TAKEN` / `ASSET_GROUP_NAME_TAKEN` 等同一类，契约的
`Conflict` 响应里列的就是它们。

## 4. 批量导入：两阶段

> **P2 的验收标志：导入 500 行资产成功，错误可定位到具体行号。**
> 本文 §4.3 与 §4.4 分别是这两条的实现要点。

### 4.1 为什么要两阶段，以及 commit 为什么重新上传文件

`POST /assets/import/preview` 返回一份预览（行数、错误清单、未匹配的组），
`POST /assets/import/commit` 才真正写库。

**关键设计：commit 重新上传同一份文件，服务端不持有任何导入会话状态。**

省掉重新上传的代价是引入一份有 TTL 的内存缓存（多副本部署时会话粘滞）
或一张临时表（要多一套清理），而收益只是省掉几百 KB 的上行流量——
不划算。

更重要的是：**两阶段共用同一个 `parseImport`**。校验规则只有一份，
因此不存在「预览说没问题、提交却失败」这类偏差。一旦分成两份实现，
用户就会彻底不再信任预览。

服务端不信任客户端，所以 commit 会**重新校验**，而不是复用 preview 的结论。

### 4.2 原子性：一条不合格则一条都不写

半成功的导入会留下一个**无法回答的问题**：「台账里现在这批数据到底导完了
还是没导完？」用户拿着错误清单改完重传的成本，远低于事后逐条比对哪些
进去了哪些没进去。

所以建组 + 插资产在**同一个事务**里；任一行不合格则整体回滚。
失败时响应体是 `ErrorDetailEnvelope`，`data` 里挂**完整的预览结果**，
前端可以直接渲染出与预览阶段完全相同的错误表，而不是只弹一句「导入失败」。

> 事务边界还有一个实际作用：不会留下一批「为了这次导入而建、但这次导入
> 又没成功」的空分组。

### 4.3 两种失败的优先级

一个文件可能同时命中两种失败，**顺序是刻意定死的**：

| 优先级 | 情况 | 状态码 | 错误码 | `data` |
|---|---|---|---|---|
| 1 | 除「引用了不存在的组」之外还存在不合格行 | 409 | `ASSET_IMPORT_HAS_ERRORS` | 完整预览（含全部行级错误） |
| 2 | 唯一的阻塞原因就是「引用了不存在的组且未选自动创建」 | 400 | `ASSET_IMPORT_GROUP_NOT_FOUND` | 无（`message` 列前 5 个组名） |

**为什么必须先判第一种：** 如果先报 `GROUP_NOT_FOUND`，用户按提示把组
建出来再传一次，会撞上 `HAS_ERRORS`，白跑一轮；更糟的是那些真正的数据
错误被藏在了后面。

**为什么第二种必须真的可达：** 这条曾经是死代码——`create_missing_groups=false`
时每个未匹配的组同时也会 `ErrorRows++`，于是 `ErrorRows > 0` 永远先命中，
`ASSET_IMPORT_GROUP_NOT_FOUND` **在任何输入下都不会返回**。而契约里明确
列了它。**文档里写着却永远不会出现的错误码，比不写更糟**——调用方会照着
它写分支，然后永远走不到。

修法是让 `parseImport` 单独统计 `groupOnlyBlockedRows`（**能走到组校验
分支的行，说明它的逐格校验与查重都已经通过了**，因此它的唯一问题就是
缺组），commit 时从 `ErrorRows` 里扣掉再判断：

```go
if outcome.preview.ErrorRows-outcome.groupOnlyBlockedRows > 0 {
    return nil, errImportHasErrors(outcome.preview)   // 409
}
if len(outcome.preview.UnmatchedGroups) > 0 {
    return nil, errImportGroupNotFound(outcome.preview.UnmatchedGroups)  // 400
}
```

守门脚本对两种形态各有一条断言：`errors.csv`（10 处行错误 + 1 处缺组，
期望 `HAS_ERRORS`）与 `groups.csv`（3 行全部只是缺组，期望
`GROUP_NOT_FOUND`）。

### 4.4 行号保真：报的是**源文件行号**

错误必须报用户能在 Excel 里看到的那个行号——**含表头、从 1 开始、
且不会被中间的空行带偏**。

- **xlsx**：`excelize.GetRows` 按行序返回（含中间空行），因此下标 +1
  就是行号。
- **CSV**：`csv.Reader` **会跳过空行**，所以不能用「第几条记录」计数。
  行号取自 `r.FieldPos(0)` —— 它返回该字段在**原始文本**中的字节偏移，
  据此换算出真实行号。

踩过的坑：某个版本的行号是按「第几条记录」数出来的，文件里每多一个空行，
后面所有提示就整体偏移。**偏移后的行号看起来完全合理**，用户会去改出错
行的上一行，然后反复失败。守门脚本的 `errors.csv` 刻意在中间插了 3 个
空行，10 条错误的行号实测全部正确（4 / 7 / 8 / 9 / 10 / 11 / 12 / 13 / 15 / 16）。

### 4.5 格式按魔数嗅探，不按扩展名

`DetectFormat` 只看头四个字节是不是 `PK\x03\x04`（xlsx 本质是 zip）。

只看扩展名会踩两类坑：

1. 用户把 xlsx 改名成 `.csv`（或反过来）；
2. 浏览器上报的 MIME 类型五花八门——xlsx 常被报成
   `application/octet-stream`。

`.csv` 走 `csv.Reader`，`LazyQuotes = true`（资产名里出现一个裸双引号
不该让整份文件无法导入），`FieldsPerRecord = -1`（手改过的 CSV 字段数
不一致时，报「第几行有问题」比整份报错有用）。

**编码**：去 BOM → 试 `utf8.Valid` → 失败则用 `simplifiedchinese.GBK`
解码。必须支持 GBK，因为简体中文版 Excel 的「另存为 CSV」默认就是 GBK。
守门脚本用一份真 GBK 文件验证（`gbk.csv`，含中文类型名与中文状态）。

### 4.6 列按表头名匹配，不按位置

`mapImportColumns` 按表头**名称**映射，允许列顺序与模板不同，也允许存在
模板之外的额外列（直接忽略）。缺必需的列是**文件级**错误，直接返回
400 `ASSET_IMPORT_MISSING_COLUMNS` 并列出缺哪些——此时继续逐行校验只会
产出一堆「第 2 行 资产类型 为空」这种误导性错误。

如果按位置匹配，用户自己插一列「备注2」会让后面所有列整体错位，而
**错位后的数据看起来完全合理**——这类问题极难发现。

模板共 14 列，其中只有 2 列必填（`资产名称`、`资产类型`）。另有一个
特例：**重复列名取第一次出现的位置**，与 Excel 的行为一致。

**资产类型列同时认「码」和「中文名」**：模板里给的是码（`server`），
但用户凭直觉会写「服务器」。只认码会把最常见的一次性错误放大成一整屏
500 条报错。

中文名 → 码的别名索引由 `buildAssetTypeAliasIndex` 显式构建，不遍历
map——**Go 的 map 遍历顺序是随机的**，若两个类型恰好同名（内置类型允许
改名），按名解析的结果会在每次请求之间跳变。改成按码排序后取第一个，
并把重名的名称标记为歧义（不放进索引），于是这类输入会得到明确的
「不存在该类型」，而不是时而成功时而失败。

### 4.7 查重的两个判据

| 判据 | 范围 | 说明 |
|---|---|---|
| `asset_no` | **全局唯一**（文件内 + 库内） | 相同编号报错并指出首次出现的行号 |
| `(名称, IP 地址)` | **全局唯一**（文件内 + 库内） | 身份键用 `\x00` 做分隔符 |

第一条对应业务编号，第二条兜住「同一条资产被重复录入」——同一份清单
重传是最常见的误操作，而这类行往往没有编号。

顺序也是刻意的：**先查编号，再查身份**。同一行同时撞两者时，报「编号
重复」——它更精确、更接近用户的心智。文件内查重与库内查重的顺序同理。

还有一条实现细节值得记下来：**逐格校验没过的行不参与查重**。它的名称或
IP 可能是错的，拿一个错的值去比对只会产出第二层误导性错误。

### 4.8 边界防护

导入是一个「解析不可信文件」的入口，防护集中在 `pkg/spreadsheet`：

| 限制 | 值 | 防的是什么 |
|---|---|---|
| `MaxFileSize` | 10 MB | 上行带宽与内存 |
| `MaxRows` | 5000 | 一次导入的规模上限 |
| `MaxColumns` | 64 | 超宽表格 |
| `MaxCellRunes` | 2000 | 超长单元格（超出即**截断**而不是报错） |
| `UnzipSizeLimit` | 128 MB | **压缩炸弹**（xlsx 是 zip） |
| `UnzipXMLSizeLimit` | 32 MB | 单个 XML 部件解压上限 |

压缩炸弹是这一节里唯一「不设就会出事故」的一条：一个 10 MB 的 xlsx
可以解压出几十 GB，把内存打满。前两个限制靠 `excelize.Options` 交给
库去拦，`MaxFileSize` 由我们自己先拦一道（还没进库）。

预览里的行错误最多回传 **200 条**（`maxImportPreviewErrors`），
超出部分只计数不追加，并置 `truncated_errors = true`。
一份 5000 行全错的文件否则会产出 5000 条错误——那不是一个能用的界面。

## 5. 权限与审计

### 5.1 权限码

| 端点 | 权限码 |
|---|---|
| `GET /assets`、`GET /assets/{id}` | `asset:read` |
| `POST/PATCH/DELETE /assets`、三个 `/assets/import/*` | `asset:write` |
| `GET /asset-groups` | `asset:read` |
| `POST/PATCH/DELETE /asset-groups`、`POST /asset-groups/{id}/move` | `asset:write` |
| `GET /dictionaries` | `dictionary:read` **或** `asset:read` |
| `POST/PATCH/DELETE /dictionaries` | `dictionary:write` |

两处刻意的不对称：

1. **资产组没有独立权限码**，整个挂在 `asset:*` 下。它没有独立的管理
   场景，只是资产的组织方式；单开一对权限码只会让角色配置页面多出两个
   没人会改的开关。
2. **`GET /dictionaries` 同时接受 `asset:read`**。填资产表单时要从这里
   拉「启用中的资产类型」，而评估员/审计员都可能只有 `asset:read`。
   写接口则严格只认 `dictionary:write`——改字典会影响所有资产的分类口径。
   （与 `/roles` 的处理同理：能看用户的人也需要看角色。）

前端**不做角色硬编码**，动态路由与菜单由后端下发的权限码驱动
（见 `docs/03` §7）。

### 5.2 新增 11 个审计动作

`asset.create` / `asset.update` / `asset.delete` / `asset.import`、
`asset_group.create` / `asset_group.update` / `asset_group.move` /
`asset_group.delete`、`dictionary.create` / `dictionary.update` /
`dictionary.delete`。

`asset.import` 的明细带 `file_name` / `format` / `total_rows` /
`imported` / `created_groups` —— 审计日志要能回答「这份文件是谁在什么时候
导进来的、写进去多少条」。

### 5.3 ⚠️ 三种「审计声明」的区别

中间件在写请求结束时检查「这次操作有没有留下审计记录」，没有就打一条
告警。这需要区分三种情况，而**把它们混成两种就会毁掉这条告警的价值**：

| 声明 | 含义 | 用在哪 |
|---|---|---|
| （无声明） | 漏了 → **打告警** | 无 |
| `MarkAuditRecorded` | 审计**已经写了**，只是不经过中间件 | service 层 `auditor.record` |
| `MarkAuditSkipped` | 审计**按设计就不该写** | 导入预览 |

`POST /assets/import/preview` 必须声明 `MarkAuditSkipped`。它是写方法的
请求（**必须** POST 传文件），却不改变任何状态——审计一条「预览了某个
文件」既没有意义，又会让审计表被高频空操作灌满。

**这个区分是 P1 遗留的缺陷在 preview 上重现时补上的**：不区分的话，
每次导入预览都会打一条「本次操作不会留下审计记录」，把真正漏审计的
情况淹掉。`MarkAuditSkipped` 必须放在 handler 的**最前面**——`c.Next()`
之后中间件就要读它了。

## 6. 前端

### 6.1 三个页面 + 一个向导

| 路由 | 组件 | 权限 | 说明 |
|---|---|---|---|
| `/assets` | `AssetListView.vue` | `asset:read` | 台账：筛选（含分组树选择 + 「含子组」）、新建/编辑对话框、删除、导入入口 |
| `/assets/groups` | `AssetGroupView.vue` | `asset:read` | 分组树的增删改 + 移动 |
| `/system/dictionaries` | `DictionaryView.vue` | `dictionary:read` | 四个类别 Tab、行内启用/停用、内置项禁删 |

导入向导是 `AssetListView` 里的 `AssetImportDialog.vue`，三个阶段
（`select` → `preview` → `done`）。文件**一直留在内存**，因为 commit 要
重新上传。四个阻塞条件（缺列 / 有错误行 / 有未匹配组 / 无可导入行）
汇总成一个 `blockReason`，前端**不在本地复刻后端的分类逻辑**——
勾选「自动创建缺失的组」时重新调一次 preview，让后端说了算。

### 6.2 blob 响应下的错误信封

`GET /assets/import/template` 返回二进制流，因此前端用
`responseType: 'blob'`。**这会把错误响应也包成 Blob**：后端明明返回了
标准的 `{code, message}` 信封，axios 拦截器却取不出来，界面只剩
「请求失败（HTTP 403）」。

修法是在响应拦截器里判断 `raw instanceof Blob`，先按文本读出来解析成
信封（`client.ts` 的 `parseBlobEnvelope`），失败才退化成通用错误。
`downloadImportTemplate()` 也因此**不走** `api.get` 的高层封装，
直接用底层 `http.get<Blob>`。

文件名从 `Content-Disposition` 解析：优先 RFC 5987 的
`filename*=UTF-8''<百分号编码>`（中文文件名必须走这条），回退纯 ASCII
的 `filename`。

### 6.3 目录树的两个细节

- **`el-tree` 的过滤器用 `includes` 而不是 `new RegExp`**：用户输入的
  分组名里带 `(` 会让正则构造抛异常，整个筛选框直接失效。
- **移动对话框要把「自身 + 全部后代」标为 `disabled`**：这是前端对成环
  的第一道提示（后端的 `ASSET_GROUP_CYCLE` 是兜底）。用
  `collectSubtreeIds(selected)` 收集。

`canWrite` 一律取自 `auth.can('asset:write')` / `auth.can('dictionary:write')`，
不在前端写角色判断。

## 8. 已知取舍与后续

**明知的短板（现在不做，但触发条件明确）：**

1. **标签无法索引查询**（§1.5）。触发条件：出现「按标签统计/聚合」需求。
2. **`asset_type` 的引用计数查询**在删除时做了一次 `COUNT`。资产量到十万级
   时需要给它加索引或改成异步维护。当前 `idx_assets_asset_type` 已存在，
   属于可接受；列表页的主查询走 `idx_assets_group_status (group_id, status, id)`。
3. **导入不支持「只更新已存在的资产」**（upsert）。当前是纯新增，
   重传同一份清单会被判重拦下。这是刻意的：更新的语义（覆盖哪些字段？
   空值算不算清空？）需要一个独立的设计。
4. **`asset_no` 全局唯一而不是「按分组唯一」**。全局唯一更简单，
   也不会在分组调整后突然冲突。
5. **没有资产的批量删除**。删除是审计敏感操作，批量删除需要一个
   明确的确认设计与逐条审计，不在 P2 范围内。

**P2 期间修正的上游缺陷：**

| 位置 | 问题 | 修法 |
|---|---|---|
| `pkg/reqctx` | 写请求**按设计不该有审计**的情况无法声明，导致 preview 每次都打「未记录审计」告警 | 新增 `MarkAuditSkipped`，与 `MarkAuditRecorded` 分开；中间件早退 |
| `pkg/spreadsheet` + `assetimport` | 只有表头的文件不被 `ASSET_IMPORT_NO_ROWS` 拦住（`Read` 的 `ErrEmpty` 判据是「有没有非空行」，表头本身是非空行） | `parseImport` 里补 `len(dataRows) == 0` 判定 |
| `service/assetimport` | `ASSET_IMPORT_GROUP_NOT_FOUND` 因判断顺序**永不可达**（契约里却列着） | 新增 `groupOnlyBlockedRows`，commit 时扣除后再判优先级 |
| `repository/assetgroup` | 子树查询用 ID 拼前缀，只对根组成效 → 按分组筛选静默返回 0 条、删组 500 而非 409 | 改签名 `SubtreeIDsByPath(ctx, groupPath)`，编译期堵死（§2.3） |

Nessus/OpenVAS/Excel 解析器、漏洞清单）。

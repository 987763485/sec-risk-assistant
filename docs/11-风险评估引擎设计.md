| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-10-11 |
| 覆盖阶段 | **P4**（风险评估引擎、评估任务、矩阵下钻、报告数据导出） |
| 对应验收标志 | **「手工核算与系统结果一致；界面值 = 落库值 = 报告值三者完全一致」** |
| 守门脚本 | `scripts/verify-assess.sh`（**227 断言**，15 节，隔离临时库 `sec_risk_assess_e2e` + 端口 18085） |

本文档回答四件事：**风险值为什么用定点整数算、配置快照为什么是这张表的核心、
三条路径的一致性靠什么保证、矩阵为什么必须有空格子**。每一处都写清
「不这么做会怎样」——这几处都是「实现得看起来很对、错起来完全静默」的区域。

## 1. 范围

**做**：

- 风险计算：GB/T 20984 相乘法（`internal/pkg/riskengine`），**只在后端实现**
- 评估任务：CRUD、范围三选一（全部 / 资产组 / 手工指定）、任务级默认威胁
- 试算（`preview`）：只读、可反复调、不落库、不写审计
- 计算（`calculate`）：事务内先清后写，落 `risk_items` + `assessment_assets`
- 配置快照：计算时的权重与阈值随评估行冻结，历史评估永久可复现
- 风险矩阵：固定 5×5 网格 + 按格下钻
- 逐项威胁覆盖：`manual` 来源，重算时保留
- 报告数据导出（`export-data`）：P5 渲染器消费的那份结构化数据（P5 已完成对接，见 §6.1 的补充说明）

**不做**（明确的边界，避免误以为已有）：

- 不渲染报告文档（PDF / Word）：属 P5 的 docgen，P4 只交付**数据**
- 不做整改建议、不做漏洞生命周期：属 P6
- 不做多模型切换：`model_key` 已落库，但当前只实现 `gb_t_20984_multiplication`
- 不做风险项的手工增删：风险项粒度是「资产 × 漏洞」，没有无来源的手工风险项
  （见 §5.4 关于 `vuln_id NOT NULL` 的讨论）
- 不做定时重算、不做配置变更的批量回溯

## 2. 模型：GB/T 20984 相乘法

```
R = A × T × V
```

| 量 | 含义 | 取值来源 | 取值范围 |
|---|---|---|---|
| **A** | 资产价值 | `assets.importance`（1–5）× 资产价值权重系数 | 0.001 – 500 |
| **T** | 威胁权重 | `dictionaries(category=threat).weight` | > 0，默认 3.000 |
| **V** | 脆弱性权重 | `vulnerabilities.severity`（1–5，扫描器定级） | 1 – 5 |
| **R** | 风险值 | A × T × V，**参与阈值比较** | 0.001 – 125 起，权重可放大 |

档位判定（从高到低，闭区间）：

| 档位 | 条件（默认阈值） |
|---|---|
| `very_high` 很高 | R ≥ 20 |
| `high` 高 | R ≥ 12 |
| `medium` 中 | R ≥ 6 |
| `low` 低 | R ≥ 2 |
| `very_low` 很低 | R < 2 |

### 2.1 为什么 V 取 `vulnerabilities.severity`，而不是字典的 V 权重

这是实施期拍板的决策之一（计划里的 D3）。理由：漏洞的严重程度**已经由扫描器给出了**
（P3 里 `severity` 是「CVSS 优先、等级词兜底」换算出来的 1–5 档），
再让用户在字典里配一套 V 权重，等于让同一个概念有两处真相源。
两处必然会在某个时刻不一致，而不一致时没人知道该信哪个。

字典的 V 权重因此**只保留给「无漏洞来源的手工风险项」**——而当前版本没有这种输入路径
（见 §5.4），所以它实际上处于待用状态。这不是遗漏，是刻意的：先把唯一真相源定死。

### 2.2 为什么不指定威胁时用 T = 3 而不是 T = 1

`DefaultThreatWeight = 3.0`，取中档。与 `importance` / `severity` 缺省为 3 同一条原则：
**「不填」不等于「最低」**。若缺省取最低档，漏配一个威胁就会系统性地低估全部风险，
而低估是安全产品里最危险的方向——它不会报错，只会让报告看起来一片绿。

威胁码在字典里查不到时（被删了 / 被停用后清理过），**既不报错也不静默替换成 3**：
把原码原样显示出来（`threat_name = code`），用户一眼就能看出「这条的威胁配置失效了」。
静默兜底会让一条配置错误的评估看起来完全正常。

## 3. 定点整数：整个引擎的地基

### 3.1 问题：阈值边界上的浮点误差

R 要参与 `≥ 20 / ≥ 12 / ≥ 6 / ≥ 2` 的比较。设想 `A = 1.5`、`T = 4.0`、`V = 2.0`，
数学上 `R = 12.000000000000`，应当判「高」。但浮点乘法的实际结果可能是
`11.999999999999998` 或 `12.000000000000002`：

- 前者判「中」
- 后者判「高」

同一个数学值，两种结论，**而且不报错、不告警**。它只在某个特定权重组合下出现一次，
换一台机器、换一个 Go 版本可能就不再复现。这是最难排查的一类事故：
数据看起来都对，只是档位和昨天不一样了。

### 3.2 做法：放大 1000 倍走 int64

`Scale = 1000`，与 `system_configs` 里 `DECIMAL(6,3)` 的三位小数精度对应。
内部所有量都是 `int64`，阈值同样放大后比较，**只在出参时除回**。

```go
func Compute(cfg Config, in Input) Result {
    aWeighted := int64(in.Importance) * cfg.AssetWeight // importance × wA × Scale
    tMilli := milli(in.ThreatWeight)                     // T × Scale（四舍五入）
    vMilli := int64(in.Severity) * Scale                 // V × Scale

    rMilli := aWeighted * tMilli / Scale * vMilli / Scale

    return Result{A: ..., T: ..., V: ..., R: float64(rMilli) / float64(Scale),
        Level: LevelOf(cfg, rMilli)}
}
```

三个必须注意的细节：

1. **两次除法都是截断，且左结合**。`aWeighted * tMilli / Scale * vMilli / Scale`
   等价于 `((aWeighted * tMilli) / Scale * vMilli) / Scale`，不是
   `aWeighted * tMilli * vMilli / (Scale * Scale)`。两者在绝大多数数据上结果相同，
   在个别数据上差 1 个定点单位（0.001）——而 0.001 恰好就是能把档位翻过去的量。
   **守门脚本因此照着这个截断序列重抄了一遍**（见 §12），而不是用浮点乘一遍再 round。
2. `milli()` 用 `math.Round` 而不是直接截断：`19.999 * 1000` 在 float64 里是
   `19998.999999999996`，截断会得到 `19998`，于是「19.999」被静默变成「19.998」。
3. `NaN` / `±Inf` 在 `milli()` 里归零，在 `ParseConfig` 里报错——配置入口必须拒绝，
   而不是让它算出个 `0` 混进结果。

### 3.3 阈值的自洽校验：不启动一个自相矛盾的等级

`Config.Validate()` 在**解析阶段**就拒绝三类配置：

| 检查 | 不检查会怎样 |
|---|---|
| 四个阈值严格递减（很高 > 高 > 中 > 低） | `very_high == high` 时「高」这一档永远为空——不报错，只是所有结果都少一个等级，而汇总里那格永远是 0 |
| `low ≥ 1` | 低档位下界为 0 时，「很低」永远为空；为负时 R 恒 ≥ 它，「很低」连出现的可能都没有 |
| `0 < asset_weight ≤ 100` | 权重为 0 会把所有 R 压成 0；过大的权重会让 `aWeighted * tMilli` 逼近 int64 上界 |

档位判定的 `switch` **顺序从高到低，不能反**：反过来以后 R = 25 会先撞上「低」的条件
直接返回 `low`，而这是不可能被数据发现的错误（结果看起来是个合法等级）。

### 3.4 配套：数据库也用 DECIMAL

`risk_items.asset_value_a / threat_weight_t / vuln_weight_v / risk_value_r` 全部是
`DECIMAL(6,3)` / `DECIMAL(8,3)`，**不用 FLOAT**。理由与 §3.1 相同：若落库是 FLOAT，
「引擎算对了」也会在存取一个来回之后变成别的值——落库值与报告值的一致就断了。

## 4. 配置快照：`assessments.config_snapshot` 是这张表的核心

### 4.1 问题：改一次阈值会静默改写全部历史评估

权重与阈值存在 `system_configs` 里，界面上随时可改。如果计算时**不冻结**，
那么「三个月前的报告说这台机器是高风险」这个结论会在管理员调整阈值后变成「中风险」——
报告已经发出去了，库里的数据和昨天的对不上，而**没有任何地方报错**。

这是最难排查的一类事故：数据看起来都对，只是和昨天不一样了。

### 4.2 做法：算的时候冻结，之后一律读冻结值

`config_snapshot` 存**人类可读的真实值**（`{"model":"…","asset_weight":1.5,
"thresholds":{"very_high":20,…},"captured_at":"…"}`），不是定点整数。
快照是给人看的、给审计用的，必须能直接读懂。

### 4.3 关键语义：写路径用「当前配置」，读路径用「快照」

这是 P4 里最容易搞错的一处，单列一张表：

| 路径 | 用的配置 | 理由 |
|---|---|---|
| `preview`（试算） | **当前配置** | 用户就是在问「按现在的配置会怎样」 |
| `calculate`（计算） | **当前配置**，并写进快照 | 算完即冻结；用户显式点「计算」就是要按现在的配置算 |
| `matrix`（矩阵） | **快照** | 展示的是那次计算的结论 |
| `export-data`（报告） | **快照** | 报告必须与它引用那次计算一致 |
| `PATCH .../risk-items/{id}`（逐项覆盖威胁） | **快照** | 覆盖后只改这一条的重算，它属于那次评估 |

一句话：**算的时候用当时的配置，之后所有展示与导出都用那次算的配置。**
这样「界面值 = 落库值 = 报告值」就不是靠三处各写一遍再对数，而是由结构保证的。

`configForAssessment()` 实现读路径：有快照用快照，草稿（没算过）用当前配置。
快照解析失败时**回退到当前配置并打 WARN**——守门脚本专门抓这条日志，
它一旦出现就说明历史评估正在被当前配置污染。

### 4.4 快照不追溯，但「重算」会重新冻结

改配置**不会**动任何已算评估的快照与结果（守门脚本 §6 逐条验证）。
但如果用户对老评估再点一次「计算」，就会用当前配置重算并覆盖快照——
这是正确的：用户的动作是显式且即时的，他知道自己在重算。
真正要防的是「用户什么也没做，报告却变了」。

## 5. 数据模型

三张表，落在迁移 `000006_assessment`。字段清单见 `docs/02-数据模型.md` §10，
这里只讲**六个刻意的设计约束**。

### 5.1 `assessments.scope_ref` 是 JSON，`scope_type` 决定怎么解

`all` / `group` / `custom` 三选一，明细存 `scope_ref`。做成一个 JSON 列而不是三张关联表，
是因为范围明细是**时点快照**：评估建好之后，资产组里再加一台机器，不该影响这份评估
（范围已经定了）。关联表会让人忍不住去 join 出「最新成员」，那是另一种语义。

### 5.2 `max_risk` 可空 —— `0` 与「没算」必须可区分

未计算时是 `NULL`，不是 `0`。

用 `0` 当哨兵会让「算了但范围内风险值恰好为 0」与「根本没算过」无法区分。
前端因此在列表页能正确显示「—」而不是「0.0」——这不是展示细节，
而是「这份评估到底跑没跑过」这个业务判断的依据。

`level_counts` 同理：**五个等级键一定都在**（没有的填 0），前端不必在模板里写一堆 `|| 0`。

### 5.3 风险项 A / T / V / R **四列齐存**，不只存 R

下钻时用户要问「这台机器为什么是 20 分」，必须能当场拆出 `A=4 × T=5 × V=1`。
只存结果等于放弃可解释性，事后也无法复核规则本身是否合理——
这与 P3 保留 `severity_raw` 是同一条理由。

### 5.4 `risk_items.asset_id` / `vuln_id` **刻意不建外键**

风险项是**时点快照**（与 §4 的 config_snapshot 同类），不是实时派生数据。

- 若建 `CASCADE`：删掉一条漏洞会连带抹掉历史评估里的一行，报告的「当时结论」被悄悄改写
- 若建 `RESTRICT`：会因为一份三个月前的评估而让用户删不掉一条误录入的漏洞

折中：**ID 保留用于下钻跳转，展示一律走快照列**（`asset_name` / `asset_ip` / `vuln_title`）。
目标被删时跳转 404，但报告仍然完整可读。

`assessment_id` 则**建外键并 CASCADE**——它与上面不矛盾：评估任务被删除，说明用户不再需要
这份评估，它的结果行是**派生数据**，跟着主体走是正确语义。而资产 / 漏洞是外部的
**事实来源**，删掉它们不该改写历史结论。

### 5.5 `vuln_id` 收紧为 `NOT NULL`（初版计划写的是可空）

两个原因：

1. MySQL 的唯一索引把多个 `NULL` 视为互不相同（`000004` 约束 2 踩过这个坑）。
   `vuln_id` 可空则 `uk_risk_items_target (assessment_id, asset_id, vuln_id)` 形同虚设，
   重复计算会堆出重复行。
2. 当前粒度就是「资产 × 漏洞」，没有无漏洞来源的输入路径。

将来真要做手工风险项，应当**新增迁移**，而不是让唯一索引从一开始就虚设。

### 5.6 唯一键与索引

```sql
UNIQUE KEY uk_risk_items_target (assessment_id, asset_id, vuln_id)
KEY idx_risk_items_matrix (assessment_id, importance, severity)
KEY idx_risk_items_level  (assessment_id, risk_level)
```

唯一键是「先清后写」之外的第二道保险：即使重算逻辑将来出 bug 重复插入，数据库也会拒绝。
矩阵索引对应下钻的两种查法（按格、按等级）。

## 6. 三条路径的一致靠结构，不靠对数

### 6.1 `preview` 与 `calculate` 共用 `build()`

系统里**不允许存在第二条风险计算路径**。做法不是三处各写一遍再对数，
而是让它们共用 `build()`，而这个函数内部只调 `riskengine.Compute`。
只要有一条路自己算，三处一致性迟早会在某个边界条件下分叉，且分叉不报错。

`export-data` 更进一步：它**不做任何计算**，只把已落库的结果读出来重新组装。
所以它天然与落库值一致，而落库值又由 `build()` 产出。

> **P5 的扩展（重要）**：`ExportData` 被拆成了两层 ——
> `ExportData = buildExportData + 写 assessment.export 审计`，报告导出走**前者**。
> 理由：报告导出自己已经记了 `report.export`，若它调 `ExportData`，
> 审计表里就会多出一条**没有发生过的** `assessment.export`。
> 这个拆分同时把「两条取数路径是同一份实现」钉死在结构上——
> 报告值与界面值不可能分叉，因为它们根本是同一次调用。
> 详见 `docs/12` §4.1。

### 6.2 逐项覆盖与重算的交互

`threat_source` 记录威胁的来源（`default` 取任务级 / `manual` 逐项覆盖）。
重算时**保留 `manual` 的覆盖**——否则用户半小时的逐条调整会被一次「重新计算」悄悄回退。
这与 P3 保留 `vuln_asset_links.matched_by` 同理：**能溯源才敢批量改回去**。

### 6.3 重算是事务内「先清后写」

`DeleteResults` 与写入在同一个事务里，是为了让「旧的删掉了、新的没写进去」这种状态
不可能被其它请求看见。

**副作用（已知且必须记住）**：重算后风险项是**新插入的行，自增 ID 全变了**。
任何缓存了风险项 ID 的地方，在重算之后都必须重新拉取。前端结果页重算后重新加载列表，
不只是「刷新数据」，而是**必须**——拿着旧 ID 去 PATCH 会得到 404。
守门脚本把这条语义也钉成了断言（"重算后该条换了新 ID"）。

> **P6 之后要补一句**：这条副作用从 P6 起不再只影响「缓存 ID 的代码」，
> 而是会**跨模块断链**。整改单一旦把 `risk_item_id` 当作自己的业务身份，
> 一次重算就会让所有单子指向不存在的行——而且**不报任何错**。
> 应对只有一处是**结构性**的（整改单身份改用 `(asset_id, vuln_id)`，
> 并把展示所需字段冗余成快照列；`risk_item_id` 降级为「发现出处」，允许失效），
> 其余（约定"重算后重新拉取"）都只是约定。设计理由与反向验证见
> `docs/13-整改跟踪与仪表盘设计.md` §2 的 D1 与 §6；
> `scripts/verify-remediate.sh` 第 5 节会真的重算一次来做反向对照。

## 7. 风险矩阵：固定 25 格，不许稀疏

横轴 `importance`（资产重要性），纵轴 `severity`（漏洞严重程度），都是**原始档位**，
不受权重影响——否则改一次权重，同一台机器会从一格跳到另一格，矩阵失去可比性。

**格子数量恒为 25**（包括没有命中任何风险项的格子）：

- 不能用「只返回命中的格子」的稀疏结构。「昨天这块是红的」依赖位置稳定；
  稀疏结构会让空格子的位置随数据变化，热力图看起来就是另一张图。
- 每格的 `level` 由**格内最大 R** 与快照阈值判定（不是平均，也不是计数）。
  一台机器能被打穿到什么程度，取决于它最弱的那一环。

资产级汇总（`assessment_assets`）同理取该资产下的**最大 R**，而不是平均。

## 8. 权限与审计

**权限零新增**：`assessment:read` / `assessment:write` / `system:read` / `system:write`
在 P1 已登记。

读接口放宽是有意的：`GET /api/system/configs` 同时接受 `system:read` 与 `assessment:read`。
评估员没有系统设置权限，但他在评估执行页**必须能看到当前阈值**才能理解结果。
与 `/roles`、`/dictionaries` 是同一处理。

审计动作（P4 新增 6 个 + 1 个系统配置）：

| 动作 | 何时写 |
|---|---|
| `assessment.create` | 建评估 |

漏声明会在服务端日志里留下「写操作未记录审计」告警，守门脚本盯这条日志。

## 9. 前端铁律：只查表，不做比较

前端**不参与任何风险计算**，连「哪个档位更严重」的判断都不做：

- 等级的颜色、标签、排序权重全部是**查表**（`RISK_LEVEL_COLORS[level]` 这类），
  **没有一处比较运算**（不写 `r >= 20`，不写 `level > other`）
- 等级枚举顺序来自后端，前端不重新定义

理由：一旦前端有了比较逻辑，就出现了第二处对「阈值」的解释。
后端改阈值、前端没改，界面就会和落库值不一致——而这类不一致在开发环境
（阈值恰好是默认值）永远不会暴露。

执行页的试算结果是**后端返回的完整结果**，不是前端拼出来的；
连「临时阈值试算」也是把阈值原样发给后端算，前端只负责显示。

## 11. 实现期对计划的修正

计划是纸面的，实现会遇到纸面没写的情况。以下每一条都是实际发生并被修正的，
列出来是为了让后来的人知道「为什么和初版计划不一样」。

### 11.1 `vuln_id` 从可空收紧为 `NOT NULL`（计划 §数据模型）

见 §5.5。计划里写的是可空，实现时发现唯一索引对多个 NULL 无效。

### 11.2 风险项不建外键（与 `000004` 约束 5 的初版设想不同）

`000004` 曾设想「P4 接入引用检查」，即资产 / 漏洞被引用时禁止删除。
实现时改为**逻辑引用 + 快照列**（§5.4）。理由：一份三个月前的评估不应该阻止用户
删掉一条误录入的漏洞，而删掉它也不该改写已经发出的报告结论。
两者不可兼得时，选了「报告不可变」。

### 11.3 `top_items` 确实排了序（守门脚本抓到的缺陷）

契约里 `top_items` 写的是「风险值最高的风险项，最多 20 条」，
`Preview` 的注释也写着「排序在 build 里已经做过，这里只负责截断」。

**但 `build()` 只排序了资产汇总，从没排过风险项。** 于是执行页上所谓的
"最该先看的 20 条"其实是数据库返回顺序（按 asset_id、vuln_id）的前 20 条——
它既不报错，结果也不"错"，只是**展示的是别的东西**。

修法是在 `build()` 末尾对 `Items` 排序，并**重建 `TopItemIndex`**：
这个索引存的是切片下标，而 `Calculate` 要靠它取 `CreateRiskItems` 回填的自增 ID；
重排后旧下标全部失效，不重建会让资产汇总的 `top_item_id` 指向别的资产的行——
同样不报错，只是下钻跳错页面。

### 11.4 `createVulnerability` 的响应码是 200，不是契约里的 201

守门脚本比对创建接口时发现：`POST /api/vulnerabilities` 的契约写 `201`，
实现却用了 `response.OK`（200），而 `assets` / `dictionaries` / `asset-groups`
三个创建接口都是 `201`。P3 的守门脚本恰好没断言这一码的具体值，所以一直没暴露。

已统一为 `201`，并同步修正了 P3 脚本中两处断言。

### 11.5 `preview` 的 `scope_ref` 曾是 `null`（契约修正）

`PreviewResult.ScopeRef` 来自 `decodeScope(probe)`，而 `decodeScope` 在 `all` 范围下
返回 `nil`——Go 的 `nil` 切片序列化成 JSON 是 `null` 而不是 `[]`。
契约里写的是「`all` 时为空数组」，前端因此会在 `scope_ref.length` 上运行时崩溃
（而且**编译期发现不了**，因为契约当时没标 `required`）。

修了两处：服务层显式非 nil 化；契约把一批必然返回的字段（`scope_ref`、`assets`、
`top_items`、`max_risk` 等）标为 `required`。可空指的是「值可以是 `null`」，
不是「key 可能缺席」——前端因此可以直接 `.length`，不必层层写 `?? []`。

### 11.6 风险项 ID 在重算后变化（已知语义，非缺陷）

见 §6.3。列在这里是因为它会影响任何缓存 ID 的代码。

**P6 补充**：这条语义影响的不只是「缓存」。任何把 `risk_items.id` 当业务主键使用的下游模块，
都会在这里踩坑——最典型的是整改单。`docs/13` §2 的 D1 记录了完整推理，
结论是：下游模块的业务身份**不能**建在 `risk_items.id` 上，
`risk_item_id` 只能作为「发现出处」保留（允许失效），展示所需字段另存快照。
这条副作用因此是 `docs/13` 全部七项决策里唯一一条由 P4 直接派生的。

## 12. 守门脚本与验收

`scripts/verify-assess.sh`，15 节 227 断言，隔离临时库 `sec_risk_assess_e2e` + 端口 18085。

### 12.1 最重要的设计：**独立算术**

预期值**不复用后端任何代码**，而是在脚本里用 bash 整数运算照着后端的截断序列重抄一遍：

```bash
rmilli() {  # <importance> <w_milli> <t_milli> <severity>
  local am=$(( $1 * $2 ))
  local vm=$(( $4 * 1000 ))
  echo $(( am * $3 / 1000 * vm / 1000 ))
}
```

这不是多余。如果脚本改成调后端自己的算法来「验证」后端，那就成了自己证明自己：
算法改错了，两边一起错，脚本依然是绿的。用浮点乘一遍再 round 也不是等价物——
它在绝大多数数据上给出相同答案，于是测试是绿的，但那是巧合（§3.2）。

### 12.2 覆盖的 15 节

### 12.3 边界用例怎么构造的

用 `asset_weight` 覆盖把 R 精确凑到边界值。边界评估的范围只含 1 台资产、1 条漏洞、
默认威胁 T=1，于是 `R = 1 × w × 1 × 1 = w`——把 w 设成目标值即可。

不用「造一个 T=0.999 的威胁」是因为：**后端 `ParseConfig` 的四个阈值参数是 `int`**，
阈值只能是整数（阈值是「20 分」这种整数分界，权重才需要小数），
所以一律「动权重、不动阈值」。

测 `19.999` 而不是 `19.001`，是因为 `19.999` 与 `20` 只差**一个定点单位**（0.001）——
任何浮点误差都足以让它翻档，这正是 §3.1 要挡的那类 bug。

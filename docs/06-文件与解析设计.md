## 1. 范围

**做**：

- 扫描报告上传：三重校验（扩展名 / MIME / 魔数）、内容哈希去重、流式落盘
- 三类报告的解析：Nessus（.nessus）、OpenVAS（.xml）、通用表格（.xlsx / .csv）
- 解析采用**两阶段**：`preview`（只读）→ `commit`（入库），行级错误定位到源文件行号
- 漏洞清单：分页筛选、手工录入、三态编辑、删除
- 资产关联：提交时按主机 IP **自动匹配** + 人工**手动补挂**兜底

**不做**（明确的边界，避免误以为已有）：

- 不做漏洞去重合并：同一文件重新解析会产生重复条目（见 §11）
- 不做漏洞生命周期（状态流转、复测）：属 P4 评估 / P6 整改
- 不做风险值计算：属 P4（`internal/pkg/riskengine`）
- 不解析 Burp / Nmap / Qualys 等其它格式：接口已开好口子（§5.1）
- 不做报告合并、去重比对、跨文件差异

## 2. 数据模型

三张表，落在迁移 `000005_file_vuln`。字段清单见 `docs/02-数据模型.md` §9，
这里只讲**六个刻意的设计约束**——它们每一条都对应一类具体缺陷。

### 2.1 `scan_files.sha256` 唯一 —— 去重判据

```sql
UNIQUE KEY uk_scan_files_sha256 (sha256)
```

判据是**内容哈希**而不是文件名：同一份报告被重命名后重传（`内网扫描.xml`
→ `内网扫描-最终版.xml`）在业务上是同一份文件，靠文件名去重一点用都没有。

命中唯一键时**不报错**，而是幂等返回已有记录（§4.3）。这样做的收益：
磁盘上同一份报告永远只有一份；审计里能回答「这份报告被谁传过几次」。

### 2.2 `storage_path` 故意不带扩展名

落盘路径是 `YYYYMM/<32hex>`（`crypto/rand` 取 16 字节转十六进制），
**没有 `.nessus` / `.xml` 后缀**。理由：

1. 原文件名是用户可控的，把它带进文件系统路径就要处理 `..`、`/`、`\0`、
   超长名、Windows 保留名……一条漏掉就是一个洞。用随机名 + 单独的元数据表，这类问题一次性消失。
2. 不带后缀的文件即使被放到能被静态服务访问的位置，也不会被按扩展名解析执行
   （Nginx 侧另有 `/uploads/` 403 兜底）。

`original_name` 只存在数据库里，下载时通过 `Content-Disposition` 还原——展示用的名字
与磁盘上的实体完全解耦。

### 2.3 `vulnerabilities.source_file_id` 可空

`NULL` = 手工录入；有值 = 由该文件解析而来。用**一张表**装两种来源，而不是
「解析表 + 手工表」两张，是因为清单页、筛选、统计都希望它们是同一种东西：
一个被评估人员确认的漏洞，不该因为来源不同而在列表里长得不一样。

### 2.4 `severity` 与 `severity_raw` 双列并存

| 列 | 类型 | 用途 |
|---|---|---|
| `severity` | `tinyint` 1–5 | 筛选、排序、统计、将来的风险计算 |
| `severity_raw` | `varchar(64)` | 保存**定级依据**，供人工复核 |

只存原始串的问题：Nessus 写 `High`、OpenVAS 写 `4.3`、中文表格写`高危`，
三份报告没法按同一条线排序；只存换算值的问题：用户看到「4 级」，却不知道
这是扫描器的判断还是我们算出来的，出了疑问无从追溯。

`severity_raw` 存什么取决于**定级依据**：带 CVSS 分值就存分值（`8.1`），
否则存等级词（`HIGH`）。这一点在契约 `Vulnerability.severity_raw` 里有完整说明——
因为列名叫「原始等级」而值是 `8.1` 时，人在界面上会以为数据错了（前端的列表头
因此写作「原始等级/分值」）。

### 2.5 `cve_ids` 逗号分隔一列，不建子表

CVE 列表是**展示与跳转用**的弱关系：界面上就是一行文字（`CVE-2021-44228,
CVE-2021-45046`），不参与连接查询，也不需要引用完整性。

建子表要付三笔成本：写入时要展开（一次 500 条漏洞 × 平均 2 个 CVE = 1000 行）、
查询时要 `GROUP_CONCAT` 回去、删除时要跟着清理。换来的是「按 CVE 反查漏洞」——
而这个需求用 `LIKE 'CVE-2021-44228%'` 已经够用（存量规模是万级）。

写入前统一做**大写 + 去重**，否则 `cve-2016-6329` 与 `CVE-2016-6329`
会变成两个看起来一样的东西。

### 2.6 删除语义：RESTRICT 与 CASCADE 分开设

| 外键 | 行为 | 理由 |
|---|---|---|
| `vulnerabilities.source_file_id` → `scan_files` | **RESTRICT** | 文件是漏洞的**证据**。删掉证据却留着结论，清单就变成一堆无法核对的条目 |
| `vuln_asset_links.vuln_id` / `.asset_id` | **CASCADE** | 关联是**派生数据**。漏洞没了，说它影响哪些资产就没有意义 |

RESTRICT 在接口层表现为 `409 FILE_IN_USE`，并给出 `?force=true` 这条**显式**通道：
强制删除会在同一事务里级联删掉该文件解析出的全部漏洞。前端不替用户做这个决定——
确认框里把「会连带删除 N 条漏洞」写在按钮上，让用户带着完整信息点。

> 注意与资产的对比：`vuln_asset_links.asset_id` 也是 CASCADE，意味着删掉一台资产
> 会顺手摘掉它的全部漏洞关联。这是对的（资产删除是「修正误录入」的语义，
> 且拦截「还有漏洞关联的资产」会让误录入根本无法清理），但要清楚它是有代价的。

## 3. 存储层 `internal/pkg/filestore`

只做四件事：**存、取、删、算出哈希**。不认识任何业务概念（没有"报告"、没有"漏洞"）。

### 3.1 落盘是「临时名 + rename」

```go
tmp := path.Join(dir, ".tmp-"+randomHex())
f, _ := os.Create(tmp)
io.Copy(io.MultiWriter(f, hasher), io.LimitReader(r, maxBytes+1))
os.Rename(tmp, final)
```

直接写目标路径的问题：进程在写一半时被杀、或磁盘写满，都会留下一个**半截文件**。
它的大小是真实的、路径是合法的、数据库记录也可能已经建好——直到有人去解析它，
才报一个「格式损坏」的错，而真实原因是几小时前的一次写入中断。

`rename` 在同一文件系统内是原子的：要么看到完整的文件，要么什么都看不到。
临时名以 `.tmp-` 开头，万一有残留也一眼能认出来是垃圾。

### 3.2 单次遍历同时算哈希与落盘

`io.MultiWriter(tmp, hasher)` 让一份数据只从网络流过一次。分两趟读
（先存盘、再读盘算哈希）在 10 MB 的报告上没什么感觉，但它把一个
「上传耗时 = 2 × 文件大小 / 带宽」的常数写进了实现里，没有收益。

### 3.3 超限即清理

`io.LimitReader(r, maxBytes+1)` 多读 1 字节，用来区分「正好等于上限」
与「超过上限」——只读到 `maxBytes` 的话两者无法区分。超限时**删掉临时文件**
再返回错误（`filestore.ErrTooLarge`）。

不清理的话，攻击者可以用「每次上传一个 100 MB 的垃圾文件」把磁盘填满——
请求全部被拒，但拒的是「这次上传」而不是「已落盘的垃圾」。守门脚本专门断言了
「被拒的上传没有留下残留文件」。

### 3.4 `resolve()` 双重穿越检查

`Open` / `Remove` 都先把相对路径拼成绝对路径，再校验结果仍在 `root` 之内，
并且**拒绝含 `..` 或绝对路径的入参**。

为什么是双重：只检查拼出来的路径是否以 root 开头，会被 `root/../../etc/passwd`
这类输入绕过（前缀仍然匹配）；只检查入参则绕不过符号链接。
两道一起上，路径穿越在这层就不可能发生——虽然路径本身由我们生成（随机十六进制），
但「不会有人传恶意路径」是一个假设，而防御性检查的成本是四行代码。

### 3.5 `Remove` 是幂等的

删一个不存在的文件返回 `nil`。理由：删除的调用点都在错误处理路径上
（上传校验失败要清理刚落盘的临时文件），那里我们希望「尽力清理，别把真正的
错误盖掉」。删不掉一个本来就不存在的文件，不是需要上报的异常。

单测 6 项覆盖：往返读写、超限不留垃圾、穿越拒绝、文件缺失、幂等删除、
不同内容不同哈希（`filestore_test.go`）。

## 4. 上传：三重校验

**顺序即报错优先级**：扩展名 → MIME → 魔数，从「最容易被用户理解」排到「最权威」。

| 道次 | 判据 | 失败表现 |
|---|---|---|
| 1. 扩展名 | 白名单 `.nessus` / `.xml` / `.xlsx` / `.csv` | `400 FILE_TYPE_REJECTED`，提示「不支持的文件类型」 |
| 2. MIME | 白名单（宽松：`application/octet-stream`、空串都放行） | 同上 |
| 3. **魔数** | 内容必须与扩展名声明的大类一致 | 同上，提示「内容与扩展名不符」 |

### 4.1 为什么这个顺序

第 1 道最容易说清楚（用户改个后缀就行），第 3 道最权威（内容无法伪造到
「既是 PK 又是 XML」）。把最权威的放前面也能工作，但错误信息会变成
「文件内容与声明不符」——而用户最需要的恰恰是先从最简单的可能性开始排除。

第 3 道是**真正的闸门**：它挡的是「改后缀伪装」。webshell 类攻击、
以及把 `.xlsx` 改名成 `.csv` 想绕过解析器的行为，都在这里被拒。

### 4.2 魔数规则

| 声明 | 判据 | 实现 |
|---|---|---|
| `.xlsx` | 前 4 字节 = `PK\x03\x04`（zip 头） | 读文件头比对 |
| `.nessus` / `.xml` | 跳过 BOM 与空白后首字符 = `<` | `validateMagic` |
| `.csv` | 无 `NUL` 字节（文本文件判据） | 扫头部 |

MIME 白名单刻意宽松（`application/octet-stream` 与空串都在里面）：浏览器的
MIME 上报五花八门，xlsx 常被报成 `application/octet-stream`，某些客户端
干脆不发。把第 2 道设成严格白名单的结果是「合法报告被拒」，而不是「更安全」——
因为真正的判定在第 3 道。

### 4.3 哈希去重是幂等的

```
落盘 → 算哈希 → 查 sha256
  命中 → 删掉刚落的盘，返回已有记录 + duplicate=true
  未命中 → 三重校验 → 嗅探格式 → 建记录
```

两个细节：

1. **先查再删**，顺序不能反。反过来的话，在「删掉新文件」与「查到已有记录」
   之间有一个窗口，此刻同一份内容在系统里没有任何实体。
2. 审计分两条动作：`file.upload` 与 `file.upload_duplicate`。合并成一条的话，
   「这份报告被谁传过几次」就答不上来了——而那正是安全审计会问的问题。

### 4.4 体积上限

单文件 10 MB（`SR_STORAGE_MAX_FILE_BYTES`，默认 `10 << 20`）。两道闸：

- handler 先看 `Content-Length > 上限 + 1 MB` → 直接 `413 FILE_TOO_LARGE`，
  一个字节都不读
- 再看不行就 `http.MaxBytesReader` 兜住分块传输（`Content-Length` 可以撒谎）
- 最后 filestore 的 `LimitReader` 兜住前两道的漏（服务层被非 HTTP 调用时）

## 5. 解析器接口化

### 5.1 接口

```go
type Parser interface {
    Format() ScanFileFormat      // nessus / openvas / excel
    Detect(data []byte) bool     // 只做前缀嗅探，不做完整解析
    Parse(data []byte) (*ParseResult, error)
}
```

`Detect` **刻意不做完整解析**：判定阶段要按顺序问每一个解析器「这是你的格式吗」，
如果 `Detect` 内部做完整解析，一份 10 MB 的 Nessus 报告会被 XML 解析器与
表格解析器各解析一遍。因此 `Detect` 只看前缀（根元素名 / 魔数），
真正的解析只发生一次。

判定顺序：**Nessus（根元素 `NessusClientData_v2`）→ OpenVAS（根元素 `report`）
→ Excel（PK 魔数或首字符非 `<`）**。

顺序是有意的：Nessus 与 OpenVAS 都是 XML，但根元素不同，先判具体的；
Excel 兜底接住「不是 XML 的表格文本」。

```go
func Parse(data []byte) (*ParseResult, error)  // 按 Detect 顺序认领
func DetectFormat(data []byte) ScanFileFormat   // 上传时只用它嗅探展示用的格式
```

### 5.2 三实现要点

**Nessus（`nessus.go`）**

- 路径：`NessusClientData_v2 > Report > ReportHost > ReportItem`
- 主机 IP 取 `HostProperties > tag[name=HOST]`，**不取 `ReportHost.name`**：
  部分 Nessus 版本把 UUID 写在 `name` 属性上，直接信它会让自动关联挂到
  一个不存在的「IP」上（表现为全部未匹配，且看不出为什么）
- `port="0"` + `svc_name="general"` = 与端口无关 → 端口与 service 一起清空
- `<description>` 常带 CDATA，由 `encoding/xml` 的 chardata 声明自然处理
- CVE 规范化：大写 + 去重

**OpenVAS（`openvas.go`）**

- 路径：`report > results > result`
- `port` 形如 `443/tcp`、`general/tcp` → 拆成端口与协议（`general` → 端口为 `NULL`，
  协议 `tcp` 保留）
- `host` 可能是 `10.0.0.5 (db-01)` → **只取 IP**。把别名一起存进 `host_ip`，
  自动关联会永远匹配不上（资产表里的 `ip_address` 是纯 IP），而且是静默的
- `severity = -1.0`（QOD 不可判）→ 按信息级处理，**不报错**：这份报告本身没问题，
  扫描器只是无法判断

**Excel / CSV（`excel.go`）**

- 复用 P2 的 `pkg/spreadsheet`：魔数嗅探、GBK 回退、行号保真
- 只有「漏洞名称」是必需列（其余留空按缺省处理）。缺必需列 → `MissingColumns`
  非空，此时其它字段无意义
- 行级错误带 `Row`（**源文件行号，含表头、从 1 开始**）、`Column`、`Value`、`Message`，
  最多列 200 条（超出的只计数）
- `severity` 列：1–5 整数当等级、含小数点当 CVSS 分值、其它当等级词
- 模板下载（`GET /api/parser/template`）：静态 xlsx，把「漏洞名称 / CVE编号 / 端口」
  三列设成文本格式，防 Excel 把 `1E5` 之类的编号静默改写

### 5.3 severity 换算：两条线

```
有 CVSS 分值（Nessus 的 cvss_base_score / OpenVAS 的 severity / 表格里的小数）
  → ≥9 → 5；≥7 → 4；≥4 → 3；>0 → 2；=0 → 1
无 CVSS，看等级词
  → Critical/严重/危急 → 5；High/高危/高 → 4；Medium/中/中危 → 3；
    Low/低/低危 → 2；Info/信息/提示 → 1
两者都没有 → 默认 3（中）
```

**CVSS 优先于等级属性**：CVSS 是客观数值，等级属性是扫描器的档位判断。
证据：Nessus 报告里同一个条目可能写着 `severity="3"` 而 `cvss_base_score="8.1"`——
以 CVSS 为准得到 4 级，以属性为准得到 3 级，守门脚本专门断言了这条
（期望 4，而不是属性里那个有欺骗性的 3）。

**等级词表必须对称**：`中危` / `低危` 在表里，`高危` 却漏了——这是 P3 守门脚本
抓到的一处真缺陷。漏掉的后果**不是报错而是静默降级**：整表按默认「中危」入库，
高危漏洞被系统性低估，且界面上没有任何提示。现已补齐 `高危` / `危急`，
并在代码注释里写明「对称性在查表里就是正确性」。

### 5.4 规模上限

`MaxVulns = 5000`。读取时用 `MaxVulns + 1` 作为上限去读，用**多读的一行**
区分「正好 5000 条」与「超过 5000 条」——只读到 5000 的话两者无法区分，
只能报一个「可能超限」的模糊错误。超过 → `400 VULN_IMPORT_TOO_MANY_ROWS`。

## 6. 两阶段解析

### 6.1 为什么分成 preview 与 commit

预览阶段要回答的事，与入库需要的事**不一样**：用户要先看到「这份报告能解析出
多少条、有多少能被自动挂上资产、有没有不合格的行」，再决定是否入库。

把所有问题都推迟到 commit，用户会先经历一次「部分写入 + 报错」，然后自己猜
哪里错了；把所有判断都放在前端，就得在前端重写一遍解析器。

| 阶段 | 端点 | 写数据 | 改 `parse_status` | 审计 |
|---|---|---|---|---|
| 预览 | `POST /api/parser/preview` | **否** | **否** | **无**（`MarkAuditSkipped`） |
| 提交 | `POST /api/parser/commit` | 是 | 是 | `file.parse` |

预览**可以反复调用**（比如先补了几条资产再看匹配情况会不会变好），
因为它读而写。守门脚本断言了「预览不写漏洞、不改状态、不产生审计」三条。

两个端点共用同一段 `parseFile`，**入参只有 `file_id`**。

### 6.2 铁律：commit 重新解析，不复用预览结果

服务端**不持有解析会话状态**。预览结果是一张快照，commit 必须重新解析重新校验。

不这么做的话会遇到：用户 A 预览 → （5 分钟）→ 另一台机器把资产删了 →
用户 A 点提交 → 写进去一份基于过期事实的关联。重新解析恰好能让「期间新上线的
资产」参与匹配，这是正向收益。

前端因此**不能**把 preview 的对象当作 commit 的入参传回来——这也是
`api/files.ts` 里 `commitParse(fileId)` 只接受 ID 的原因。

### 6.3 原子性

任一行不合格 → **一条都不写**。Excel 路径下错误行为 `ErrorRows > 0` 时返回
`409 VULN_HAS_ERRORS`，响应体的 `data` 里挂着**完整的预览结果**，前端因此可以
渲染出与预览阶段一模一样的错误表，而不是只弹一句「解析失败」。

### 6.4 并发 commit 的裁决：`MarkParsed` 先行

```go
rows := tx.ScanFile.MarkParsed(ctx, fileID, format, count)   // WHERE parse_status = 'unparsed'
if rows == 0 { return errFileAlreadyParsed() }               // 输家：在写数据之前退出
// 赢家继续：写漏洞 → 建自动关联
```

条件更新把「谁赢」这件事交给数据库裁决，不需要分布式锁。关键是它**放在写漏洞之前**：
放在后面的话，输家会先写一批漏洞，再发现自己是输家，然后靠事务回滚把它们撤掉——
同样正确，但白写一遍数据，且回滚失败的代价是脏数据。

守门脚本的第二条 commit 因此必须得到 `409 FILE_ALREADY_PARSED`。

### 6.5 解析失败要留痕

`parseFile` 失败（格式认不出、0 条、超限、破损 XML）时把文件标成 `failed` 并打
**WARN** 日志。不标的话，用户在列表里看到的还是「未解析」，会反复点解析；
标成 `parsed` 更糟——那等于谎报成功。

WARN 而不是 ERROR：报告本身不合格是**用户的输入问题**，不是系统故障。

## 7. 资产关联

### 7.1 自动关联：只按精确 IP

commit 时把解析出的 `host_ip` 去重后批量查 `assets.ip_address`，命中就建
`matched_by = 'auto'` 的链接。

三个刻意的选择：

1. **只做精确匹配，不做网段猜测**。看到 `192.168.1.10` 就去挂 `192.168.1.0/24` 里的
   资产，在 NAT、多网卡、多环境共存时会把漏洞挂到完全无关的机器上——
   而这类错误在界面上「看起来是对的」（关联数还更多）。
2. **同 IP 的多台资产全部挂上**：一条漏洞确实同时影响绑定同一 IP 的多个资产。
3. **未匹配的 IP 不阻塞 commit**，只作为 `unmatched_ips` 提示返回。
   「先传报告、后补资产」是完全正常的顺序，把它设成硬门槛等于逼用户先整理台账。

### 7.2 匹配口径必须与 commit 一致

`preview.matched_count` 与 `commit.linked_auto` **都是漏洞条数**，不是 IP 个数。

P3 守门脚本抓到过这里的口径分裂：预览按「匹配上的 IP 个数」计数（2），
commit 按「关联成功的漏洞条数」计数（4）。同一个文件在界面上显示
「可关联 2」，点提交后被告知「自动关联 4 条」——用户只会认为哪里算错了。
现已统一为条数，脚本里加了一条断言把这个等式钉死。

### 7.3 手动关联：整体替换，且不动自动关联

```
PUT /api/vulnerabilities/{id}/assets   { asset_ids: [12, 34] }
```

- `asset_ids` 是**最终状态**，不是增量。传空数组 = 清空全部手动关联。
  增量语义（add / remove 两个列表）在两端同时保存时会产生合并冲突，
  而整体替换让前端只需「取详情 → 改 → 整体提交」
- 只影响 `matched_by = 'manual'` 的行：`DeleteManualLinks` 的 WHERE 里带着这个条件
- 存在性校验（不存在的 ID → `404 ASSET_NOT_FOUND`）、去重、上限 100

**手动操作无权覆盖解析结果**：自动关联是「报告说了什么」的事实，
只能随文件删除一起消失；人工不能通过一次编辑把它抹掉。

前端因此必须**只把 manual 的 ID 填进选择框**（`detail.assets.filter(a => a.matched_by === 'manual')`），
把全部资产（含 auto）原样提交会把「解析器匹配上的」误标成「人手工挂的」。

### 8.1 端口与路径

| 方法 | 路径 | 权限 | CSRF | 审计 |
|---|---|---|---|---|
| POST | `/api/files/upload` | `file:write` | 是 | `file.upload` / `file.upload_duplicate` |
| GET | `/api/files` | `file:read` | 否 | — |
| GET | `/api/files/{id}` | `file:read` | 否 | — |
| GET | `/api/files/{id}/download` | `file:read` | 否 | — |
| DELETE | `/api/files/{id}?force=` | `file:write` | 是 | `file.delete` |
| GET | `/api/parser/template` | `file:write` | 否 | — |
| POST | `/api/parser/preview` | `file:write` | 是 | 无（设计如此） |
| POST | `/api/parser/commit` | `file:write` | 是 | `file.parse` |
| GET | `/api/vulnerabilities` | `vulnerability:read` | 否 | — |
| POST | `/api/vulnerabilities` | `vulnerability:write` | 是 | `vuln.create` |
| GET | `/api/vulnerabilities/{id}` | `vulnerability:read` | 否 | — |
| PATCH | `/api/vulnerabilities/{id}` | `vulnerability:write` | 是 | `vuln.update` |
| DELETE | `/api/vulnerabilities/{id}` | `vulnerability:write` | 是 | `vuln.delete` |

共 **14 个操作 / 9 条路径**。权限码**无需新增**：`file:*` 与 `vulnerability:*`
在 P1 就预置在 `internal/auth/rbac.go` 里了（assessor 两者可写，
auditor 由 `readOnlyPermissions()` 派生为只读）。模板下载挂在 `file:write`
而不是 `file:read`：只有要上传报告的人才需要模板。

### 8.2 状态码语义

| 码 | 何时 | 备注 |
|---|---|---|
| `400 FILE_TYPE_REJECTED` | 扩展名 / MIME / 魔数任一不过；**请求里没有 `file` 字段** | 后者也归这一类：「这次请求里没有可接受的文件」是同一件事 |
| `413 FILE_TOO_LARGE` | 超过 10 MB | |
| `415 FILE_FORMAT_UNKNOWN` | 通过校验但没有解析器认领 | 415 的本义（Unsupported Media Type） |
| `409 FILE_ALREADY_PARSED` | 重复 commit | |
| `409 FILE_IN_USE` | 文件仍有漏洞引用且未 `force` | |
| `409 VULN_HAS_ERRORS` | 有行级错误，整批未写，`data` 带完整预览 | |
| `404 FILE_NOT_FOUND` / `VULN_NOT_FOUND` / `ASSET_NOT_FOUND` | 资源不存在 | |

### 8.3 两个必须记得写的声明

审计中间件只认三种状态，handler 必须显式声明自己属于哪一种：

1. **写操作由中间件记录** —— 默认，无需声明
2. **写操作由服务层记录** → `reqctx.MarkAuditRecorded(c)`
   上传、解析提交、漏洞增删改、手动挂资产全部属于这一类：审计明细里要带
   文件名 / 条数 / 关联数，这些只有服务层知道
3. **必须用 POST 但不写任何数据** → `reqctx.MarkAuditSkipped(c)`
   只有 `parser/preview`：它用 POST 传 `file_id`，却按设计不产生审计

漏掉第 2 类声明不会让审计消失（服务层照常落库），但会在日志里打一条
「写操作既未由中间件记录、也未声明已由服务层落库」的 WARN。
**这正是 P3 守门脚本抓到的一处真缺陷**：`FileHandler.Upload` 漏了这个调用
（见 §12 第 2 条）——这类缺漏不会影响功能，只会把真正需要关注的告警淹掉。

## 10. 安全要点

| 面 | 做法 |
|---|---|
| 路径穿越 | 随机十六进制文件名 + `resolve()` 双重检查（§3.4） |
| 伪装文件 | 魔数校验，内容与扩展名不符以内容为准拒绝（§4.1） |
| 解析器 DoS | 10 MB 上限 + `MaxVulns = 5000` + 流式读取 |
| **XXE / 实体膨胀** | Go `encoding/xml` **不支持外部 DTD 实体**，天然免疫；配合体积上限挡住「十亿笑声」类膨胀 |
| 下载响应 | `application/octet-stream` + `attachment` + `X-Content-Type-Options: nosniff` 三件套：阻止浏览器按内容嗅探执行、强制下载而非内联渲染 |
| 越权 | 全部 14 个操作都挂 `RequirePermission`；守门脚本断言只读角色上传 / 解析 / 删文件 / 改关联全部 `403`，但**可以**下载与查看 |
| 磁盘占用 | 哈希去重（同一内容一份）+ 超限即清理 |
| 审计 | 8 个动作（`file.upload` / `file.upload_duplicate` / `file.delete` / `file.parse` / `vuln.create` / `vuln.update` / `vuln.delete` / `vuln.link`），明细带文件名与条数 |

## 11. 已知取舍

| 取舍 | 现状 | 若将来要改 |
|---|---|---|
| 同一文件重复解析会产生重复漏洞 | 靠「已解析的文件不给解析入口」+ 删后重传规避 | 加「按 `(source_file_id, title, host_ip, port)` 去重」或「重新解析 = 替换旧结果」语义；两者都要先想清楚人工编辑过的条目怎么办 |
| Nessus 的 `risk_factor` 在带 CVSS 时不入库 | `severity_raw` 只存定级依据（分值） | 若要两个都留，得加一列（`severity_raw` 的语义已经占用） |
| CVE 不建子表 | `LIKE` 查询足够 | 存量到百万级再加子表，届时需回填历史数据 |
| 不做漏洞生命周期 | 清单是「一次扫描的快照集合」 | P4 评估 / P6 整改会引入状态列，注意与手工录入的共存 |
| 上传内容不做病毒扫描 | 无 AV / 无沙箱 | 若准入生产，建议在存储前接一层扫描，或限制文件为纯文本格式 |
| `vuln_asset_links` 对资产是 CASCADE | 删资产会摘掉它的漏洞关联 | 若「资产退役」与「误录入修正」需要区分，应先给资产加软删除 |

## 12. 守门验证：`scripts/verify-file.sh`

**186 断言 / 14 节 / 隔离临时库 `sec_risk_file_e2e` / 端口 18084 / 上传目录也隔离**。

| 节 | 覆盖 |
|---|---|
| 5 | 三重校验（含两种伪扩展名、非白名单后缀、二进制垃圾）、哈希去重幂等、磁盘只留一份、被拒不留残留、413 |
| 6 | 预览只读：不改状态、不写漏洞、不产生审计、可反复预览 |
| 7 | Nessus 与 OpenVAS：条数、CVSS 优先、CVE 规范化、端口/协议/别名解析、`severity=-1.0` |
| 8 | Excel(CSV)：解析条数、未匹配 IP 不阻塞、来源三态与关联筛选 |
| 9 | 原子性与行号保真（错误定位到源文件第 3、4 行）、缺必需列、0 条、超 5000 条 |
| 10 | 500 条一次入库（**验收标志的规模侧**） |
| 11 | 手工录入（等级词映射）、三态 PATCH、关联整体替换与 auto 不被覆盖 |
| 12 | `FILE_IN_USE` → `force` 级联（4 条一起删）→ 删除后 404；下载逐字节一致 |
| 13 | 只读角色：可读可下载，上传 / 解析 / 删 / 改关联全部 403 |
| 14 | 8 个审计动作落库、明细含文件名与条数、日志无「未记录审计」告警、无 ERROR |

### 12.1 这一轮守门验证抓到的四个问题

写脚本的价值不在「跑通」，而在**它发现了什么**。P3 抓到 3 个真缺陷 + 1 处口径错误：

1. **【真缺陷】`VULN_IMPORT_MISSING_COLUMNS` 被错配成 `VULN_IMPORT_NO_ROWS`。**
   「表头少了一列」与「一行数据都没有」被同一个码表示，前端只能弹一句含糊的提示。
   已新增独立错误码（与 P2 的 `ASSET_IMPORT_MISSING_COLUMNS` 对称）。

2. **【真缺陷】上传接口漏声明「审计已由服务层落库」。**
   `FileHandler.Upload` 少了 `reqctx.MarkAuditRecorded(c)`，于是每次成功上传都会打一条
   「写操作未记录审计」的 WARN。审计本身没丢（服务层照常写），但这个告警一旦成为
   常态，「真的漏了审计」就被淹掉。**只有端到端脚本会看日志**，单测看不到。

3. **【真缺陷】预览与 commit 的匹配口径不一致。**
   预览按 IP 个数（2），commit 按漏洞条数（4）。用户会认为系统算错了。已统一为条数。

4. **【口径错误】等级词表缺「高危」。**
   中危 / 低危在表里，高危漏了 → 中文表格里的「高危」被静默降级为默认「中危」。
   这是**最危险的一类缺陷**：不报错、不告警，只是把高危漏洞系统性地低估。

> 这四条有一个共同点：**没有一条是单元测试能抓到的**。1 是错误码语义、
> 2 是日志、3 是跨阶段口径、4 是查表对称性——四者都要「把真实请求打进去、
> 把真实日志读出来」才看得见。这也是每个阶段都要配一个端到端脚本的原因。

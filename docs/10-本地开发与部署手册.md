## 1. 环境要求

| 依赖 | 版本 | 说明 |
|---|---|---|
| Go | 1.25.11+ | `go.mod` 声明的最低版本 |
| Node.js | ≥ 22.12.0 | 前端构建 |

## 2. 首次启动

```bash
# ① 生成 .env（从 .env.example 复制）
make setup

# ② 一条命令起全部服务（数据库 + 后端 + 前端热重载）
make dev
```

`make dev` 做的事（`scripts/dev.sh`）：

1. 检查 `.env` 是否存在，不存在则自动生成
2. 检查 Docker 守护进程是否运行
3. `docker compose up -d --build mysql docgen gotenberg`
4. **轮询等待 MySQL 就绪**（最多 120 秒）
5. 本地跑 Go 主服务，并把容器内地址映射回宿主机
6. **轮询等待 `/api/health` 返回 200**（最多 45 秒）
7. 首次运行会自动 `npm install`
8. 启动 Vite dev server（HMR）

`Ctrl-C` 退出时会自动清理后台的 Go 进程，不留僵尸。

启动完成后：

```
  前端界面   http://localhost:5173
  后端接口   http://127.0.0.1:8080/api/health
  样式验证页 http://localhost:5173/dev/style-check
```

> ⚠️ **`.env` 里禁止行尾注释。**
> `.env` 被 Makefile 直接 `-include`，行尾注释会被当成值的一部分读进去。
> 注释必须独占一行。

## 5. 环境变量

`.env.example` 是模板，`.env` 是实际生效的文件（已被 `.gitignore` 忽略）。

### 5.1 命名规则

后端配置的前缀是 `SR_`，点号替换为下划线：

```
database.host  →  SR_DATABASE_HOST
server.port    →  SR_SERVER_PORT
```

前缀 `SR_` 用来隔离命名空间，避免与 `PATH`、`HOME` 等系统变量
或同机其他服务的变量撞名。

### 5.2 配置来源优先级（高 → 低）

1. **进程环境变量**（容器 / CI 注入的）
2. **`.env` 文件** —— ⚠️ 只在进程环境中尚无该变量时生效，不覆盖已有值
3. 内置默认值

> 关键设计：`.env` 的定位是「把变量放进进程环境」的本地便利手段，
> **而不是一种配置格式**。这样本地开发与容器部署走的是**完全相同**的读取路径，
> 不会出现「本地正常、容器里配置读不到」这类问题。
>
> 曾经踩过的坑：早期用 viper 的 `SetConfigFile` 直接读 `.env`，
> 结果是环境变量名被转成小写（`sr_database_host`），无法映射到嵌套键
> `database.host`，所有配置静默回落到默认值（端口变成 3306，连接被拒 15 次）。
> 现在改用 `godotenv.Load()` 把变量放进进程环境，再由 viper 的 `AutomaticEnv` 读取。

### 5.3 主要变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `SR_APP_ENV` | `dev` | `dev` / `test` / `prod` |
| `SR_APP_LOG_LEVEL` | `info` | `debug` / `info` / `warn` / `error` |
| `SR_SERVER_HOST` | `127.0.0.1` | **安全默认值**；容器内需显式设 `0.0.0.0` |
| `SR_SERVER_PORT` | `8080` | — |
| `SR_SERVER_CORS_ORIGINS` | `http://localhost:5173,...` | 逗号分隔；生产必须显式配置 |
| `SR_DATABASE_HOST` | `127.0.0.1` | 本机开发连 docker 暴露的口 |
| `SR_DATABASE_PORT` | `13306` | ⚠️ 不是 3306 |
| `SR_DATABASE_USER` / `_PASSWORD` / `_NAME` | — | — |
| `SR_INTERNAL_SHARED_SECRET` | — | server → docgen 的共享密钥 |
| `SR_INTERNAL_DOCGEN_URL` | `http://127.0.0.1:8090` | 容器内为 `http://docgen:8090` |
| `MYSQL_ROOT_PASSWORD` | — | 仅 compose 初始化用 |
| `MYSQL_PORT` | `13306` | 宿主机映射端口 |
| `WEB_PORT` | `8000` | 前端容器端口 |
| `APP_VERSION` | `0.1.0` | 注入到二进制与前端 |

### 5.4 配置校验：不通过就拒绝启动

`server/internal/config/config.go` 会一次性列出全部问题
（而不是逐个试错）。生产环境（`SR_APP_ENV=prod`）额外强制：

- `database.password` 不能为空
- `internal.shared_secret` 长度 ≥ 16
- `server.cors_origins` 必须显式配置，不允许留空

> 带残缺配置启动的故障排查成本，远高于启动失败。

## 6. 全栈容器化运行

```bash
make up      # 构建并启动 5 个容器
# 访问 http://localhost:8000
make down    # 停止（保留数据卷）
```

### 6.1 服务拓扑

```
web (nginx :80) ──▶ server (Go :8080) ──▶ mysql (8.4)
                        ├──────────────▶ docgen (C# :8090)   ← 仅内网
                        └──────────────▶ gotenberg (:3000)  ← 仅内网
```

### 6.2 安全约定

- `docgen` 与 `gotenberg` 挂 `secrisk-internal` 网络（`internal: true`），
  **不声明 `ports`**，宿主机无法访问
- 两者都要求 `X-Internal-Secret` 请求头做二次校验
  （网络隔离挡不住同网络内被攻陷的其他容器）
- MySQL 端口**只绑 `127.0.0.1`**，局域网不可见
- 三个 Dockerfile 均以**非 root 用户**运行
- Nginx：`server_tokens off`、CSP、`/uploads/` 与 `/reports/` 直接 403

> ⚠️ **`docgen` 与 `gotenberg` 为什么"宿主机无法访问"很关键，别绕过它。**
> 本地要用真渲染（比如手动打一次 `curl` 试 docgen），正确的做法是在
> **内部网络里**执行（`make infra` 起上游后从 nginx / server 容器里打，或临时
> `docker run --rm --network secrisk-internal`），**不要**给它们加 `ports`。
>
> 加 `ports` 这件事有个极具误导性的失败模式，见 §9.2 倒数第二条：
> 只挂 `internal: true` 网络的服务加了 `ports`，Docker **不报错、不警告、
> 直接把它丢掉**——配置看起来完全正确、容器健康、`make dev` 也不报错，
> 只有点导出时才 503。

### 6.2.1 本地覆盖为什么用 `deploy/compose.dev.yml`

想在本地给 compose 加覆盖（比如临时把一个内部服务挂到宿主机调试），
**覆盖文件不能叫 `docker-compose.override.yml`**。

原因：compose 会**自动加载**这个名字的文件。一旦用了它，
「把内部服务端口暴露到宿主机」这条本地调试配置就会在 `make up`（生产语义）
时**一并生效**——而没有人会在 `make up` 时想到去看一眼一个叫 override 的文件。
这类配置一旦不小心提交，内部服务就长期挂在宿主机端口上了，而且**没有任何东西会报错**。

因此本地覆盖文件命名为 **`deploy/compose.dev.yml`**，它不会被自动加载，
必须显式叠加：

```bash
docker compose -f docker-compose.yml -f deploy/compose.dev.yml up -d
```

「必须显式 `-f`」本身就是一层防呆：本地调试是**有意为之**的动作，不是默认行为。

### 6.3 Nginx 的关键配置

| 项 | 值 | 原因 |
|---|---|---|
| `client_max_body_size` | `64m` | 与 gotenberg `--api-body-limit`、后端 limit 对齐 |
| `/assets/` | `expires 1y; immutable` | 文件名带 content hash |
| `/index.html` | `Cache-Control: no-store` | ⚠️ 否则发版后用户仍加载旧版 JS |
| `/uploads/`、`/reports/` | `deny all; return 403` | 绝不直接吐出文件，必须经后端鉴权（webshell 防线） |
| `/api/` | `proxy_buffering off` | 报告导出可能返回大文件，避免内存堆积 |
| `/api/` | `proxy_read_timeout` / `proxy_send_timeout` **200s** | 必须**大于**后端 `server.write_timeout`（180s），见 §6.5 |

### 6.4 上传与导出目录

compose 中以 volume 覆盖，**不放在镜像内**，便于备份与迁移：

```
./storage/uploads  →  /var/www/uploads
./storage/reports  →  /var/www/reports
```

`uploads` 内部再按月分层：`YYYYMM/<32 位十六进制>`（如 `202610/9f3c…`）。
**文件名与用户上传的文件名无关**（原文件名只存在数据库里，下载时回填），
所以「路径穿越」在结构上就不可能发生。本地开发的默认根目录是 `./storage/uploads`，
可用 `SR_STORAGE_UPLOAD_DIR` 覆盖——`verify-file.sh` 正是靠它把上传目录也指到临时目录，
避免验证过程在项目里留下样本文件。

> `./storage/reports` 是预留给后续阶段（P6+）「报告持久化」的目录。
> **P6 也没有用到它**——P6 的范围是整改跟踪与首页统计，纯数据面，
> 不产生任何文件。当前导出**不落盘**（D1 决策：流式返回，只留审计），
> 所以现在跑完 `make verify-report` 去看这个目录会**始终是空的**
> —— 那是符合预期的，不是导出失败。

### 6.5 三道超时闸：必须严格递增

报告导出是全系统最慢的一条链（Word 要起 .NET，PDF 要起 Chromium），
它同时被**三个**超时管着。这三个值必须**严格递增**，否则用户会看到错误的报错：

```
后端 server.write_timeout            180s
  < Nginx proxy_read/send_timeout    200s
    < 前端 axios timeout             210s
```

**为什么必须是这个顺序**：超时决定「谁先放弃」。若 Nginx 的 200s 小于后端的 180s，
那么当渲染真的卡住时，**先放弃的是 Nginx** —— 它直接掐断连接，后端那句
`503 REPORT_RENDER_FAILED`（或 `409 REPORT_NOT_CALCULATED`）就此躺在服务端送不出去。
用户看到的是「请求超时」，而系统日志里是一次正常的失败返回。
排查时两边对不上，是最费时间的一类问题。

反之，按上面的顺序，最内层先到时后端会**主动**写回一个带正确错误码的 JSON 响应，
Nginx 有 20s 余量把它转发出去，前端也还有 20s 余量把它读进来。

| 层 | 位置 | 值 |
|---|---|---|
| 后端写超时 | `config.go` `server.write_timeout` | 180s |
| Nginx | `deploy/nginx/default.conf` | 200s |
| 前端 axios | `web/src/api/reports.ts` `EXPORT_TIMEOUT_MS` | 210000 ms |

**改任一个都要三个一起看**，不要只改一处。后端 `config.go` 里那段注释
（`server.write_timeout` 上方）记着 180s 是怎么从「docgen 30s×2 + gotenberg 60s×2 = 120s」
加余量算出来的，改动时照着那个算法重新推一遍。

> 单次上游调用的超时另有配置：`SR_INTERNAL_DOCGEN_TIMEOUT`（默认 30s）与
> `SR_INTERNAL_GOTENBERG_TIMEOUT`（默认 60s）。它们与上面三道闸不是一回事
> —— 前者管「一次上游调用等多久」，后者管「整个 HTTP 请求可以活多久」。

## 7. 数据库

### 7.1 迁移

用 **golang-migrate**，刻意**不用** GORM 的 `AutoMigrate`：

- 迁移文件是 SQL（`server/migrations/*.sql`），可用 `//go:embed` 打包进二进制
- 主服务启动时自动执行迁移
- 也可单独执行：`make server-migrate`

当前迁移：

| 文件 | 内容 |
|---|---|
| `000001_init.up.sql` | 建 `system_configs` 表并写入 GB/T 20984 阈值种子数据（very_high 20 / high 12 / medium 6 / low 2） |
| `000001_init.down.sql` | 回滚 |

### 7.2 连接串要点

`Database.DSN()` 中带 `multiStatements=true` —— 这是 golang-migrate
执行含多语句的迁移文件所必需的。业务查询一律走 GORM 预编译语句，不受其影响。

### 7.3 备份

```bash
make db-backup
# 或自定义目录与保留天数
BACKUP_DIR=/data/backups RETENTION_DAYS=30 bash scripts/db-backup.sh
```

- 用 `--single-transaction` 保证 InnoDB 一致性快照，**不锁表**
- gzip 压缩，文件名带时间戳：`sec_risk-20261010-163000.sql.gz`
- 自动清理超过保留天数（默认 14 天）的旧备份

## 8. 守门验证

**改动相关代码后必须重跑。** 本节 8.1 起是 P0 建立的样式与构建产物断言；
P1 / P2 / P3 / P4 / P5 / P6 陆续补上了 `make verify-auth`（后端认证授权，74 项）、
`make verify-asset`（资产与字典，182 项）、`make verify-file`（上传与解析，188 项）、
`make verify-assess`（风险评估引擎，**227 项**）、
`make verify-report`（报告导出，**149 项**）、
`make verify-remediate`（整改跟踪与仪表盘，**333 项**），六者也在此列。

**共同的隔离约定**：所有 verify 脚本都**不碰开发库** —— 各自建一个隔离临时库、
把服务指过去，退出时整体 `DROP`（`trap cleanup EXIT`，另挂 INT/TERM 兜底，
Ctrl-C 也收干净）：

| 脚本 | 临时库 | 端口 |
|---|---|---|
| `verify-style-check.sh` | `sec_risk_style_e2e` | 18083（API）/ 5174（dev server） |
| `verify-auth.sh` | `sec_risk_auth_e2e` | 18081 |
| `verify-web.sh` | `sec_risk_e2e` | 18082（API）/ 4173（前端预览） |
| `verify-asset.sh` | `sec_risk_asset_e2e` | 18080 |
| `verify-file.sh` | `sec_risk_file_e2e` | 18084；另把 `SR_STORAGE_UPLOAD_DIR` 指向 `/tmp/sr-file-uploads` |
| `verify-assess.sh` | `sec_risk_assess_e2e` | 18085 |
| `verify-report.sh` | `sec_risk_report_e2e` | 18086 |
| `verify-remediate.sh` | `sec_risk_remediate_e2e` | 18087 |

⚠️ `verify-file.sh` 是唯一会**在磁盘上真的写出文件**的脚本。只隔离数据库是不够的：
删掉临时库的 `scan_files` 行不会删掉磁盘上的文件，所以上传目录必须一起指走并在退出时清理。
（`verify-report.sh` **不落盘**：报告导出按设计是流式返回、不写 `storage/reports`
——见 `docs/12` §2 的 D1 决策，产物只在内存里过一遍。）

⚠️ `verify-assess.sh` 的预期值**不复用后端代码**：它用 bash 整数运算照着
`riskengine.Compute` 的定点截断序列重抄一遍（`rmilli()`），再逐条比对。
不要"优化"成调后端接口取期望值——那样就成了自己证明自己（见 `docs/11` §12.1）。
它还会**直查 MySQL** 做「界面值 = 落库值 = 报告值」的三方比对，所以必须能连到临时库。
`verify-report.sh` 的同名比对（它做的是**五方**：落库 / 界面 / export-data / docx / xlsx）
也直查 MySQL，且**必须带 `--default-character-set=utf8mb4`**，
理由见 §9.2 的最后一条。
`verify-remediate.sh` 同样直查 MySQL，但它比的是**时间语义**而不是数值：
把「已逾期 / 即将到期 / 正常」三档分别与一条**独立写的 SQL** 对账，
再把仪表盘的逾期数与整改列表页 `?overdue=true` 的条数对账
——两处若用了不同的「今天」，这个断言会立刻炸（见 §8.5 与 `docs/13` §6）。

端口全部避开 8080 与 5173（dev server 占用的两个端口）：脚本启动前会清掉端口
占用者（防止断言打在残留的旧进程上），占着 dev server 的端口就会把它一并杀掉。

### 8.5 整改跟踪与仪表盘

```bash
make verify-remediate      # 或 bash scripts/verify-remediate.sh
```

**不需要 `make infra` 也能跑**：P6 是纯数据面（整改单 + 状态流转 + 首页统计），
全程不碰 docgen 与 gotenberg，所以没有 §8.4 那道上游可达性探测与降级矩阵
（`verify-report.sh` 是六个端到端脚本里唯一需要渲染上游的）。
隔离库 `sec_risk_remediate_e2e` + 端口 18087，其余约定与其它脚本一致。

它存在的理由是一条**静默失败**风险：P4 的风险引擎是「先清后写」，
每重算一次 `risk_items.id` 就**整批换新**。如果整改单的外键指向 `risk_item_id`，
一次重算就能让所有单子断链而**没有任何报错**。所以脚本第 5 节会**真的重算一次**，
然后拿同一张单子问四个问题：

```
✅ 重算后：旧风险项 id 已不存在（出处失效）
✅ 重算后快照 asset_name 完好
✅ 重算后：单子从列表页仍可查到、状态与期限未变
✅ 库里存在 2 张「出处已失效但单子完好」的整改单（设计如此）
```

最后一条是**反向对照**：它先直查 SQL 确认库里真有 `risk_item_id` 已指向不存在行的单子，
再确认这些单子在界面上一切正常。把「设计意图」变成了「可观测事实」——
否则「快照列起作用了」这句话在测试里是没有任何痕迹的。

14 节（0–13 + 汇总）/ 333 断言的覆盖面：

| 节 | 内容 |
|---|---|
| 0–2 | 环境准备、登录、造数（6 台资产 × 3 个漏洞，`T=1` 使 `R = 重要性 × 严重程度` 恰好铺满五档） |
| 3 | 建单：快照回填、初始态、`transitions` 投影 |
| 4 | 唯一性 `(asset_id, vuln_id)`：二次建单 409、`active_key` 实测值、闭环后变 `NULL`、闭环后可再建 |
| 5 | **重算不断链**：旧 id 消失 / 单子仍在 / 快照五列完好 / 出处原样保留 / 反向对照 |
| 6 | 状态机：九条边逐条走通、非法流转拒绝、必填说明、终态无出边（打回记 `from_status`/`to_status`） |
| 7 | 逾期：三档（已逾期 / 今天到期算即将到期 / `NULL` 永不算）+ 闭环归零 + 与直查 SQL 对账 |
| 8 | 批量建单：命中 / 新建 / 跳过（第二次 `created=0 / skipped=3`）、500 上限、草稿评估 409 `_BATCH_EMPTY` |
| 9 | 删除限制（只有 `pending` 且从未流转可删；两个 409 文案都给出替代动作） |
| 10 | 列表筛选与三态字段（`overdue` / `due_soon` / 正常），含 `status` 与 `active` 同时给出的优先级 |
| 11 | 权限：匿名 401 / CSRF 403 / 审计员只读 / 评估员可写（四象限） |
| 12 | 仪表盘：口径绑定（`assessments.latest`）、草稿全零、数字自洽、**与整改列表页跨页对账** |
| 13 | 审计与流转痕迹：5 个动作码 + `Detail` 明细对象 + 非法流转不留痕 + 无「未记录审计」告警 |

实测结果：**333/333**，约 1 分 28 秒（全系统最慢的 `verify-report.sh` 约 40 秒，
但这个脚本的请求数是它的一倍多）。

> 第 9 节有两条断言专门用来防「口径漂移」：一条把模糊状态集合
> （「未闭环」的 SQL 字面量）与列表页筛选条件对齐，另一条把仪表盘逾期数
> 与列表页 `?overdue=true` 对齐。这两个数字在实现里来自**不同代码路径**，
> 只有「今天」是同一个来源时才可能相等——把这条写成断言，
> 比在文档里写「注意保持一致」有用得多。

## 9. 故障排查

### 9.1 通用

| 现象 | 原因与处理 |
|---|---|
| `make doctor` 报 Docker 未运行 | 启动 Docker Desktop |
| `make dev` 卡在「等待 MySQL 就绪」 | MySQL 首次初始化较慢（需建库建用户）；通常 30 秒内完成。超过 2 分钟看 `docker compose logs mysql` |
| 端口 13306 / 8000 / 8080 / 5173 被占用 | `make doctor` 会列出占用情况 |
| 后端连接被拒、配置像是没生效 | 检查 `.env` 是否有**行尾注释**（会被 make 读进值里） |
| `curl` 本机地址返回 502 或超时 | 代理环境变量作祟，加 `--noproxy '*'` |

### 9.2 本项目实际踩过的坑（记录以便快速复现排查）

| 现象 | 根因 | 处理 |
|---|---|---|
| npm 安装报 `EACCES`（`~/.npm/_cacache`） | 受限环境下 home 目录不可写 | 指定 `--cache ../.npm-cache` |
| `docker compose build` 报 `operation not permitted` | `~/.docker/buildx` 不可写 | Makefile 中 `export BUILDX_CONFIG := $(ROOT)/.buildx` |
| `make help` 报 `grep: bad regex` | 受限环境的 `grep` 是 toybox，不支持 GNU ERE 的 `[...]+` | `help` 目标改用 `awk` 实现 |
| 脚本报 `DOCX（: unbound variable` | UTF-8 locale 下 bash 会把紧跟变量的中文字符合进变量名 | 变量后接非 ASCII 字符时统一写 `${VAR}` |
| `verify-docgen.sh` 断言 `w:space` 失败 | 属性实际是 `xml:space`（xml 命名空间，不是 w） | 修正断言 |
| 无头 Chrome 加载页面后一直不退出 | `--headless=new` 打印/截图后不自动退出 | 轮询到预期输出后 `kill -9`，并加 `cleanup` trap |
| 守门验证拿到 0/0 项断言 | 无头浏览器中 `requestAnimationFrame` 被节流甚至不触发 | 改用 `setTimeout(resolve, 200)`，并加重试 |
| ESLint 报 24 个「未定义变量」 | 扁平配置移除了 env 推导，未声明 `globals` | 按文件运行环境注入 `globals` |
| `format` 与 `lint` 来回推翻 | `eslint-plugin-vue` 的纯排版规则与 Prettier 冲突 | 铺 `eslint-config-prettier`，格式归 Prettier |
| **导出 Word / PDF 报 503，但容器里 `curl localhost:8090` 一切正常** | 给只挂 `internal: true` 网络的服务加了 `ports`，Docker **静默丢弃**了端口映射（`docker port` 为空、`docker ps` 的 PORTS 列为空，但**不报任何错**）。事后 `docker network connect` 补普通网络也补不回来——端口绑定在容器创建那一刻就定了 | 先让服务多挂一张非 internal 网络，**再**加 `ports`；见 `deploy/compose.dev.yml` 文件头与 §6.2.1 |
| **同一个坑会复发：`docker port secrisk-docgen` 输出为空，`make verify-report` 第 0 节直接失败** | 只要 docgen 容器被**重建**过一次而重建时没带 `-f deploy/compose.dev.yml`（例如手工 `docker compose up -d docgen`、`docker compose down` 后 `up`），端口映射就又丢了。`docker compose ps` 的 PORTS 列是唯一可靠的判据 | `make infra`（内部就是带 `-f` 的 `up -d --build`）；`make infra` 结尾的「渲染服务就绪」探测会顺带证实这一点 |
| **直查 MySQL 拿到的中文全是 `?`，逐条比对断言集体失败** | `docker compose exec mysql mysql` 的连接字符集默认是 **latin1**，中文在**读出来的时候**就变成了 `?`（库里数据其实是好的） | 每条命令都带 `--default-character-set=utf8mb4`。`verify-report.sh` 的 `sql()` 已统一带上 |
| 新建用户登录后调任何接口都 403 | 新建用户首次登录处于「必须改密」状态，业务请求一律 `AUTH_MUST_CHANGE_PASSWORD` | 断言权限前先走一次改密；写审计/权限断言时先确认账号已过改密 |
| 「未登录应 401」的断言实际拿到 403 | 匿名请求没带 CSRF 令牌时，**先**被 CSRF 中间件拦住，401 断言是"靠另一个原因碰巧通过" | 先给匿名会话取一次 CSRF 令牌，再发请求断言 401 |
| **一整节权限断言集体 403 `AUTH_CSRF_INVALID`，看起来像权限配置错了** | 脚本里 `login()` 每次登录都刷新同一个 `SESSION_CSRF` 变量，而请求工具函数恒用**管理员**会话 —— 创建完审计员账号后再发请求，就带上了审计员的令牌 | 管理员令牌单独存 `ADMIN_CSRF`，与「最后一次登录」的 `SESSION_CSRF` 分开维护。⚠️ 更危险的是：它会让「失败请求不留下审计」这类断言因为**请求根本没进业务层**而**假绿**——这类"因为另一个原因碰巧通过"的绿色比红色更难发现 |
| 断言「创建人显示名已回填」期望登录名却对不上 | `NamesByIDs` 优先返回 `display_name`，空才回退 `username`；引导管理员的显示名来自 `SR_AUTH_BOOTSTRAP_DISPLAY_NAME`（`.env` 里是「系统管理员」） | 从库里取真实显示名再断言（`SELECT IF(display_name = '', username, display_name) ...`），不要把这个假设写死进期望值 |
| 拼 `IN (...)` 的 SQL 报语法错，而 `sql()` 只返回空串 | 取 JSON 数组的辅助函数返回的是 Python repr（`[1, 2, 3]`），不是 SQL 的逗号串 | 单独写一个把数组转 `1,2,3` 的辅助函数，别拿通用取值函数硬拼 |

## 10. 生产部署注意事项

1. **必须替换全部默认密码与密钥**

   ```bash
   openssl rand -hex 32     # 用于 SR_INTERNAL_SHARED_SECRET
   ```

   `SR_INTERNAL_SHARED_SECRET` 与 docgen 的 `DOCGEN_INTERNAL_SECRET`
   必须是**同一个值**（compose 中两者都取自 `${SR_INTERNAL_SHARED_SECRET}`）。

2. **`SR_APP_ENV=prod`** —— 会启用额外配置校验，并把 Gin 切到 Release 模式。

3. **`SR_SERVER_CORS_ORIGINS` 必须显式配置**，生产下前端与 API 同源，
   正常不会触发 CORS，但不能留空。

4. **docgen 的密钥缺失会直接拒绝启动**（不是告警），
   这是刻意设计：一个忘记配密钥的 docgen 等于对内部网络完全敞开。

5. **`SR_SERVER_HOST` 在容器内必须是 `0.0.0.0`**，
   否则 Nginx 无法转发。默认值 `127.0.0.1` 是安全默认值，
   compose 中已显式覆盖。

6. **HTTPS 与证书**：当前 Nginx 配置监听 80。
   正式对外时应在前面再挂一层 TLS 终结（或在 Nginx 内配置证书），
   并同步更新 CSP 与 Cookie 的 `Secure` 属性。

7. **备份**：把 `make db-backup` 加进 crontab；
   `./storage/uploads` 与 `./storage/reports` 也要纳入备份范围。

8. **日志**：后端输出结构化 JSON（slog），docgen 输出 JSON 格式控制台日志，
   可直接接采集器。

## 1. 范围

**做**：把一次评估发现的风险项变成**可跟踪的工作项**（整改单），并在首页汇总全局状态。

具体包括四件事：

1. **整改单的建与改**：逐条建单（由风险项发起）、按评估 + 等级批量建单、改字段（标题/说明/结论/负责人/期限）；
2. **状态流转**：五个状态、九条合法边、三种必填说明、完整时间线；
3. **逾期**：三档时间态（已逾期 / 即将到期 / 未设期限）、列表筛选、首页计数；
4. **首页统计**：资产 / 漏洞 / 评估 / 整改四组数字，其中风险数字**绑定一个具体评估**并回传口径。

**不做**（见 §11）：整改任务的分派与提醒（站内消息、邮件）；历史逾期率；整改工时与成本；与工单系统（Jira / 禅道）的对接；附件上传。

## 2. 七项决策与理由

编号 D1–D7 在代码注释与 `docs/openapi.yaml` 中被直接引用，**改动实现时必须同步改这里的理由**，否则「为什么这么写」会失去唯一的落点。

### 2.1 D1 —— 整改单的业务身份是 `(asset_id, vuln_id)`，不是 `risk_item_id`

这是 P6 的头号陷阱，也是唯一一个「写错了功能全都正常、只在某个时刻静默损坏」的地方。

P4 的 `calculate` 是**先清后写**：一次重算会把该评估下的 `risk_items` 全删掉再重新插入，因此 **id 整批换新**（见 `docs/11` §2.1）。于是：

| 若整改单以 `risk_item_id` 为业务身份 | 后果 |
|---|---|
| 加了外键 | 重算的 `DELETE` 被 `RESTRICT` 拦住 → **评估再也重算不了**，而这在重算当场才暴露 |
| 没加外键，但展示依赖它 | 重算后单子仍在、指向的行已消失 → **没有任何报错**，详情页的「来源风险项」一栏只是空着 |
| 唯一性建在 `risk_item_id` 上 | 重算后同一条风险项可以再建一张单（新 id 不冲突）→ 同一个漏洞出现两张未闭环单 |

正确的读法是：**整改单回答的是「某台资产上的某个漏洞要修」这个业务问题**，它是业务事实，不该被「又算了一遍」改写。所以：

```go
AssetID uint64 `gorm:"column:asset_id"`   // 业务身份
VulnID  uint64 `gorm:"column:vuln_id"`    // 业务身份
AssessmentID *uint64  // 发现出处：只回答「哪次评估发现的」，允许失效
RiskItemID   *uint64  // 发现出处：重算后即失效，允许失效
```

四个 ID **都不建外键**（同 `000006` 约束 3 的手法）：删掉一条误录入的漏洞、删掉一次不再需要的评估，都不应该连带抹掉「有人承诺过要修它」这件事。

⚠️ 但**建单的入口**仍然是 `risk_item_id`，这不是矛盾 —— 见 §4.1。

### 2.2 D2 —— 「同一 (资产, 漏洞) 只允许一张未闭环单」用生成列 + 唯一索引表达

MySQL 没有部分索引（partial index），而应用层「先查后插」在并发下有竞态窗口（两个人同时点建单 → 两张单）。

做法是生成列：

```sql
`active_key` VARCHAR(64) GENERATED ALWAYS AS (
  IF(`status` IN ('pending', 'in_progress', 'resolved'),
     CONCAT(`asset_id`, ':', `vuln_id`), NULL)
) STORED,
UNIQUE KEY `uk_remediations_active` (`active_key`)
```

闭环（`closed` / `accepted`）后 `active_key` 变 `NULL`，而 MySQL 的唯一索引把**多个 NULL 视为互不相同**（这条规则 `000004` 与 `000006` 都踩过），于是：

- 「历史上同一对象反复整改过几次」不会互相冲突；
- 「同时存在两张未闭环单」被**数据库**直接拒绝。

实测（守门脚本第 4 节会重放）：重复插入报 `ERROR 1062 Duplicate entry '7:9' for key 'remediations.uk_remediations_active'`。

⚠️ **生成列只能引用在它之前定义的列**，因此 `active_key` 必须排在 `asset_id` / `vuln_id` / `status` 之后。这条在 MySQL 的报错里是 `Unknown column`，写迁移时极易踩。

服务层仍然保留一次 `ensureNoActiveTicket` 前置查询 —— 但它**不是防线**，只是把 `Duplicate entry '7:9'` 翻译成一句人话（`REMEDIATION_DUPLICATE_ACTIVE`）。真正的防线是那个唯一索引。

### 2.3 D3 —— 终态不可逆，漏洞复发时新建一张单

状态机里 `closed` 与 `accepted` **没有任何出边**。

理由有两层：

1. 业务上，「验证通过、已闭环」与「决定不修、接受风险」都是**结论**。结论可以被推翻，但那是一次新的决策，不是「回到上一步」—— 后者会把「曾经闭环过」这件事从状态里抹掉；
2. 实现上，闭环会把 `active_key` 置为 `NULL`。如果允许闭环后重新打开，就会出现「重新打开」与「唯一索引」争取同一把锁的诡异组合：同一时刻可能出现两张未闭环单，或者重新打开失败而用户不知道为什么。

漏洞复发（补丁被回滚、配置又改回去了）在业务上是**新的一件事**，应当新建一张单 —— 这也正是 D2 里 `active_key` 变 NULL 的用途。

### 2.4 D4 —— 逾期算出来，不落库

表里只有 `due_date DATE`，**没有 `overdue` 布尔列**。

若落一个布尔列，就需要一个每日定时任务去翻它。而任务一旦停跑（部署改了 cron、容器重启、时区变了），库里的数字就**静默变成错的** —— 没有任何地方会报警，用户看到的「逾期 3 条」可能是三天前算的。读的时候算，则永远是对的。

代价是每次查询都要比一次日期，这个代价可以忽略（有 `idx_remediations_status_due`）。

判定有三条，每条都有一个具体的错误答案：

| 规则 | 不这么做会怎样 |
|---|---|
| 只有**未闭环**才可能逾期 | 「历史上逾期过」会永远挂在指标上，逾期数只增不减 |
| `due_date` 与今天都**归一到零点**再比 | 今天到期的单子从今天 `00:00:01` 起就算逾期，而正确语义是「今天之内不算」 |
| 未设期限（`NULL`）**永远不算逾期** | 「没定 deadline」的单子全部涌进逾期数，这个指标直接作废 |

### 2.5 D5 —— 状态流转是一个独立端点，不是 PATCH 里的一个字段

```
PATCH /api/remediations/:id             改字段（标题/说明/结论/负责人/期限）
POST  /api/remediations/:id/transition  状态流转（含必填说明）
```

两者**不是同一件事**：前者改的是「这张单子长什么样」，后者改的是「这张单子走到哪一步了」。拆开的三个理由，每一个单独都够：

1. 流转有**额外的条件必填参数**（说明），塞进 PATCH 就得做条件必填；
2. 流转是**打回 / 闭环 / 风险接受**这类审计上必须能一眼筛出的动作，混进 `update` 之后审计页再也分不清「改了个期限」与「把单子打回了」；
3. 流转**写两张表**（单子 + 流转记录），PATCH 只写一张。

### 2.6 D6 —— 仪表盘的风险数字绑定一个具体评估，并把口径回传

同一个「很高风险有多少条」，在四种口径下能给出四个不同的数字：

| 口径 | 结果 |
|---|---|
| 全部评估累加 | 同一条风险项被重复计数（上周算过、这周又算过） |
| 每次评估取平均 | 数字没有业务含义 |
| 最近一次评估 | 需要一个明确的「最近」定义（`calculated_at` 还是 `id`？） |
| 某个指定评估 | 需要用户在界面上选 |

而界面上只写「很高 37 条」时，**没有任何人能从数字本身看出用的是哪种口径**。这是仪表盘最容易犯、也最难被发现的错误 —— 它不报错，只是让所有读数字的人基于不同的事实讨论。

因此 P6 采取两条硬约束：

1. **风险数字全部绑定一个具体评估**，并把那个评估的 ID / 名称 / 计算时间 / 状态一并回传（`assessments.latest`），**界面上必须显示**（`DashboardView.vue` 的口径 tag）；
2. 资产、漏洞、整改单是**全局当前态**，与评估无关，不受口径影响。

不传 `assessment_id` 时取「最近一次**已计算**」的评估（`calculated_at DESC, id DESC`）；库里一次都没算过时返回 `latest: nil`（合法的空场景，不是 500）。

### 2.7 D7 —— 只有「待处理且从未流转」的单子可以删

```go
if n, _ := s.repo.Remediation.CountTransitionLogs(ctx, id); n > 0 { → 409 }
if m.Status != model.RemediationPending { → 409 }
```

已经流转过的单子是**工作记录**，删掉它就等于抹掉「有人承诺过要修、后来又改了口」这个事实。而「改过负责人/期限」不算流转 —— 改错了负责人不该让单子变成删不掉的。

两个 409 的文案里都给出**替代动作**（流转为「风险接受」并写明理由），而不是只说「不允许」：用户遇到「不能删」时真正需要知道的是「那我该怎么做」。

## 3. 数据模型

### 3.1 两张表

见 `docs/02` §11 的完整 DDL 摘要。这里只记结构意图：

| 表 | 职责 | 关键点 |
|---|---|---|
| `remediations` | 整改单本体（业务事实） | 5 个索引 + 1 个生成列唯一索引；四个 ID 都无外键 |
| `remediation_logs` | 流转与变更记录（可追溯性的载体） | 唯一有外键的表：`ON DELETE CASCADE` |

`remediation_logs` **只对「自己的单子」建 CASCADE**，与 D1「ID 都不建外键」不矛盾：流转日志是单子的**派生数据**，主体没了它没有独立存在意义（同 `000006` 约束 5 对 `assessment_id` 的处理）。

`action` 有三个取值，**刻意把字段改动也记进同一张时间线**：

| action | 用途 | from/to |
|---|---|---|
| `create` | 建单 | `to_status` = 初始状态；`from_status` 空 |
| `update` | 改字段 | 都空；`note` 记「修改字段：title、due_date」 |
| `transition` | 状态流转 | 都有值 |

分成两张表（一张状态、一张字段）会让详情页的「那天到底发生了什么」需要拼两次查询，而时间线必须能按一次读下来。

排序键是 `(remediation_id, id)` 而不是 `(remediation_id, created_at)`：同一事务里写入的多条记录可能落在同一毫秒，时间戳相同时顺序不定，**而时间线必须有一个全序**。

### 3.2 三个必须永远一致的集合

「未闭环状态 = `pending` / `in_progress` / `resolved`」这个集合有**三个**落点：

| # | 落点 | 形式 |
|---|---|---|
| 1 | `remediations.active_key` 生成列 | SQL 字面量 `status IN ('pending','in_progress','resolved')` |
| 2 | 逾期与即将到期的判定 | `repository.RemediationCountOverdue` / `CountDueWithin` 的 `status IN ?` |
| 3 | `model.RemediationActiveStatuses` | Go 切片（列表筛选 `active=true`、`FindActiveByTarget`、`ActiveByTargets` 用它） |

第 1 处写在 SQL 里，**改 Go 代码改不到它**。三者分裂的后果是：

- 唯一索引认为某状态已闭环（`active_key` 变 NULL），而服务层仍认为它未闭环 → 同一目标可以再建一张单，且两张都是「未闭环」；
- 或者反过来 → 明明还没闭环却在逾期清单里消失。

因此 `model/remediation.go` 的注释、迁移 `000007` 的注释、本节都必须点出「这是同一个集合」。改动任何一处时，另两处同步。

### 3.3 快照列

| 列 | 用途 |
|---|---|
| `asset_name` / `asset_ip` | 资产改名或删除后，单子仍能说清「哪台机器」 |
| `vuln_title` / `vuln_cve_ids` | 同上，漏洞被删后仍能说清「修什么」 |
| `risk_level` / `risk_value_r` | **建单时刻**的等级与风险值 |

最后一组最容易被误解：「风险等级」在这里是**历史快照**，不是当前值。同一个漏洞在两次评估里可能因为重要性调整而从「高」变成「很高」，而整改单记录的是**当时为什么要开这张单**。列表页按 `risk_level` 筛选、仪表盘按等级统计整改情况，用的都是这个快照。

## 4. 服务层

### 4.1 建单为什么必须由 `risk_item_id` 发起

这与 D1「业务身份是 `(asset_id, vuln_id)`」看起来矛盾，其实不是：**身份**与**入口**是两件事。

`createRemediationInput` 只收 `RiskItemID`，理由是整改单必须有风险等级与风险值（见 §3.3），而**这两者只有风险项才有**。直接给 `asset_id + vuln_id` 建单看似更灵活，但那会造出「等级为空」的单子 —— 而仪表盘的「按等级统计整改」与列表页的「按等级筛逾期」都依赖它。一个可以合法为空的字段，迟早会变成一堆没人能解释的空格子。

于是数据流是：

```
risk_item_id  →  查出这条风险项（拿到 asset_id / vuln_id / 等级 / 风险值 / 名称）
              →  用 (asset_id, vuln_id) 作为业务身份落库
              →  risk_item_id 与 assessment_id 一起降级为「出处」
```

前端因此**看不到 `risk_item_id` 这个字段**：结果页的「建单」按钮直接把它带给后端（`CreateRemediationDialog` 的 prop），用户面对的是「对这条风险项建单」。

### 4.2 批量建单：命中 / 新建 / 跳过，与「幂等」刻意不同于单张

入参只有 `assessment_id` + `levels` + `due_in_days` + `assignee_id`，返回三个数字：

```json
{ "assessment_id": 2, "matched": 3, "created": 3, "skipped": 0, "ids": [11, 12, 13] }
```

| 场景 | 单张建单 | 批量建单 |
|---|---|---|
| 该 `(资产, 漏洞)` 已有未闭环单 | **409** `REMEDIATION_DUPLICATE_ACTIVE` | **跳过**（`skipped++`），整体仍 200 |

这个差异是**刻意的**。批量建单的典型用法是「算完一次评估，把高风险的都开一次单」，用户会在评估重算后再点一次 —— 若那时因为已有单子而整批失败，这个功能就没法用了。而单张建单是一个精确动作，重复就是用户搞错了，必须报错。

配套的三条设计：

1. **`levels` 为空退化为「很高 + 高」**：这是最常见用法的默认值，让用户每次都手写一遍等级筛选没有意义；
2. **非法等级报错而不是静默丢弃**：丢弃的话 `["very_high","HIGH"]` 会悄悄变成只对「很高」建单，用户拿到「创建了 3 张」的结果，却不知道「高」那一批为什么一条都没建；
3. **「先数后取」**：先用 `CountRiskItemsByLevels` 拿到精确条数，再决定是报超限还是照常执行。这样 400 的文案里能给出**准确数字**（「本次命中的风险项有 N 条，超过单次建单上限 500 条」），用户才知道该把条件收窄到什么程度。

上限取 500：按「很高 + 高」一次几百张已经是一个正常评估的量级；再大就说明用户漏选了等级，此时正确做法是报错让他收窄条件，而不是替他建出几千张没人会看的单子 —— 那些单子会把「逾期数」这个指标彻底废掉。

批量建出单子走**与单张相同的写入路径**（`createWithLog`）。复制一份「精简版」写入逻辑会让批量建出的单子缺少首条记录，表现为详情页时间线是空的 —— 而它只在批量这条路线上出现。

### 4.3 仪表盘不引入新的计算

`DashboardService` 是**只读的聚合服务**：不写库、不留审计（读操作本就不留）、不做任何风险计算。

所有风险数字直接取 P4 已落库的结果（`assessments.level_counts` / `max_risk` / `risk_items`）。理由与「风险计算只在后端实现」同源：一旦仪表盘自己算一遍，它就会成为**第二条计算路径** —— 而那正是 P4 花力气避免的东西（三处一致迟早会被改配置的操作打破）。

`total` / `active` 也不是另查两次 `COUNT(*)`，而是**由状态集合派生**：

```go
for _, st := range model.RemediationStatuses {
    n := counts[st]; byStatus[string(st)] = n; total += n
    if st.IsActive() { active += n }
}
```

「五状态之和」与「total」若分别查，两次查询之间的新单会让它们对不上，界面上表现为「加起来比总数少一张」—— 这是最难解释的一类不一致。

## 5. 状态机

### 5.1 五个状态与九条边

```
pending ──→ in_progress ──→ resolved ──→ closed     (终态)
   │             │  ↑            │  ↑         accepted (终态)
   ├──→ resolved ┘  └────────────┘  │
   └──→ accepted                    └──→ in_progress   ← 打回
```

`model/remediationTransitions` 是**全系统唯一的状态机定义**。service 的校验与 `transitions` 投影都由它派生，前端**不另写一份**。

为什么要五个状态而不是「待处理 / 已处理」两个：两个状态只能承载一次流转，而真正需要留痕的是另外两处 ——

- `resolved → in_progress`（**打回**）：验证不通过、重做。这是整改工作的核心监督动作，也是本表最重要的一条边；
- `* → accepted`（**风险接受**）：等保检查里的标准结论。若只有 `closed` 一个出口，「修好了」与「决定不修」在数据上就完全分不清了。

### 5.2 `noteRequired` 是唯一实现

```go
func noteRequired(from, to model.RemediationStatus) bool {
    if to == model.RemediationClosed || to == model.RemediationAccepted { return true }
    return from == model.RemediationResolved && to == model.RemediationInProgress
}
```

三种必填对应三类**结论性**动作：怎么修的（`→ closed`）、为什么不修（`→ accepted`）、为什么不通过（打回）。

⚠️ 这个函数同时被**校验**（`Transition` 返回 400）与**投影**（`transitionOptions` 给前端标必填）使用。这正是它必须是唯一实现的原因：若前端另写一份，就会出现「界面没标必填、提交后被 400 拒绝」。

进入终态时说明会**同时写入 `resolution`**：结论不该只躺在日志里，列表页要能直接显示「怎么解决的」。

### 5.3 `transitions` 是后端投影

`RemediationView.transitions` 由 `toRemediationView` 填充：

```json
"transitions": [
  { "to_status": "closed",      "note_required": true  },
  { "to_status": "in_progress", "note_required": true  },
  { "to_status": "accepted",    "note_required": true  }
]
```

前端遍历它渲染按钮。因此「界面允许但接口拒绝」在**结构上**不可能出现 —— 终态返回空数组，按钮自然消失，前端不需要判「是不是终态」。

## 6. 时间与逾期

### 6.1 「今天」只有一个来源

`RemediationListQuery.Today` 由 service 层注入并传给仓储。仓库层的 SQL 里**不用 `CURDATE()`**。

理由：那会让「今天」有两个来源（Go 进程时区 vs MySQL 会话时区）。两者不一致时，同一个单子在列表页与仪表盘上会一个「逾期」一个「不逾期」—— 而两个页面各自都自洽，只有对着看才发现对不上。

同理，`DashboardService.now` 与 `RemediationService.now` 是同一个注入点：仪表盘的「逾期 N 条」与列表页 `?overdue=true` 筛出来的条数**必须是同一个数**，各取各的时刻会在跨零点时对不上。守门脚本第 12 节直接断言这两个数字相等。

### 6.2 `daysBetween` 用 `AddDate` 逐日推进

```go
for cur := from; !cur.Equal(to); { cur = cur.AddDate(0, 0, step); days += step }
```

而不是 `to.Sub(from).Hours() / 24`：**夏令时切换那一天只有 23 小时**（或 25 小时），按小时折算会得到整整一天的偏差 —— 而偏差恰好落在「今天到期」与「昨天到期」之间，也就是逾期的判定边界上。

本系统按本机时区运行，不能假设没有夏令时。循环还带一个 ±36500 天的防御性上限，避免 `due_date` 被写成一个离谱年份时转圈。

### 6.3 三档时间态是三个字段

```go
Overdue     bool   // 已逾期
OverdueDays int    // 已逾期天数（未逾期时 0）
DueInDays   *int   // 剩余天数（0 = 今天到期；未设期限 / 已逾期时为 null）
```

「还有几天到期」与「已逾期几天」在语义上**互斥**：未逾期时看前者，逾期时看后者。合成一个有符号的字段（负号表示逾期）能少一个字段，代价是每个消费方都要记得那个符号约定 —— 一旦忘了，界面上就会出现「逾期 -3 天」。宁可多一个字段，也不要把约定藏在符号里。

⚠️ 已闭环的单子返回 `overdue=false / due_in_days=null`，**即使它曾经逾期过**。逾期是当前态，不是一个历史事实。「历史逾期率」需要落库才能算，本期不做（见 §11）。

### 6.4 逾期与即将到期是两个不重叠的区间

| 判定 | 区间 |
|---|---|
| 已逾期 | `due_date < 今天` |
| 即将到期 | `今天 ≤ due_date ≤ 今天 + 7`（**闭区间**，今天到期算即将到期） |

两个口径贴在**今天**的两侧，不能重叠。重叠的话同一个单子会在两个数字里各出现一次，而用户会以为有两张单子。守门脚本第 7 节用一条 SQL 断言两个集合的交集为空、并集等于各自之和。

## 7. 前端

### 7.1 三个「不在前端算」

| 不在前端做的事 | 由什么替代 |
|---|---|
| 状态机规则 | 遍历 `remediation.transitions` |
| 逾期判定 | 读 `overdue` / `overdue_days` / `due_in_days` 三个字段 |
| 风险等级判定 | 读 `risk_level` 字符串 |

第二条与第三条对应一条更普遍的原则（`docs/01` §2.6）：凡是「值」与「值的解释」分离的地方，解释一律在后端。

### 7.2 `vue-echarts` 的样式是 unlayered 的

`vue-echarts/style.css` 给 `x-vue-echarts` 补 `display:block; width/height:100%`。它**不受** `vite-plugin-css-layer` 的 `packages: ['element-plus']` 治理（那个插件只把 Element Plus 放进 `@layer el`），因此：

- 必须在组件里**显式** `import 'vue-echarts/style.css'`，否则自定义元素是 `inline`、图塌成 0 高度；
- **不能在 `<VChart>` 上加 `h-64` 这类工具类** —— 工具类进不了 `@layer`，而 unlayered 的规则优先级高于任何 `@layer`，所以它**永远不生效**。高度一律设在外层 `<div>` 的内联 `style` 上。

`HBarChart.vue` 还做了按需注册（`use([CanvasRenderer, BarChart, GridComponent, TooltipComponent])`），避免引入约 1MB 的全量包。

### 7.3 结果页的整改列

`AssessmentResultView.vue` 在风险项表格里插了一列「整改」，数据来自一次 `loadActiveRemediationMap()`：

- 拉全部未闭环单（`?active=true`，分页循环），按 `(asset_id, vuln_id)` 建索引；
- 有单 → 状态 tag，点击跳详情；无单 → 建单按钮（无 `remediation:write` 时显示「未建单」文字）；
- 条数超过 `maxPages` 时置 `truncated=true`，表格上方显示 `el-alert` **明确说明这一列可能把已有单子的条目显示成「未建单」**；
- 加载失败时静默降级为「全部未建单」，不阻塞风险项本身的展示。

### 7.4 负责人选择器与权限解耦

`AssigneeSelect.vue` 需要用户清单（`/api/users`）。而**评估员（assessor）能建单改单，却没有 `user:write`** —— 它在 `rolePermissions[RoleAssessor]` 里被有保留地给了 `PermUserRead`（理由写在 `rbac.go`：「为了在评估任务里选择负责人时能拉到候选列表」）。

即便如此，组件仍然处理「拉不到清单」的情况：把控件禁用并在下方**说明原因**，而不是留一个空下拉框让用户以为是数据问题。

## 8. 权限与审计

### 8.1 权限：无新增权限码

`remediation:read` / `remediation:write` 在 P1 的 `rbac.go` 就已预置（P1 的守门测试要求「每个权限码都必须被某个角色持有」）。因此 P6 不需要改权限注册表，只需要在路由上挂：

| 角色 | `remediation:read` | `remediation:write` | 说明 |
|---|---|---|---|
| admin | ✅ | ✅ | 全集 |
| assessor | ✅ | ✅ | 整改的执行者 |
| auditor | ✅ | ❌ | 由 `readOnlyPermissions()` 自动派生 |

仪表盘用**「任一权限即可」**：

```go
secured.GET("/dashboard/summary",
    guard.RequirePermission(auth.PermAssessRead, auth.PermAssetRead, auth.PermRemedRead),
    dashboardHandler.Summary)
```

越权风险由「区块内不含敏感字段」控制：它只返回计数与名称快照，不含任何评估内容、漏洞详情或用户信息。

### 8.2 五个审计动作码

| 动作码 | 触发 | 明细字段 |
|---|---|---|
| `remediation.create` | 逐条建单 | `asset_id` / `vuln_id` / `risk_item_id` / `risk_level` / `title` |
| `remediation.update` | 改字段 | `changed`（改了哪些列，已排序） |
| `remediation.transition` | 状态流转 | `from` / `to` / `note`（截断 200） |
| `remediation.delete` | 删单 | `asset_id` / `vuln_id` / `title` / `risk_level` |
| `remediation.batch_create` | 批量建单 | `assessment_id` / `levels` / `matched` / `created` / `skipped` |

三条设计说明：

1. **`transition` 与 `update` 必须分开**：前者是整改跟踪的主干动作，审计要能回答「这张单子是谁在什么时候从『已整改』打回成『整改中』的」。混在一个动作码里就得把 `detail` 的 JSON 全部读一遍才能筛出来。
2. **批量建单一次只留一条记录**：理由与 `asset.import` 完全相同 —— 一次可能产生几百张单，逐张留痕会把审计页冲成一个没法看的数据转储，而明细里的评估 ID 与三个数字已经足够追溯。
3. **失败的流转不留审计**：`Audit` 中间件对 `status ≥ 400` 的请求本就不落库，且 handler 只在成功路径调用 `reqctx.MarkAuditRecorded`。守门脚本第 13 节断言「非法流转前后 `remediation.transition` 的条数不变」—— 这条断言同时守住这两道。

⚠️ 五个动作码都走 **service 自行落库** 的路径（不是中间件 `WithAuditMark`），因为只有 service 层才拿得到「改了哪些字段」「从什么状态到什么状态」这类明细。因此每个 handler 在成功路径都必须调 `reqctx.MarkAuditRecorded(c)`，否则日志里会出现「写操作既未记录也未声明」的告警。**守门脚本断言这条告警不存在。**

## 9. 实现期对计划的修正

### 9.1 `status` 与 `active` 的优先级：注释与代码不符（守门脚本抓到的缺陷）

`RemediationHandler.List` 里原本写着「active 与 status 同时给时**以 active 为准**」，而代码是：

```go
if raw := c.Query("status"); raw != "" {
    status := raw
    q.Status = &status
    q.ActiveOnly = false   // ← 实际是「status 优先」
}
```

守门脚本第 10 节按注释的语义写了断言（`?status=accepted&active=true` 应返回未闭环数），实测返回 `accepted` 的条数，**把这条注释与代码的矛盾照了出来**。

最终判定：**保留代码行为（status 优先），修正注释**。理由：

- `status` 是元素级精确筛选，用户既然指名了一个状态，再叠一个集合级条件就是自相矛盾（`status=accepted` + `active=true` 没有交集）；
- 遇到矛盾条件时，无论保留哪一个都会让用户看到「不是他要的结果」而查不出原因，而 `status` 更精确，以它为准是可解释的规则；
- 前端也据此在选出状态后禁用「未闭环」开关，因此这个组合不会从界面产生，只有直接调接口才会遇到。

守门脚本的断言同步改为「结果等于只按 `status` 筛」，并在注释里写明：**改动 handler 时必须同步改这一条，否则它会静默变成一条描述相反行为的断言**。

### 9.2 批量建单对草稿评估返回 409 而不是 400

草稿任务没有任何风险项，最初的直觉是「400 参数不合法」。但用户真正需要知道的是「先去算一次」，而 `409 REMEDIATION_BATCH_EMPTY` 的文案能承载这个信息（错误码语义上对应「当前状态不允许」，正合适）。守门脚本按 409 断言。

### 9.3 前端类型：`Me` 类型的主键字段是 `user_id`

「我的整改单」筛选需要用当前用户 ID，最初写 `auth.user?.id` 导致 `vue-tsc` 报 `TS2339`。正确字段是 `auth.user?.user_id`（`Me` 类型沿用后端契约的命名）。

这条不需要调接口：`mine` 筛选直接用 `auth.user?.user_id` 拼 `assignee_id` 查询参数，**不拉用户清单** —— 评估员虽然能拉到清单，但没必要为「我是谁」多打一次请求。

### 9.4 `loadActiveRemediationMap` 的分页终止条件

初版用 `res.items.length < pageSize` 判断「到底了」。问题：当总数**恰好是整页**（例如 100 条、`pageSize=100`）时会多跑一次空请求。改为 `map.size >= res.total` —— 同时用 `maxPages` 兜底，避免分页参数异常时死循环。

（`eslint` 的 `no-useless-assignment` 抓到了配套的 `let total = 0` 初值未被使用，一并删掉。）

## 10. 守门脚本与验收

### 10.1 最重要的设计：真的重算一次

「建单成功、列表有数据、详情能打开」证明不了 D1 的任何一条 —— 一个把 `risk_item_id` 当业务身份的实现，在**第一次重算之前**与正确实现完全一样。

因此第 5 节的做法是**真的重算一次**，然后回头质问那张单子四个问题：

| 断言 | 若失败说明什么 |
|---|---|
| 旧 `risk_item_id` 查不到行了 | 重算没有真正更换 id（脚本的前提坏了） |
| 同一 `(资产, 漏洞)` 的新 id 与旧的不同 | 同上 |
| 单子还在、状态没被打乱 | 外键把重算拦住了（或单子被级联删了） |
| 快照五列（名称/IP/漏洞名/等级/风险值）逐列完好 | 展示依赖了出处而非快照 |
| 出处指向的旧 id **原样保留** | 实现偷偷把失效的出处清空了（那会让「哪次评估发现的」永久丢失） |

最后再加一条**反向对照**：

```sql
SELECT COUNT(*) FROM remediations r
 WHERE r.risk_item_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM risk_items i WHERE i.id = r.risk_item_id);
```

要求 `≥ 1`。这不是在描述缺陷，而是把设计意图变成**可观测的事实**：库里存在「出处已失效但单子完好」的行，恰恰证明表结构没有把 `risk_item_id` 当成约束。

### 10.2 覆盖的 14 节（0–13，共 333 项断言）

| 节 | 覆盖 | 断言数（约） |
|---|---|---|
| 0 | 隔离库 `sec_risk_remediate_e2e` + 端口 18087 | 2 |
| 1 | 登录、改密、取出真实显示名 | 4 |
| 2 | 6 资产 × 6 漏洞 + 威胁 T=1 + 3 个评估；**等级分布铺满五档** | 45 |
| 3 | 建单快照逐列、初始态、时间态、流转投影 | 29 |
| 4 | 唯一性（二次 409 / `active_key` 实测 / 闭环后可再建） | 13 |
| 5 | **重算不断链** | 17 |
| 6 | 状态机（非法 409 不留痕 / 400 三处 / 打回 from-to / 终态无出边） | 40 |
| 7 | 逾期三档 + 精确天数 + 区间不重叠 + 闭环归零 | 24 |
| 8 | 批量建单（命中/新建/跳过 / 幂等 / 非法等级 / 草稿 409） | 25 |
| 9 | 删除限制 | 11 |
| 10 | 列表筛选（active/status/level/keyword/assessment/排序）+ PATCH 三态 | 26 |
| 11 | 权限（匿名 401 / 缺 CSRF 403 / 审计员只读 / 评估员可写） | 27 |
| 12 | 仪表盘口径、数字对账、**换 `assessment_id` 数字要跟着变** | 45 |
| 13 | 五个审计动作码 + 明细字段 + 失败流转不留痕 + 无告警日志 | 25 |

### 10.3 两处关键的构造技巧

**① 等级分布必须铺满五档。** 3 档重要性 × 3 档严重程度 + 威胁 `T=1` 使 `R = 重要性 × 严重程度`，恰好得到 `very_high 1 / high 2 / medium 1 / low 4 / very_low 1`。若全落在「很高」，一个把等级筛选写死成「全部」的实现同样能通过第 8 节。

**② 两批资产，避免测试互相干扰。** 唯一索引的作用域是 `(资产, 漏洞)`。若「逐条建单」与「批量建单」共用一批资产，批量建单的命中数会随前面测试的执行顺序漂移，断言只能写成「≥ N」—— 那等于没有断言。因此 A 批（`RA*`）供逐条测试、B 批（`RB*`）供批量测试。


本脚本**不需要 docgen / gotenberg** —— `make infra` 会把它们一起起起来，

## 11. 非目标

| 不做 | 理由 |
|---|---|
| **历史逾期率** | 逾期是算出来的当前态（D4）。要算「历史上逾期过几次」就必须落库，而落库需要一个可靠的每日归档任务 —— 那是另一个量级的复杂度 |
| 整改任务的分派通知（站内消息 / 邮件） | 需求文档的 P6 范围只到「站内」，而站内提醒等于「打开就有数」（首页三卡已覆盖），主动推送留给后续阶段 |
| 与工单系统对接（Jira / 禅道） | 需要对方的接口与字段映射，且要处理双向同步的冲突；本系统的整改单粒度是 `(资产, 漏洞)`，与工单的粒度未必对齐 |
| 附件上传（整改截图 / 补丁包） | 需要存储配额、病毒扫描、权限隔离三套配套能力，`scan_files` 那一套不能直接复用 |
| 整改单的模板与批量导出 | 报告导出（P5）已覆盖「评估结果」这一类交付物，整改单是工作记录而不是交付物 |
| 状态机的可视化编辑 | 状态机是代码（`remediationTransitions`）。做成可配置会让「界面允许但接口拒绝」重新变成可能 |

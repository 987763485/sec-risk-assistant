## 1. 范围

**做**：把一份**已计算**的评估渲染成三种格式的文件并下载；报告内容自证口径（阈值、快照时刻、导出人）；导出留审计；上游不可用时可降级（Excel 始终可用）。

**不做**：报告模板的在线编辑；报告的版本管理与历史留档（每次导出即用即走）；定时/批量导出；报告的电子签章。

## 2. 五项决策与理由

### 2.1 报告不落库

导出的文件**不写进数据库、不落到 `storage/reports/`**，直接流式返回给调用方。

理由：报告是**数据库当前状态的一个投影**，而投影是可以随时重算的。把它存下来会立刻引入三个新问题——存储配额、清理策略、「库里这份报告与刚才那次计算是否还对得上」。最后一个最要命：报告落库之后，任何一次重算都会让存下来的旧报告变成**表面上仍然有效、实际已经过期**的文件，而这种失效不会报错。

需要留档时由用户自己另存，或者由审计日志回答「谁在什么时候导过什么」（见 §8）。

> ⚠️ 一处例外：`storage/reports/` 这个卷仍然挂在 web 容器上（`docker-compose.yml`）。它是为将来可能的「异步大批量导出」预留的落点，当前代码不往里写任何东西。

### 2.2 POST 而不是 GET

导出看起来是读操作，用 GET 更自然，但契约把它定成 **POST**：

| 问题 | GET 的后果 |
|---|---|
| 审计 | 一个 `<a href="…/reports/export?…">` 就能触发一次导出（顶层导航带 Cookie，SameSite=Lax 不拦）。审计里会出现**用户从未做过的** `report.export` —— 这比漏记一条更糟，它会让人怀疑整套审计的可信度 |
| CSRF | CSRF 中间件只保护非安全方法，GET 天然绕过 |
| 预取 | 导出是重操作（起 .NET / Chromium 进程），不该能被浏览器预加载、爬虫、聊天软件的链接预览随手触发 |

换 POST 后三件事一起消失：CSRF 中间件生效、链接点不出来、预取器不会发 POST。

代价在前端：不能再用 `<a href>` 或 `window.open` 拿文件，只能走 XHR 把字节读出来自己存盘 —— 这正是 `@/utils/download` 里 `saveBlob` 存在的原因。

### 2.3 未计算不可导出（409）

`status != calculated` 时**在渲染之前**返回 `409 REPORT_NOT_CALCULATED`。

理由：草稿任务没有结果行，硬渲染会得到一份「0 条风险项」的报告。那份报告**看起来完全正常**：有封面、有目录、有矩阵（全 0）、有口径说明。收到它的人不会想到「这份评估其实还没跑」，只会得出「这个系统的资产全都没风险」这个结论。

这种「安静地说错话」的错误比报错危险得多，因此必须在渲染前拦住。前端也据此隐藏导出入口（列表页与结果页都按 `status === 'calculated'` 判，而不是按 `risk_items_count > 0` —— 后者是「算出来有几条」，一份范围内零风险项的评估同样可以、也应该能出报告）。

### 2.4 超时与重试：重试一次，不做熔断

| 项 | 取值 | 理由 |
|---|---|---|
| docgen 超时 | 30s | 纯内存的 OpenXML 拼装，几十毫秒级 |
| gotenberg 超时 | 60s | 要起 Chromium 进程渲染排版，秒级起步 |
| 重试 | 1 次，**仅**网络层错误与 5xx | 4xx 是我们自己把请求构造错了，重试一次只会把同一个错误再犯一遍 |
| 熔断 | 不做 | 见下 |
| `server.write_timeout` | 180s | 必须 ≥ 最慢链路：docgen 30×2 + gotenberg 60×2 |
| nginx `proxy_read/send_timeout` | 200s | 必须 > 后端 180s，否则用户拿到的是 nginx 的截断/504，而不是我们那份说明原因的 JSON 503 |
| 前端 axios 超时 | 210s | 必须 ≥ nginx，**让服务端先决定结局**（见 §7.2） |

这三个数字（180 / 200 / 210）是**同一条链路上的三道闸**，必须严格递增。任何一道反了，用户看到的就是「请求超时」，而真正的原因（503 上游不可用 / 409 未计算）其实已经躺在服务端那份因为客户端先断开而送不出去的响应里了。

**不做熔断**的理由：报告导出是低频的人工操作，不是一个会自己放大流量的自动调用链。熔断器要解决的问题（故障期间持续打垮下游）在这里不存在。引入它只会新增一类状态——「明明服务已经好了，但因为熔断器还没到半开时间而继续 503」——而这类状态很难向用户解释。

## 3. 架构：一个纯函数 + 两个上游

### 3.1 `report` 包的边界

```go
// 本包唯一的对外入口
func Render(ctx context.Context, client *Client, format Format, data ReportData) ([]byte, error)
```

`Render` **不连数据库、不判权限、不做风险计算**。输入是已经完全定型的展示值（`ReportData`），输出是字节流。三种格式在这一层被抹平成同一个签名 —— `service` 层不需要知道「Excel 不用起容器」这种实现细节，也就不需要为它写一条特殊分支。

这样切的一个直接好处：`report` 包的单元测试只测排版，不牵动模型层、仓储层、权限层（`go test ./internal/report/` 23 个用例，含 `-race`）。

### 3.2 依赖方向

```
handler → service → report
              ↘ repository
```

`report` 在依赖树的最下游，**不反向依赖任何业务包**。它甚至不 import `model`：风险等级码在 `report/data.go` 里用裸字符串常量重新声明了一遍（`LevelVeryHigh = "very_high"` …）。

这不是偷懒，是刻意切断 —— 一旦 `report` 依赖 `model`，改一个字段名就会牵动两层，而这两层的演化速度完全不同（模型跟着业务走，排版跟着模板走）。

### 3.3 三种格式三条路线

| 格式 | 实现 | 依赖 | 失败模式 |
|---|---|---|---|
| word | `docgen`（C# / OpenXML） | **需要**上游服务 | 上游不可用 → 503 |
| excel | `excelize`（纯 Go） | **无** | 只可能因为自己的 bug 失败（500） |
| pdf | `html/template` → Gotenberg（Chromium） | **需要**上游服务 | 上游不可用 → 503 |

这张表里最值得记住的是 Excel 那一行：**它不依赖任何上游**。这不是刻意设计出来的特性，但它确实是对的 —— 一个不需要外部依赖的功能，不该被外部依赖拖垮。上游没起来时（部署期最常见的一类问题），用户至少还能拿到 Excel 去干活，而不是被一个空白页面挡住。

「一个上游挂了会怎样」不能靠推理，必须被测到，所以守门脚本第 10 节**逐个停掉上游**验证这个矩阵（停 docgen → Word 503 而 Excel/PDF 仍 200；停 gotenberg → PDF 503 而 Word 仍 200）。

## 4. 取数：只有一条路径

### 4.1 `ExportData` 与 `buildExportData` 的分工

`ReportService.Export` 调用的是 `AssessmentService.buildExportData`（**无审计版本**），而不是 `ExportData`（带审计版本）。

区别只在一行：

```go
func (s *AssessmentService) ExportData(ctx, p, meta, id) (*ExportDataView, error) {
    view, err := s.buildExportData(ctx, id)
    if err != nil { return nil, err }
    s.audit.record(ctx, ..., model.ActionAssessmentExport, ...)  // ← 只有这里有
    return view, nil
}
```

如果 `ReportService` 图省事直接调 `ExportData`，审计表里会凭空多出一条 `assessment.export` —— 那条记录对应的是一个**没有发生过的动作**（用户点的是「导出报告」，不是「导出 JSON 数据」）。审计的价值在于可信，一条凭空出现的记录足以毁掉它。

而拆出 `buildExportData` 又保证了**取数实现只有一份**：`/api/assessments/{id}/export-data` 与 `POST /api/reports/export` 拿到的 `ExportDataView` 逐字段相同。「界面值 = 落库值 = 报告值」的第三个等号靠的就是这个。

### 4.2 快照时间不能补 `time.Now()`

`configForAssessment` 返回 `(riskengine.Config, time.Time, error)` —— 第二个返回值是**落库的 `config_snapshot.captured_at`（计算时刻）**。

报告里写的是这句话：

> 配置在计算时刻即被快照冻结，快照时间：X

如果这里的 X 用导出时刻去补，这句话在**事实上说谎**，而且不会报任何错：报告照常生成，数字照常正确，只是那句「冻结于 X」指向了一个错误的时刻。一份几个月后导出的报告会声称它的配置是几分钟前冻结的。

因此 `configForAssessment` 把快照时间一路带出来，`buildExportData` 只在 `capturedAt.IsZero()`（历史数据缺字段）时才回落到 `time.Now()`，并且该回落在守门脚本里有对应的反向断言（日志里不得出现快照回退告警）。

### 4.3 `toReportData` 只搬运，不加工

`toReportData` 把 `ExportDataView` + `MatrixView` 映射成 `ReportData`。**A / T / V / R、条数、档位一律原样搬，一处都不重算**。

唯一被改写的是两个时间字段的**展示格式**（RFC3339 → `2006-01-02 15:04:05`），那是排版，不是数值。

唯一被「生成」的是序号 `Seq`：用 1..N 的展示序号而不是风险项的数据库主键 —— 报告读者拿主键在系统里查不到东西（风险项没有单独的详情页），只会让人以为漏了页。

这条「不加工」纪律的价值在于：它让「报告值 = 落库值」成为一个**结构性**的事实，而不是一件需要每处小心维护的事。只要这里对某个数动一次手（哪怕是「保留两位小数」这种看起来无害的格式化），等式就断了，而且断在渲染器之外。

矩阵单独用 `s.assess.Matrix` 取一次，而不是从 `export-data` 里的 R 值自己推算格子等级 —— 自己按 R 推一遍就是第二条判定路径，与快照阈值一旦分叉，**格子颜色与明细里的等级会对不上，而两边都不会报错**。

## 5. 报告结构

### 5.1 Word：封面 + 目录 + 六章 + 附则

| 序 | 章节 | 表 |
|---|---|---|
| — | 封面（标题、副标题、生成时间、导出人） | — |
| — | 目录（TOC 域） | — |
| 一 | 评估概述 | 表 1 评估任务基本信息 |
| 二 | 评估方法与配置 | 表 2 本次评估所用配置（配置快照） |
| 三 | 风险等级分布 | 表 3 风险等级分布 |
| 四 | 风险矩阵 | 表 4 风险矩阵（5 × 5） |
| 五 | 资产风险汇总 | 表 5 资产风险汇总（按风险值降序） |
| 六 | 风险项明细 | 表 6 风险项明细（资产 × 漏洞） |
| 附 | 口径说明 | — |

**章节顺序固定，不做「按数据有无增删章节」的动态编排**：读报告的人会拿两份报告对比，章节位置一变，对比就成了找不同。同理，矩阵即便全 0 也照常渲染（恒 25 格）。

分页：封面与目录各占一页，之后每个一级章节另起一页（第一节不设 `pageBreakBefore` —— 目录之后本来就有分页符，再设会多出一整页空白）。合计 8 处分页符，守门脚本对此是**精确断言**而不是「≥ N」。

页脚由 `footerText(d)` 推导：`{评估名}　{yyyy-MM-dd HH:mm}`。它**不由调用方提供**（`ReportData` 里没有这个字段）——页脚上的时间是「这份文件何时生成」，而调用方手上飘着好几个时间（计算时刻、快照时刻、请求开始时刻），随手传错一个不会有任何报错，但报告会写着一个错误的时间戳。

### 5.2 Excel：三张表

| 工作表 | 内容 |
|---|---|
| 风险项明细 | 标题行 + 表头 + N 行；11 列（序号/资产名称/资产IP/漏洞/威胁/重要性/A/T/V/R/等级） |
| 资产风险汇总 | 7 列（资产名称/IP/重要性/资产价值 A/最高风险值 R/风险等级/风险项数） |
| 风险矩阵 | 两块 5×5：计数块 + 最高等级块，中间空一行分隔 |

**数值必须是数值，不是文本**。所有 A / T / V / R 按 `float64` 写入。写成字符串的话，业务方在 Excel 里连求和都做不了 —— 而他们之所以要 Excel 而不是 PDF，正是为了算。这条错误在界面上看不出来（单元格右对齐与否只是显示习惯），所以守门脚本直接读回单元格的**类型**来断言。

⚠️ **OOXML 的一个坑**：数值单元格**根本不写 `t` 属性**（数值是默认类型，excelize 写数值时显式置 `c.T = ""`）。因此断言绝不能写成「类型等于某个数值类型常量」—— 那个比较**恒不成立**，会让断言永远为假或永远为真（取决于写法）。正确姿势是「不属于文本类型集合」，并配一条**阳性对照**（同一张表的等级列必须被认成文本）。这条踩坑经过见 §11.3。

### 5.3 PDF：HTML → Chromium

链路是 `ReportData → html/template → Gotenberg(Chromium) → PDF`。

用 HTML 而不是直接用 Go 的 PDF 库排版：后者要自己处理字体嵌入、换行、分页、表格跨页 —— 那是一个需要长期维护的排版引擎。而 Chromium 已经把这些都做好了，项目里本来就在跑 Gotenberg，复用它的边际成本为零。

用 `html/template` 而不是拼字符串：报告内容含用户录入的数据（资产名、漏洞标题、评估描述），`html/template` 的上下文感知转义会自动按 HTML / 属性 / CSS 各自的规则处理。手工拼接的话，一个叫 `</td><script>…` 的资产名就能改变报告结构 —— 而报告是要发给外部看的文件。

**页脚单独传**：Chromium 不支持 CSS Paged Media 的 `@bottom-center`（那是 WeasyPrint / Prince 的能力），页码必须由 Gotenberg 注入 —— 它会在页脚 HTML 里找 class 为 `pageNumber` / `totalPages` 的元素并填值。页脚 HTML 是**手工拼**的（没有模板引擎的自动转义），因此评估名必须显式 `html.EscapeString`：把评估名起成 `<b>` 的话，页脚就会变成粗体。

## 6. 文件名：两端都要处理

### 6.1 服务端

响应头形如：

```
Content-Disposition: attachment; filename="security-assessment-report.docx"; filename*=UTF-8''<百分号编码的中文名>
```

- `filename*`（RFC 5987）是**主路径**，值是 `{清洗后的评估名}_{格式}_{yyyyMMdd-HHmm}.{ext}`；
- `filename` 是给老客户端的 ASCII 兜底，值固定为 `security-assessment-report.{ext}` —— 不带评估名（那是中文）也不带时间戳（那不是给人读的）：兜底路径下唯一重要的是**扩展名对**，操作系统靠它决定用什么程序打开。

`SanitizeFileName` 的规则：字母 / 数字 / 汉字（`unicode.IsLetter` 已覆盖，CJK 的类别就是 `Lo`）、以及 `- _ 空格 .` 原样保留，其余一律换成下划线。防的是三件事：`"` 与换行造成的**响应头注入**（CRLF injection）、`/` `\` 让客户端当成路径、控制字符让浏览器直接拒绝保存。长度上限 80 个**字符**（不是字节，否则中文名会被拦腰截断）。

> 兜底名由**调用方**给出（`asciiReportName(format)`），不是函数内部写死的。此前 `contentDisposition` 里硬编码着 `asset-import-template.xlsx`，对文件下载和报告导出都不对 —— 一个下载报告的人会拿到名为「资产导入模板」的文件。

### 6.2 前端

前端优先取 `filename*` 并解码（`filenameFromDisposition`，放在 `@/utils/download`，与 `saveBlob` 同模块）；解析不出时回落到 `fallbackFileName(assessmentName, format)`，只保证**带对扩展名**。

**刻意不复刻服务端那套命名规则**：复刻出来就是第二条命名路径，两边一旦分叉（时间戳差一分钟、清洗规则不一致），用户会看到同一次导出生成了两个不同命名的文件，反而更难理解。兜底路径的唯一目标是「别让浏览器把文件存成 `download`」。

## 7. 前端

### 7.1 `api.download`：为什么需要一个「返回完整响应」的方法

`api.get/post/...` 都会拆掉统一信封只返回 `data`。下载场景不行：**文件名在响应头里**，只给 `data` 就把它丢了。

因此 `web/src/api/http.ts` 里把请求核心拆成两层：

```
send()     把请求发出去并保持会话有效（CSRF 注入、401 静默刷新后重试、失败收敛成 HttpError）
  ├── request<T>()   拆信封 → 给 get/post/patch/put/delete
  └── api.download() 原样返回 AxiosResponse → 给「需要读响应头」的调用方
```

这个拆分不是为了让代码好看，而是**为了避免第二份 CSRF / 刷新逻辑**。若在 `reports.ts` 里直接用底层 `http` 实例，就得手写 `X-CSRF-Token`（要自己 `await ensureCsrfToken()`）、并且失去 401 的静默刷新重试 —— 那意味着用户在长时间停留后点导出，会看到一句「登录状态已失效」而不是自动续期后把文件给他。

### 7.2 210 秒超时

`exportReport` 显式传 `timeout: EXPORT_TIMEOUT_MS = 210_000`，因为 axios 实例上有一个 30s 的全局默认值，而 PDF 链路的最坏耗时是它的好几倍。

取值推导：后端 `server.write_timeout` = 180s，nginx = 200s，前端 = 210s。**严格递增**的意图是让服务端先决定这次导出的结局 —— 前端比服务端先放弃的话，用户看到的是「请求超时」，而真正的原因（503 / 409）已经躺在服务端那份因为客户端断开而永远送不出去的响应里了。

同时显式设 `Accept: */*`：client 实例上挂着一个全局的 `Accept: application/json`，而我们要的是二进制。服务端不做内容协商（它按 `format` 直接回字节），这个头只是把意图写清楚。

### 7.3 错误信封由拦截器统一读回

`responseType: 'blob'` 之下，即使后端返回的是标准 JSON 错误信封，axios 也会把它包成 `Blob`，拦截器取不出 `code` / `message`，界面上就只剩「请求失败（HTTP 403）」。

这件事已经由 `client.ts` 的 `parseBlobEnvelope` 统一处理（读回 JSON、拼回 `HttpError`），**`reports.ts` 不需要再处理一次** —— 二进制响应的错误信封与普通响应的错误信封走同一条路。

界面据此能显示后端给的原话：409 会说「该评估任务尚未计算」，503 会说「报告渲染服务暂时不可用，请稍后重试」—— 比一句笼统的「导出失败」更能让用户知道下一步做什么。

### 7.4 入口位置

| 页面 | 入口 |
|---|---|
| 评估结果页 | 「导出报告」下拉：Word / Excel / PDF / 导出报告数据（JSON） |
| 评估列表页 | 操作列「导出」下拉（仅 `calculated` 行显示）：Word / Excel / PDF |

列表页的价值只是「不必为了拿一份文件先进去再点两下」，**不是第二条导出路径** —— 两处调用同一个 `exportReport`。

列表页的 loading 状态用**行 id** 而不是布尔量：布尔量会让点一行的导出时整张表都在转圈，用户会以为自己不小心触发了批量导出。

## 8. 权限与审计

### 8.1 权限

挂在 **`report:read`** 而不是 `assessment:read`：

- `report:read` / `report:write` 这两个权限码在 P1 就随 RBAC 一起预置了（`internal/auth/rbac.go`），P5 只是把它接上，没有新增权限码；
- admin / assessor / auditor **三者都持有 `report:read`** —— 审计岗要能把报告取走归档，没有导出权限的审计员只能靠截图留痕；
- 这也说明：「这个接口会写审计」与「它需要写权限」是两件事。POST 只解决 CSRF 与预取，不是写权限。

### 8.2 审计

动作码 **`report.export`**，`resource = assessment`，`resource_id = <评估 ID>`，明细：

```json
{
  "name": "评估任务名",
  "format": "word",
  "file_name": "…docx",
  "size_bytes": 123456,
  "assets_count": 5,
  "risk_items_count": 26,
  "max_risk": 125
}
```

明细里这几项是刻意选的：报告一旦被转发出去，审计日志就不在它身边了，`file_name` 与 `size_bytes` 是事后追查「这份流出文件是不是这一次导出」的唯一线索。

**失败不写审计**：草稿任务的 409、参数错误的 400、上游不可用的 503 都不产生记录 —— 审计记的是「发生过的事」，一次被拦下的请求没有产生任何数据外流。守门脚本对此有反向断言（被拒前后 `report.export` 的 total 必须相同）。

审计在 **service 层**落库（不经过审计中间件的通用路径），因为要记的明细只有那里有。handler 里随后调 `reqctx.MarkAuditRecorded(c)` 声明一句，免得审计中间件把这次 POST 当成「未记录审计的写操作」告警。

## 9. 上游不可用时的降级矩阵

| 停掉 | Word | Excel | PDF |
|---|---|---|---|
| docgen | **503** `REPORT_RENDER_FAILED` | 200 | 200 |
| gotenberg | 200 | 200 | **503** `REPORT_RENDER_FAILED` |
| 两者都停 | 503 | **200** | 503 |

错误分类：

| 情况 | 状态码 | 业务码 | 用户该做什么 |
|---|---|---|---|
| 上游连接被拒 / 超时 / 5xx（重试后仍失败） | 503 | `REPORT_RENDER_FAILED` | 稍后重试 |
| 调用方取消（关掉页面） | 503 | `REPORT_RENDER_FAILED` | 无需看到这句话（日志记 info） |
| 自己的 bug（模板坏了、数据超预期） | 500 | `INTERNAL` | 联系管理员 |

**先判 `ctx.Err()` 再判 `errors.Is(err, ErrUpstream)`**：调用方取消时 err 里也含「网络层错误」的形态，若先撞上 `ErrUpstream` 分支，日志里会记一条「上游不可用」的假警报，把「用户关了页面」误报成故障。

## 10. 环境：`internal` 网络会静默丢弃端口映射

这是 P5 环境改造中代价最大的一课，单独立一节。

**现象**：`make dev` 不报错、容器健康、`docker-compose.override` 看起来完全正确，但导出 Word/PDF 一律 503。

**根因**：给只挂 `internal: true` 网络的服务加 `ports`，**Docker 不报错、不警告，直接丢掉这条端口映射**。`docker port` 为空、`docker ps` 的 PORTS 列为空。事后 `docker network connect` 补一张普通网络也**补不回来** —— 端口绑定在容器创建的那一刻就决定了。

**实测结论**（docker 28.3.2 / Compose v2）：compose 里同时挂「普通网 + internal 网」+ `ports` → 映射生效（`8090/tcp -> 127.0.0.1:8090`，宿主 HTTP 200）。

**做法**：

- 生产（`docker-compose.yml`）：docgen / gotenberg 只挂 `secrisk-internal`，**不声明 `ports`**，靠网络隔离 + `X-Internal-Secret` 双重保护；
- 开发（`deploy/compose.dev.yml`）：额外挂一张普通网 `dev-edge` 并映射回环端口。

⚠️ 覆盖文件**不能**命名为 `docker-compose.override.yml` —— compose 会自动加载那个名字的文件，于是「把内部服务端口暴露到宿主机」的配置会在 `make up`（生产）时一并生效。因此它叫 `deploy/compose.dev.yml`，必须显式 `-f` 叠加。

守门脚本把「上游宿主可达性」放在**第 0 节**先查（`curl` 两个 `/health`，失败时 `docker port` 打印诊断并提示 `make infra`），而不是等到第 3 节才看见一堆 503 —— 后者会把排查方向带向 docgen / gotenberg 本身。

## 11. 实现期对计划的修正

### 11.1 `report` 包不 import `model`

计划里没有明确写这一条。实现时选择让 `report` 用自己的等级码常量（不 import `model`），代价是两处字符串需要保持同步 —— 但换来了「单测只测排版」，以及标题里说的那种「两层演化速度不同」的解耦。

### 11.2 `contentDisposition` 的兜底名改为参数

原实现把 `asset-import-template.xlsx` 写死在函数内部，P5 复用这个函数时才发现它对文件下载 / 报告导出都不对。改为 `contentDisposition(name, asciiFallback string)`，三个调用点各自给出正确的兜底名。

### 11.3 excelize `GetCellType` 的陷阱（守门脚本抓到的缺陷）

守门脚本第一版断言 `cellType == CellTypeNumber`，**恒不成立**。根因：`GetCellType` 直接返回 OOXML 的 `t` 属性，而**数值单元格在 OOXML 里根本不写 `t`** —— excelize 写数值时显式置 `c.T = ""`，落到映射表零值上返回 `CellTypeUnset(=0)`。字符串则走 `t="s"`。

修法：断言改为「**不属于文本类型集合**」（`CellTypeSharedString` / `CellTypeInlineString` / `CellTypeFormula`），并补一条**阳性对照** —— 同一张表的文本列必须被认成 `CellTypeSharedString`。阳性对照的作用是证明「类型断言机制本身是有效的」：如果这个机制坏了（比如类型恒返回同一个值），阳性对照会先失败。

单测（`excel_test.go`）与守门脚本现在都用这套写法。

### 11.4 快照时间：`configForAssessment` 从单返回值改为双返回值

原签名只返回 `riskengine.Config`，P5 需要快照时刻才能写对报告里那句话。改为返回 `(Config, time.Time, error)`，三处既有调用点补 `_`。这是一次**向后不兼容的内部改动**，但它比「在报告侧再查一次 `config_snapshot` 表」更好 —— 后者的错误形态是「两份快照」，前者只是多一个返回值。

### 11.5 `ReportData.FooterText` 字段被删除

初版把页脚文本做成 `ReportData` 的字段，由 service 填。实现时删掉了：页脚是「这份文件何时生成」，只能由 `footerText(d)` 从 `GeneratedAt + 评估名` 推导。暴露成字段意味着调用方可以传一个不一致的值，而那种错误不会报错。

### 11.6 前端多了一个 `api.download`

计划里写的是「`exportReport` 解析 `Content-Disposition`」，隐含「用底层 http 实例」。实现时选择在 `api` 上加一个 `download` 方法并重构出 `send()`，理由是 §7.1 说的：避免第二份 CSRF / 刷新逻辑。

### 11.7 前端 `filenameFromDisposition` 从 `assets.ts` 提到 `utils/download.ts`

它被两类调用方用到（api 层握 `AxiosResponse`、视图层握 DOM），放在任何一侧都会让另一侧产生莫名其妙的依赖。与 `saveBlob`、`DownloadedFile` 一起放在下载主题模块里。

## 12. 守门脚本与验收

### 12.1 最重要的设计：**把文件拆开看内部**

「导出成功、下载下来能打开」证明不了验收标志里的任何一条。一个所有汉字都渲染成空心方框、或者整张明细表缺失的 docx，同样能 200 下载成功。

因此对三种产物都**解包到内部格式**再断言：

| 格式 | 解开看什么 |
|---|---|
| docx | `word/document.xml`：文本、表格、分页符数量、`w:sectPr` 位置、TOC 域、页脚 |
| xlsx | `xl/worksheets/*.xml`：工作表名、单元格值、**单元格类型** |
| pdf | 内容流里的**文本层**：中文能不能被读回来 |

解析器：`scripts/lib/ooxml.py`（docx / xlsx，纯 zip + XML）与 `scripts/lib/pdf_text.py`（PDF，纯 zlib + re）。沙箱里 `python-docx` / `openpyxl` / `pdftotext` 都没有，所以是自己实现的 —— 但这也带来一个好处：它们同样可以给人用（`.docx` 改名 `.zip` 直接看 XML，是排查这类问题最快的手工手段）。

### 12.2 覆盖的 13 节（149 项断言）

| 节 | 内容 |
|---|---|
| 0 | 环境准备：隔离库 + 端口 + **渲染上游宿主可达性** |
| 1 | 启动后端（指向临时库）并登录 |
| 2 | 数据准备：5 档资产 × 5 档漏洞 + 1 条独立漏洞 + 两个威胁档 + 已计算任务 + 草稿任务 |
| 3 | Word：双端文件名、8 处分页、TOC 域、样式注册、6 张表、7 个章节、页脚 |
| 4 | Excel：三张表、明细行数、**数值类型**（含阳性对照）、矩阵两块 5×5 |
| 5 | PDF：`%PDF-` 魔数、文本层抽回中文、页码 |
| 6 | **五方一致**：落库 ↔ 界面 ↔ export-data ↔ Word 明细表 ↔ Excel 明细表 |
| 7 | 未计算不可导出（409 × 3 格式，且不留审计） |
| 8 | 参数校验：格式、ID、空体（400 / 404） |
| 9 | 权限与会话：匿名 401、缺 CSRF 403、审计员可导出 |
| 10 | 上游降级矩阵：逐个停上游，验证「该挂的挂、该活的活」 |
| 11 | 导出确定性：连导两次，数据区逐格相同 |
| 12 | 审计落库与服务端日志 |

### 12.3 边界用例怎么构造的

- **矩阵计数不是恒为 1**：5 台资产各挂 5 条漏洞 = 25 条（每格 1 条），再加一条漏洞**(只挂 A5)** → 格 (5,5) 有 2 条。全是 1 的矩阵看起来整齐，却证明不了计数是对的 —— 一个把格内计数恒写成 1 的实现同样能通过。
- **T 列有两种取值**：任务默认威胁 T=3，再把其中一条风险项**逐项覆盖**为 T=5。这同时证明了「报告读的是落库后的风险项，而不是任务级默认威胁」。
- **审计员要能导出**：新建的审计员首次登录处于「必须改密」状态，不改密的话任何业务请求都是 403 `AUTH_MUST_CHANGE_PASSWORD` —— 少这一步的话，断言「审计员可以导出」会以一个与权限毫无关系的理由失败，而人会去查半天 RBAC 配置。

### 12.4 三源比对为什么比对「集合」而不是「顺序」

落库查询按 `id` 排序，而界面 / export-data 的排序规则是业务决定的（可能按 R 降序）。按顺序比对会在排序规则变化时给出大量假差异；按 `(资产名, 漏洞名)` 建映射再比对值，才是真正要验证的事（同一对目标在两个源里是不是同一个数字）。

数值一律转成**定点整数（×1000）**再比：JSON 里的 `12` 与 `12.0` 是同一个数，字符串直接比会在这种表示差异上误判。

### 12.5 运行

```bash
make infra          # 或 make dev，确保 docgen / gotenberg 映射到宿主回环
make verify-report  # 约 40 秒
```

产物保留在 `/tmp/.sr-report-{word.docx,excel.xlsx,pdf.pdf}`，**建议人工打开确认一次** —— 脚本能证明「文本层里找得到这个汉字」，但版式好不好看、Word / WPS 里目录域更新后是否正确，仍然需要人眼。

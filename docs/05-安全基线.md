## 0. 本文怎么用

三句话说明定位，避免与 `03` 重复：

1. `03` 回答「**为什么**这么设计」——每项决策的取舍与反例。
2. 本文回答「**现在到底做到了没有**」——每项控制点写出**实现位置 + 判据 + 验证方式**。
3. 任何一项如果只写在文档里而没有对应的代码位置或验证命令，就当作**没做**。

每张控制表最后都有一列「状态」，取值只有四种：

- ✅ **已生效**：有代码位置，**且**被自动化验证覆盖（写明脚本/测试名）。
- 🔶 **已实现未验证**：有代码位置，但**没有**自动化断言兜底（写明缺口与建议补法）。
- ⚠️ **部分生效**：有代码位置，但只对部分路径生效，或强度被削弱（写明缺哪部分）。
- ⛔ **待 P<n>**：本阶段不做，已登记归属阶段（见第 7 节）。

> **为什么单列 🔶**：把「写了代码」当成「做了安全控制」是最常见的自欺。
> 🔶 不是缺陷清单，而是**待补测清单**——它明确告诉后来者「这块改动没有东西帮你兜底」。
> 当前 111 项中 ✅ 81 项、🔶 28 项、⚠️ 1 项、⛔ 1 项；🔶 的完整清单与补法见 §6.1。

## 1. 威胁模型

### 1.1 信任边界

```
                    ┌──────────────── 不可信 ────────────────┐
                    │  公网 / 办公网浏览器                     │
                    └───────────────┬────────────────────────┘
                                    │ HTTPS（生产）
                                    │ ★ 边界①  Nginx 静态资源 + 反代
                    ┌───────────────▼────────────────────────┐
                    │  Nginx  :80/:443                        │
                    │   · server_tokens off                   │
                    │   · CSP / nosniff / DENY 响应头          │
                    │   · /uploads/ /reports/ 一律 403         │
                    └───────────────┬────────────────────────┘
                                    │ HTTP（compose 内网，仅 /api/）
                                    │ ★ 边界②  后端进程
                    ┌───────────────▼────────────────────────┐
                    │  Go 主服务  :8080                        │
                    │   中间件链 → 鉴权 → 业务                  │
                    └───────┬────────────────────┬────────────┘
                            │                    │
            ★ 边界③ DB 凭据最小化    ★ 边界④ 内部共享密钥
                    ┌───────▼──────────┐  ┌──────▼───────────────┐
                    │ MySQL :3306      │  │ docgen :8090          │
                    │ 不暴露到宿主机    │  │ 不暴露到宿主机         │
                    └──────────────────┘  └───────────────────────┘
```

四条边界分别对应第 2 节中「传输与响应头」「认证与授权」「配置与部署」「服务间调用」四组控制。

### 1.2 攻击者假设

| 攻击者具备的能力 | 对应的控制项 |
|---|---|
| 能伪造任意 HTTP 请求（含 Cookie，受同源策略约束） | CSRF 双提交 + Origin 校验（§2.2） |
| 能无限次尝试登录（撞库、暴力破解、用户名枚举） | 账号锁定 + IP 限流 + 等耗时比较（§4） |
| 能把恶意内容存进系统，再让其他用户看到 | 输出编码 + CSP + 审计明细剔除（§2.4） |
| 能拿到一份数据库备份（离线） | argon2id 参数强度（§3） |
| 能读到网络中间环节的流量 | Cookie 属性 + HTTPS + 刷新令牌路径收窄（§2.1） |

**明确不在范围内**（本期不防，也不假装防）：

- 已失陷的终端（键盘记录、浏览器恶意扩展）——任何 Web 应用都无法防。
- 有权限的运维人员直接读数据库文件——本期靠审计日志留痕，不靠加密。
- 应用层 DDoS——单机部署，靠前置 Nginx 限流与上游清洗，不属本应用职责。
- 供应链攻击——靠锁版本 + 依赖体积控制降低概率，不做完整 SCA（见 §7）。

**#38 是容易漏的一项**：gin 的默认行为是**信任所有代理**。若保持默认，客户端只要自己加一个 `X-Forwarded-For` 头，就能同时做到两件事——绕过登录限流（每次换一个伪造 IP）、把审计日志里的操作人 IP 写成任意值。因此这里不是「配置优化」，而是**限流与审计是否可信的前提**。

> ⚠️ 顺带记一个**实测踩过的坑**（P5 期间）：给只挂 `internal: true` 网络的服务加 `ports`，

### 2.9 报告导出（P5）

> 报告必须自己能回答「这是谁什么时候导出的」。

### 2.10 整改跟踪（P6）

前九个阶段的数据都是**事实**（资产、漏洞、风险值、报告）。P6 引入的是一类新东西：
**人对事实做出的承诺** —— 「这个漏洞要修、我负责、下周五之前」。

承诺有两个区别于事实的性质，它们决定了这一节的每一项在防什么：

- **承诺会被悄悄丢掉。** 一张整改单指向的风险项可能因为「又算了一遍」而消失
  （P4 的 `calculate` 是先清后写，`risk_items.id` 整批换新）。事实消失了没人会惊讶，
  但**承诺的凭据消失了**就意味着「有人答应过要修」这件事再也没人知道。**#76** 防的就是这个。
- **承诺的变更本身就是记录。** 「谁在什么时候把单子从『已整改』打回成『整改中』」
  才是整改工作的主干信息。**#79 #80 #81** 防的是「改了但查不出来」。

> **#76 是这一节的核心，也是最容易被写错的一条。** 一个把 `risk_item_id` 当业务身份的实现，
> 在**第一次重算之前**与正确实现完全一样：建单成功、列表有数据、详情能打开。
> 差别只在重算之后才出现，而那时的表现是「详情页的『来源风险项』一栏空着」——
> 不报错、不告警、日志里什么都没有。这正是 `docs/01` §2.6「界面值 = 落库值 = 报告值」
> 那条铁律在**写操作**上的对偶：读的时候数字要一致，写的时候**凭据不能悄悄消失**。
>
> **#85 与 #84 是一条线上的两件事**：逾期不落库是因为「落库就需要一个每日任务去翻，
> 而任务停跑时库里的数字会静默说谎」——这与 #84「失败请求不留审计」同属
> 「**宁可没有数字，也不要一个错的数字**」这一类取舍。

### 2.11 扩展模块：出站请求与情报源（P7）

前面十节的输入都来自**我们自己**（用户填表、上传的文件）。P7 引入的是第一类
**由用户决定「服务器去哪」**的输入 —— `integrations.base_url`。

这一节的所有控制项都在防同一件事：**把「拉取情报」这个动作变成「让这台服务器替我发请求」**。
SSRF 的价值来自不对称性 —— 攻击者用自己的机器连不上 `10.0.0.5`，但让这台服务器去连
就能连上，而且带着服务器的网络身份与信任关系。另外两个次级目标：

- **凭据不落任何持久化介质**（库、审计、错误信息、日志都是会流出的东西，环境变量不会）；
- **拉取这个动作可追溯**（谁、何时、向哪个地址、拉了什么、成没成）。

> 「不写进去」不需要有人在每个出口都记得擦。

> 让「没发生的事」不留痕迹**。所以配置不许删（审计指着它），而 4xx 不写审计
> （它没发生业务动作）。

## 3. 口令与凭证存储

**用的是 argon2id，不是 bcrypt。** 这一点值得单独写明，因为两种算法在参数语义上完全不同，混用会写出「看起来配了强度、实际很弱」的代码。

| 参数 | 取值 | 说明 |
|---|---|---|
| 算法 | `argon2id` | 兼顾 GPU 抗性与侧信道抗性 |
| 内存 `m` | 64 MiB（65536 KiB） | 高于 OWASP 最低建议 19 MiB，GPU 爆破性价比大幅下降 |
| 迭代 `t` | 2 | |
| 并行 `p` | 2 | |
| 盐长 | 16 字节 | 每用户独立随机盐 |
| 派生密钥长 | 32 字节 | |
| 单次校验耗时 | 约 100 ms | 对登录接口完全可接受，同时天然限制了暴力破解速率 |
| 存储格式 | PHC 字符串 | `$argon2id$v=19$m=65536,t=2,p=2$<salt>$<hash>` |

**为什么用 PHC 格式而不是自己拼接**：参数随哈希一起存储，将来提高强度时旧哈希仍可校验，不需要强制全员改密。如果只存 `salt:hash`，改参数就意味着所有存量口令失效。

**口令长度双向设限**（`auth/password.go:52`）：

- 下限 8 位（按 **rune** 计数，避免中文口令被字节长度误判成合格）
- 上限 128 位——上限不是为了「安全」，而是为了**防超长口令 DoS**：argon2 对输入长度敏感，128 位以上没有任何安全收益，只会让攻击者用超长密码消耗 CPU。

**解析哈希时的护栏**（`decodeHash`）：`m > 1<<20` 直接判为格式非法。防的是「数据库被人塞进一条 `m=99999999` 的记录，之后每次登录都吃光内存」——离线拿到写权限才算数，但成本极低，值得加。

## 4. 防滥用：两条互补的线

只有一条防线是不够的，因为两种攻击模式的形状不同：

| 防线 | 拦什么 | 配置项 | 默认值 |
|---|---|---|---|
| 账号锁定 | 「盯着一个账号猛试」 | `SR_AUTH_MAX_LOGIN_ATTEMPTS` / `SR_AUTH_LOCK_DURATION` | 5 次 / 15 分钟 |
| IP 限流 | 「用一堆用户名轮着试」 | `SR_AUTH_LOGIN_RATE_LIMIT` / `SR_AUTH_LOGIN_RATE_WINDOW` | 20 次 / 15 分钟 |

调大 `LOGIN_RATE_LIMIT` 会让第二种攻击重新变得可行——这两个值不是「越大越宽松越好」，而是**安全与可用性的直接权衡点**。

限流器是进程内滑动窗口（`middleware/ratelimit.go`），不是 Redis。取舍已写明：单机部署下引入 Redis 只换来「重启不清零」，却多一个要运维的组件；将来横向扩容时换实现即可，接口不变。

### 4.1 两个必须记住的实现细节

这两个都是**实测踩出来的**，不是理论推测，改动相关代码前务必先读：

**① `RecordLoginFailure` 的字段顺序不可调换**（`repository/user.go:156`）

```sql
UPDATE users
SET locked_until = CASE WHEN failed_login_attempts + 1 >= ? THEN ? ELSE locked_until END,
    failed_login_attempts = failed_login_attempts + 1,
    ...
```

MySQL 的 `UPDATE` 是**从左到右求值，后面的表达式能看到前面赋值的结果**（标准 SQL 是取原始值）。所以若把自增放在前面，`CASE` 里的 `failed_login_attempts + 1` 会拿到自增后的值，等于多加一次——**结果就是提前一轮锁定**（第 4 次失败即锁）。

另外这里**不能用 GORM 的 `Updates(map)`**：它会对 map 的键排序，无法保证语句内的字段顺序。这也是为什么这段特意写成了原生 SQL。

**② 可信代理必须显式配置** —— 见 §2.5 #38。

以下条件任一不满足，`config.Validate` 会让**进程直接启动失败**（而不是打一条警告继续跑）：

| 条件 | 错误方向 |
|---|---|
| `auth.jwt_secret` 长度 < 32 | 启动失败 |
| `auth.jwt_secret` 等于开发默认值 | 启动失败 |
| `auth.cookie_secure = false` | 启动失败 |
| `auth.bootstrap_password` 未设置或等于开发默认值 | 启动失败 |
| `database.password` 为空 | 启动失败 |
| `internal.shared_secret` 长度 < 16 | 启动失败 |
| `server.cors_origins` 为空 | 启动失败 |
| `server.trusted_proxies` 含 `0.0.0.0/0` 或 `::/0` | 启动失败 |

**为什么用「启动失败」而不是「警告」**：配置类安全项一旦以警告形式存在，就一定会在某个赶时间的发版里被忽略，然后一直忽略下去。

**环境隔离说明**：五个端到端验证脚本都**不碰开发库**，各自建一个隔离临时库，退出时整体 `DROP`（`trap cleanup EXIT`，另挂 INT/TERM 兜底），引导口令由脚本自己临时指定：

| 脚本 | 临时库 | 端口 |
|---|---|---|
| `verify-auth.sh` | `sec_risk_auth_e2e` | 18081 |
| `verify-web.sh` | `sec_risk_e2e` | 18082（API）/ 4173（前端预览） |
| `verify-asset.sh` | `sec_risk_asset_e2e` | 18080 |
| `verify-style-check.sh` | `sec_risk_style_e2e` | 18083（API）/ 5174（dev server） |
| `verify-file.sh` | `sec_risk_file_e2e` | 18084（API）；**上传目录也隔离**到 `/tmp/sr-file-uploads` |
| `verify-assess.sh` | `sec_risk_assess_e2e` | 18085 |
| `verify-report.sh` | `sec_risk_report_e2e` | 18086 |

三件事决定了必须这么做：

1. 引导口令只在「系统内一个账号都没有」时生效。不隔离就得知道开发库里那个管理员的口令，让验证脚本依赖一个开发期口令，既别扭又不可靠——口令一改，脚本就静默失效。
2. 验证过程会创建账号、禁用账号、往审计表写记录。跑在开发库上就是往真实数据里掺测试垃圾，而且**事后删不干净**。旧版 `verify-auth.sh` 跑在开发库上，用「把账号置为 disabled」充当清理，账号行仍然留在 `users` 表里，跑十次就积四十个——「清理」本身成了污染源。改成隔离库后，清理不再是打补丁，而是整体销毁。
3. **落盘文件也必须隔离**（P3 新增）。上传验证会在磁盘上真的写出文件，若指向默认的 `./storage/uploads`，每跑一次就留下几份样本；而它删不掉，因为「删掉临时库的 scan_files 行」并不会删磁盘文件。所以 `verify-file.sh` 把 `SR_STORAGE_UPLOAD_DIR` 也指到临时目录，退出时随库一起 `rm -rf`。

端口避开 8080 是同一个理由的另一面：脚本启动前会 `free_port` 掉端口占用者（防止断言打在残留的旧进程上），占 8080 就会顺手把开发者正在跑的后端一起杀掉。

**一条容易误解的检查**：`verify-web.sh` 里对后端的预检**必须带 CSRF 令牌**。不带令牌的探针只能证明「CSRF 中间件在拦人」，看着像在工作，实际什么都没测到（会被当成「后端已就绪」放过去）。

建议与前六条一起做 —— 其中 **#88 最值得优先补**：它是唯一一条验证「数据库级兜底
真的在工作」的断言，而服务层的「先查后插」在并发窗口前是无效的。
P7 新增的三条里，**#111（只读账号的能力边界）最值得优先补**：它只有「低」成本，
却一次钉住两件事 ——「MCP 不是后门」与「能力边界由后端 RBAC 决定」。
#110 同为「低」，两条可以一起做。

> **P5 / P6 / P7 那几条缺口有个共同形状**：它们防的都是**「没有行为的行为」**——
> 不落盘、不写第二条审计、不执行注入、不截断超长文本、不越过 500 条上限、
> 不跟随重定向、不把入参写进日志。这类约束在代码评审里最难被看出来
> （因为「没写」在 diff 里不留痕迹），也最需要一条断言钉住。
>
> P7 的 #95 还多一层：它是**「离线测不了」**而不是「忘了测」——
> 隔离的测试服务都在 127.0.0.1 上，而那个地址恰好被我们自己的第二层防护拒掉。
> 这条只能靠「把拦截逻辑抽小 + 单元级测试」绕开，写在这里以免下次又当成「忘了补」。

**这份清单的用途**：任何人改动上述控制点（尤其是 `config.Validate`、`middleware/audit.go`、`service/auth.go` 的登录路径）时，要意识到**没有测试会因你改错而变红**。

## 8. 变更守则

以下八类改动**必须**同步更新本文档与其验证脚本，否则视为未完成：
（这一句里的数字此前一直是「四类」，而条目已经涨到 7 条都没跟上 —— 记账口径同样适用于正文标题。）

1. **新增公开端点** → 登记进 `router.PublicRoute`，并确认确实不应认证（测试会强制对齐）。
2. **新增权限码** → 登记进 `auth.allPermissions`，否则启动自检失败；同时补进 OpenAPI 的 `PermissionCode` 枚举（`TestContractCoversEveryPermissionGuard` 会比对）。
3. **新增写接口** → 在 handler 里显式声明审计归属，否则联调时会打「未记录审计」Warn。三种状态别混用：
   `MarkAuditRecorded`（服务层已经写了审计）/ `MarkAuditSkipped`（按设计就不该写，如各类 `preview`）/
   不声明（由中间件按通用规则记录）。写在 handler 的**最前面**，理由见 `docs/04` §5.3、`docs/06` §8.3。
4. **调整安全相关配置项** → 同步 `.env.example` 与 `config.setDefaults`，并确认生产强制校验是否需要跟着改。
5. **新增任何「数据出厂」的出口**（导出、下载、外发）→ 三件事一起做，缺一视为未完成（理由见 §2.9）：
   ① 用 **POST** 而非 GET（GET 天然豁免 CSRF，且能被 `<a href>`、预取器触发）；
   ② **写审计**，且明细要能独立回答「谁、什么时候、导了什么、多大」——报告一旦被转发，日志就不在它身边了；
   ③ 产物**不落盘**，或落在 Nginx 直接 403 的目录里。
6. **改动内部渲染上游的网络暴露面** → 记牢 `docs/10` §6.2.1：本地调试覆盖文件**不得**命名为 `docker-compose.override.yml`（compose 会自动加载，让调试配置在生产一并生效）。给只挂 `internal: true` 网络的服务加 `ports` 会被 Docker **静默丢弃**，症状是「配置看起来全对、只有点导出才 503」。
7. **新增任何「记录人的承诺」的数据**（工单、审批、待办、结论）→ 四件事一起做（理由见 §2.10）：
   ① 业务身份**不依赖任何会被重算 / 重建的 ID**（P6 的教训：先清后写会换 ID）；
   ② 展示一律走**快照列**，出处（评估 / 风险项 / 上游单据）允许失效；
   ③ 每一次状态变更**留痕**，含操作人**快照**——账号改名不改写历史；
   ④ 状态机的**终态无出边**，需要重开时新建一条。
8. **新增任何「让服务器主动向用户指定的地址发起请求」的能力**（情报源、Webhook、回调、
   导入远端文件）→ 五件事一起做，缺一视为未完成（理由见 §2.11 与 `docs/07` §6）：
   ① **按解析后的 IP 判，不按字符串**——`0x7f.1` / `2130706433` / `[::ffff:127.0.0.1]`
      这类写法能绕过任何字符串黑名单；解析出**全部**地址逐个校验，不能只取第一个；
   ② **必须在 `connect` 之前再复核一次实际 `sockaddr`**（`net.Dialer.Control`）——
      预检与连接之间的时间差足够让 DNS 变脸（rebinding / TOCTOU）；
   ③ **禁跟随重定向、禁代理**，并限制响应体大小与超时——重定向能把公网善意地址
      302 到 `169.254.169.254`，跟随等于把①②全部作废；
   ④ **凭据只存环境变量名，且限定固定前缀**——放开自由度等于开出一个
      「读取进程内任意环境变量」的原语；出口处另加 sanitize 兜底；
   ⑤ **每一次出站都留审计，明细里记「实际去向的地址」**——只在配置页看当前值是不够的，
      因为配置可以被改。

> **为什么编号不会重排（以及 07 曾经为什么是空号）**
>
> 文档编号是**稳定标识符**，不是排序号 —— 不因内容变化或增删而重排。
> 全仓库有 **205 处** `docs/NN` 形式的交叉引用
> （`grep -o "docs/[0-9]\{2\}" docs/*.md README.md | wc -l`，2026-10-12 P7 收口终测）；
> 让 07 之后的编号往前挪一位，会让这些引用**全部指错文件**，而这类错误**不报错**：
> 链接照样可点，只是跳到另一个文档，读的人按错的依据干活。
>
> `07` 是立项时（v1.0 §3 的规划目录树）就为 **P7 扩展模块**预留的编号。
> **P7 之前它一直是空号**（属预期状态，不是漏号），P7 完成后已按其原始编号落位。
> 同理，「风险计算模型」从规划的 03 挪到实际的 `11`、「部署手册」从规划的 06 挪到 `10`，
> 都是**换编号而不是改标题**，也是为了避免连锁改动。
>

## 1. 项目概述

### 1.1 定位

面向企业/团队内部使用的网络安全风险评估系统，打通「资产梳理 → 扫描报告导入 → 风险量化 → 整改跟踪 → 报告输出」全流程闭环，并为后期接入第三方威胁情报 API、对外暴露 MCP 能力预留扩展位。

### 1.2 目标与验收标准

| # | 目标 | 验收方式 |
|---|---|---|
| 1 | 多用户登录 + 角色权限（管理员/评估员/只读） | 不同角色登录后菜单与接口权限差异符合预期 |
| 2 | 资产台账管理 + Excel 批量导入 | 导入 500 行资产成功，错误可定位到具体行号 |
| 3 | 文件上传与扫描报告解析 | 上传 Nessus / OpenVAS / 通用 Excel 均可解析出漏洞列表 |
| 4 | 风险评估计算 + 风险矩阵可视化 | 按 GB/T 20984 相乘法算出风险值并落库，热力图可下钻 |
| 5 | 报告导出（Word / Excel / PDF） | 导出文件可正常打开、中文不乱码、图表正常 |
| 6 | 本机一键运行 | 单条命令拉起全部服务，浏览器可访问 |
| 7 | 生产环境部署上线 | 服务器一键起，公网 HTTPS 可访问 |
| 8 | 预留第三方 API / MCP 扩展位 | 有独立模块与配置表，不改核心代码即可接入 |

**端到端验收路径**：初始化管理员 → 登录 → 录入资产 → 上传报告 → 创建评估 → 导出报告 → 查看审计日志。

### 1.3 范围边界

**本期做**：资产管理、报告解析、风险评估、整改跟踪、报告导出、用户权限、审计日志、第三方 API/MCP 骨架、生产部署。

**本期不做**：主动扫描探测（不集成 nmap 主动扫描，只解析已有报告）、LLM 智能分析（仅预留接口）、多组织多租户隔离、移动端适配、工单系统对接。

## 2. 技术方案

### 2.1 架构总览

```
浏览器 (Vue 3 SPA + Element Plus)
      │  HTTPS
      ▼
   Nginx ──── 静态资源 (dist)
      │
      │  /api 反向代理
      ▼
  Go 主服务 (Gin) ── GORM ── MySQL 8.4
      │
      ├─ 文件存储（本地卷，与 Web 根物理隔离）
      ├─ 报告解析（标准库 encoding/xml + excelize）
      ├─ Excel 导出（excelize）
      ├─ PDF  导出 ──► Gotenberg 容器（Chromium 渲染 HTML → PDF）
      └─ DOCX 导出 ──► C# docgen 服务（raw OpenXML SDK → 二进制流）
```

`docker-compose.yml` 编排 5 个容器：

| 容器 | 职责 | 对外暴露 |
|---|---|---|
| `mysql` | MySQL 8.4 LTS | 否（仅内网） |
| `server` | Go 主服务（API + 解析 + 风险计算 + 编排） | 经 Nginx |
| `web` | Nginx：静态资源 + /api 反代 | 80 / 443 |
| `gotenberg` | HTML → PDF | **否（仅内网）** |
| `docgen` | JSON → DOCX（C# / .NET 10） | **否（仅内网）** |

本机开发与服务器生产共用同一份编排，仅通过 `.env` 区分环境。

### 2.3 安全基线（Web 形态强制要求）

1. **会话**：Access / Refresh 令牌存放 httpOnly + Secure + SameSite=Lax Cookie，配 CSRF 双提交令牌；Refresh 令牌落库、支持轮换与吊销；**禁止写入 localStorage**
2. **密码**：argon2id 哈希；首次初始化管理员强制改密；登录失败限流 + 账号锁定
3. **上传**：扩展名 + MIME + 文件魔数三重校验；文件名 UUID 化；存储目录与 Web 根物理隔离；Nginx 对上传目录返回 403 并禁止任何解析执行；单文件与总量限额
4. **XSS**：后端存储层过滤 + 前端默认转义；禁用 v-html，确需渲染时过 sanitize；下发 CSP 响应头
5. **传输**：生产强制 HTTPS（HSTS），生产环境 Cookie 带 Secure
6. **访问控制**：中间件级 RBAC，前端仅做体验层隐藏，**权限判断以后端为准**
7. **数据库**：GORM 参数化查询，**禁止字符串拼接 SQL**；数据库账号最小权限；所有查询把过滤条件下推到 SQL，**不在应用层全表捞出后过滤**
8. **审计**：所有写操作落 audit_logs（操作人、IP、对象、前后值、时间）
9. **Nginx**：server_tokens off，安全响应头（CSP / X-Frame-Options / X-Content-Type-Options / Referrer-Policy）
10. **密钥**：全部走环境变量，.env 不入库，仓库提供 .env.example
11. **内网服务隔离**：gotenberg 与 docgen **不映射任何端口到宿主机**，仅在 Compose 网络内可达；Go 调用时附加共享密钥请求头做二次校验
12. **容器**：一律非 root 用户运行；docgen 无数据库连接、无状态、不持有任何业务数据
13. **docgen 输入校验**：只接受符合契约的 JSON，渲染器内部对字段做边界校验；**不执行任何用户提供的模板/表达式**（杜绝模板注入与 RCE）

### 2.5 ⚠️ Element Plus × Tailwind CSS v4 共存方案（P0 必须定稿）

> **重要前提**：换用 Element Plus **并不能消灭这个风险**，两类冲突在两库上完全相同。选它的真正理由是**有生产验证过的方案可照做**，工程确定性更高。

**冲突的两个层面**

| 冲突层 | 现象 | 根因 |
|---|---|---|
| ① preflight 重置 | el-button 背景变透明、el-input 边框消失、el-icon 垂直对齐异常 | Tailwind preflight 用元素选择器重置了 button / input / img 的默认样式 |
| ② 层级优先级 | `<el-button class="w-full">` 这类工具类**覆盖不动** Element Plus 样式 | **Element Plus 的 CSS 是 unlayered（无层）的，而 CSS 级联规则中「无层样式永远压过 @layer 内的样式」**；Tailwind v4 的 utilities 全在 @layer utilities 里 |

**为什么两个常见方案无效**

- `prefix: 'tw-'` —— 只改类名，**对 preflight 的元素选择器重置完全无效**
- 全局 `!important` —— 会破坏 .el-button--primary:hover 这类状态伪类，且后续无法判断哪条规则真正生效

**✅ 采用方案：CSS @layer 分层 + 自研 Vite 插件**

核心思路：把 Element Plus 的 CSS **打包进 @layer el**，并让该层排在 utilities **之前** —— 这样 Tailwind 工具类即可正常覆盖组件样式。

新增 `web/plugins/vite-plugin-css-layer.ts`：

```ts
// 作用：将 element-plus 的 CSS 模块包裹进 @layer el { ... }
//      并保证 utilities 层级高于 el，使 Tailwind 工具类可覆盖组件样式
// 参考实现：Vue Vben Admin 的 viteCssLayerPlugin
```

**⚠️ 关键工程细节（踩坑记录，必须照做）**

层顺序声明**不能**在 transform 阶段随包层 CSS 一起输出 —— 构建器（rolldown-vite）的 CSS 合并会把「层顺序声明 + @layer 规则」形式的模块拆层，且产物压缩阶段会**丢弃该声明**。因此必须改在 **generateBundle 阶段对最终 CSS 产物统一注入**层顺序声明。这样无论 chunk 加载顺序如何，层优先级都正确。

**若忽略此细节**：本地开发一切正常，**打包上线后样式全乱**，且极难排查。

样式入口 `web/src/styles/index.css`：

```css
@layer theme, base, el, components, utilities;

@import "tailwindcss/theme.css" layer(theme);
/* 关闭 preflight：避免重置 Element Plus 依赖的原生 button/input/img 默认样式 */
/* @import "tailwindcss/preflight.css" layer(base); */
@import "tailwindcss/utilities.css" layer(utilities);

/* 手动补齐必要的基础重置，保证跨浏览器一致性 */
@layer base {
  *, *::before, *::after { box-sizing: border-box; }
  body {
    margin: 0;
    font-family: system-ui, -apple-system, "PingFang SC", "Microsoft YaHei", sans-serif;
  }
}
```

**团队使用纪律（写入开发规范，Code Review 必查）**

- Tailwind 工具类**只用于布局、间距、响应式、显隐控制**；p-* / border-* / bg-* / font-* **禁止**直接加在 el- 组件上
- 微调组件外观用 CSS 变量（--el-color-primary 等）或 :deep(.el-xxx) 显式覆盖
- 禁止全局 !important

**P0 守门验证（3 条必须同时通过）**

1. el-button 背景不透明、el-input 边框正常、el-icon 垂直对齐正常
2. **`<el-button class="w-full">` 工具类能生效** → 证明分层优先级正确
3. `<div class="flex gap-4">` 等纯布局类正常生效

### 2.6 ⚠️ 风险计算归属与前后端契约

**问题**：原方案前后端共用一份风险引擎（同一份 TS 代码），结构上保证「界面预览值 = 报告落库值」。后端改 Go 后跨语言无法共享，若双端各写一份实现，必然出现**同一资产在界面显示「高风险」、导出报告写「中风险」**——在风险评估系统里这是致命缺陷。

**解决方案**

1. **风险计算只在 Go 主服务**，前端不做任何风险计算
   - 评估页调整参数 → 调 POST /api/assessments/preview → 后端返回算好的风险值、等级与矩阵数据
   - 参数与阈值只维护一处；评估属低频操作，前端加防抖即可，体验无损
2. **OpenAPI 作为契约唯一真相源**
   - Go 侧 swag 注解 → spec → 前端 openapi-typescript 生成 TS 类型
   - C# 侧 Microsoft.AspNetCore.OpenApi → spec → Go 侧生成客户端（或手写瘦客户端 + 契约测试）
3. **packages/shared 已整体取消**

**P4 强制验收**：同一份数据，界面显示值、数据库落库值、导出报告值**三者必须完全一致**。

### 2.7 ⚠️ C# docgen 服务设计（Word 生成）

#### 2.7.1 架构铁律

**docgen 服务只做「结构化数据 → docx」，绝不放任何业务逻辑。**

- ❌ 无数据库连接
- ❌ 无用户体系、无权限判断
- ❌ 不做风险计算
- ✅ 无状态：相同输入必得相同输出
- ✅ 可独立部署、独立重启、独立压测

这样它才能安全地作为内网工具服务存在，不会成为绕过权限的后门。

#### 2.7.2 接口契约

```
POST /api/v1/render/docx
Content-Type: application/json
Header: X-Docgen-Token: <共享密钥>
Body:
{
  "template": "risk-assessment",     // 渲染器名称
  "traceId": "<uuid>",               // 日志关联
  "data": { ... }                    // 结构化数据（评估结果、资产、风险项、整改建议）
}
→ 200
Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document
Body: <docx 二进制流>
```

附加端点：GET /health、GET /openapi/v1.json（spec）

大报告若生成超过 5 秒，可增加异步模式（202 + jobId + 轮询 GET /jobs/{id}/result）——**本期不实现，留接口位**。

#### 2.7.3 模板策略（关键设计）

raw OpenXML SDK 意味着「文档树由代码构造」。两种做法：

| 做法 | 说明 | 评价 |
|---|---|---|
| (a) 纯代码构造 | 样式与结构全部写在 C# 里 | 完全可控，但**版式迭代必须改代码、重新发版** |
| (b) **外置 docx 模板 + 占位符替换 + 动态插入** | 版式由业务/设计在 Word 里设计好（封面、页眉页脚、字体、样式），代码只负责填数据与生成动态表格 | ✅ **采用**：版式迭代零发版 |

**采用 (b) 为主 + (a) 兜底**，因为安全评估报告的核心难点是**动态内容**：

- 风险项表格行数不固定 → 必须用 OpenXML 代码动态生成行
- 风险矩阵存在合并单元格 → 必须代码控制 GridSpan / VerticalMerge
- 章节数量随评估范围变化 → 必须代码控制分节

**纯占位符替换做不到这些**——这正是必须用 OpenXML SDK 而非简单模板替换的原因。

#### 2.7.4 ⚠️ 实战踩坑清单（静默失败，最难排查，必须写进开发规范）

| 坑 | 后果 | 正确做法 |
|---|---|---|
| **中文字体名用中文** | 中文不生效且不报错 | 用英文名 SimSun / Microsoft YaHei；RunFonts 的 Ascii 与 EastAsia 分别设置 |
| **自定义样式未注册到 StyleDefinitionsPart** | 引用 StyleId **编译通过、运行不报错、样式就是不生效** | 必须先注册再引用 |
| 字号单位是 half-point | 所有文字小一半 | 16pt 要写 Val="32" |
| 连续空格被折叠 | 排版错位 | Text.Space = SpaceProcessingModeValues.Preserve |
| 缩进单位是 twip | 间距全错 | 1 厘米 ≈ 567 twip，1 英寸 = 1440 twip |
| ParagraphBorders 与 TableBorders 混用 | 编译通过但无效果 | 两者是完全不同的类 |
| 表格跨页表头不重复 | 多页报告不可读 | 设置 TableHeader |
| 图片直接嵌 Body | 无效 | 必须经 ImagePart + Drawing 引用 |
| 每个 Section 默认共享页眉页脚 | 多章节页眉相同 | 用 DifferentFirstPageHeaderFooter 区分 |

**调试技巧**：把 .docx 改名为 .zip，直接查看内部 XML —— 这是定位样式问题最快的手段。

### 4.2 风险计算模型

**主模型（GB/T 20984 相乘法）**

```
风险值 R = 资产价值 A × 威胁发生可能性 T × 脆弱性严重程度 V
```

- A / T / V 各取 1–5 级，权重与等级映射写入 system_configs，**可在系统设置中调整，不写死在代码里**
- R ∈ [1, 125]，按阈值映射为 5 档：很高 / 高 / 中 / 低 / 很低
- 风险矩阵热力图仅用于**可视化呈现**，不参与计算

**引擎实现要点（Go 侧唯一实现）**

- 位置：`server/internal/pkg/riskengine`，纯函数、无副作用、不依赖数据库与 HTTP
- 全系统**仅此一份**实现，前端与 docgen 均不重复实现
- 单测重点覆盖：边界值（R=1 与 R=125）、字典项缺失、权重为零、批量计算一致性、阈值边界

### 11.4 P1 排掉 / 暴露的四个问题

1. **「登出后旧令牌仍可用 15 分钟」** —— JWT 无状态的固有短板。
   解法是 `users.token_not_before` 生效下界 + 毫秒级 `iat_ms` 声明
   （JWT 标准 `iat` 只有秒精度，同秒内登出再登录会误判）。
2. **前端并发刷新会被自己判定为重放** —— 刷新令牌轮换是**前后端成对设计**：
   后端必须做重放检测，前端就必须做单飞刷新（`refreshInFlight`），
   否则同时发出的两个请求会让第二个触发全链吊销，把用户直接踢下线。
3. **`/api/roles` 泄漏模型字段名** —— `model.Role` 无 json tag，
   直接序列化输出 PascalCase 的 `Code` / `Name` / `IsBuiltin`。
   修法是新增 `roleView` 显式定义对外契约，并补 3 项 e2e 回归断言防止退回。
4. **「无权限看不到菜单」曾是假通过** —— `el-sub-menu` 折叠时子树 `display:none`，
   而 `textContent` 无视 `display`，会把隐藏项算进来。
   修法是断言前先展开所有分组、并用 `innerText` 取文本。

### 11.5 对 P0 产出的一处修正

**CSS 分层校验规则过严，导致误报。**

初版规则是「每个 CSS 产物都必须包含 `@layer el`」。P1 引入路由分包后，
`LoginView-*.css` 里 0 个 `.el-` 选择器（EP 样式被提升到共享 chunk），
必然报「未找到 `@layer el`」——**这条规则问的是实现细节（chunk 怎么切），
而不是失效模式本身**。

修正后的规则：**产物中出现的 `.el-*` 选择器必须全部位于 `@layer el` 之内**。
另外判据必须是 `.el-` 类选择器而**不是** `--el-` CSS 变量——
业务 base 层合法使用 `var(--el-text-color-primary)`，用变量名判定会误伤。

同时补了负向验证：手工造一个 `.el-button{color:red}` 探针文件，校验**必须**失败。
详细推理记录在 `docs/08-前端样式规范.md` §4.4。

### 12.4 P2 排掉的一个 P0 级 bug 与三处不一致

**1. 【真 bug，P0 级】物化路径的子树查询用 ID 拼前缀。**

子树查询的前缀从前是 `"/" + id + "/"`，而 `path` 存的是**完整祖先链**。
因此只对根组成效，对任何一层子组都**静默返回 0 行**。两个症状都不指向
物化路径：「按分组筛选返回 0 条」（像前端筛选条件传错了）、
「删除仍有资产的组报 500 而不是可读的 409」（像外键或事务问题）。

修法是把签名改成 `SubtreeIDsByPath(ctx, groupPath string)`——强制调用方
传该组自己的物化路径，**用类型系统堵死重蹈覆辙**。完整复盘见
`docs/04-资产与字典设计.md` §2.3。**这个 bug 只有端到端脚本能抓到**：
单元测试需要真实数据库，而单测里最容易写出的用例恰好是根组。

**2. 【契约与行为不一致】`ASSET_IMPORT_GROUP_NOT_FOUND` 永不可达。**

`create_missing_groups=false` 时每个未匹配的组同时也会让 `ErrorRows++`，
于是 commit 的 `ErrorRows > 0` 判断永远先命中，这个错误码**在任何输入下
都不会返回**——而契约里明确列着它。修法是新增 `groupOnlyBlockedRows`
统计「唯一问题就是缺组」的行，commit 时扣除后再判优先级。

**3. 【真 bug】只有表头的文件不被 `ASSET_IMPORT_NO_ROWS` 拦住。**

`spreadsheet.Read` 的 `ErrEmpty` 判据是「有没有非空行」，而**表头本身就是
一行非空行**，所以它不报错；随后 `dataRows := sheet.Rows[1:]` 是空切片，
循环一次都不跑 —— 预览返回「0 行 / 0 错误 / 0 合格」，commit 更糟：
它会写 0 条并报成功。修法是在 `parseImport` 里补 `len(dataRows) == 0` 判定。

**4. 【README 级的口径错误】`DICTIONARY_BUILTIN_READONLY` 的状态码。**

守门脚本初版期望 400，实际是 409。核对契约后确认**代码是对的**：
请求本身没毛病，是「当前状态不允许」，与 `ASSET_NO_TAKEN` /
`ASSET_GROUP_NAME_TAKEN` 同属 `Conflict`。改的是脚本的期望值。

### 12.5 P2 期间对 P1 产出的一处修正

**写请求「按设计不该有审计」的情况无法声明。**

P1 的审计中间件只认两种状态：由中间件写入、或由服务层写入
（`MarkAuditRecorded`）。P2 的 `POST /assets/import/preview` 是第三种——
**必须用 POST 传文件，却不改变任何状态**，因此审计按设计就不该写。

不区分的话，每一次导入预览都会打一条「本次操作不会留下审计记录」，
把真正漏审计的情况淹掉。修法是新增 `reqctx.MarkAuditSkipped`，
与 `MarkAuditRecorded` **分开**（前者的语义是「不该写」，不是「已经写了」），
中间件见到它就早退。`MarkAuditSkipped` 必须放在 handler 最前面——
`c.Next()` 之后中间件就要读它。

### 13.4 P3 排掉的三个真缺陷与一处口径错误

**1. 【真缺陷】`VULN_IMPORT_MISSING_COLUMNS` 被错配成 `VULN_IMPORT_NO_ROWS`。**

「表头少了一列」与「一行数据都没有」被同一错误码表示，前端只能弹一句含糊提示。
已新增独立错误码（与 P2 的 `ASSET_IMPORT_MISSING_COLUMNS` 对称），并在契约的
`ErrorCode` 枚举与 `BadRequest` 描述里同步登记。

**2. 【真缺陷】上传接口漏声明「审计已由服务层落库」。**

`FileHandler.Upload` 少了 `reqctx.MarkAuditRecorded(c)`，于是每次成功上传都打一条
「写操作既未由中间件记录、也未声明已由服务层落库」的 WARN。审计本身没丢
（服务层照常写），但这条告警从此成为常态，「真的漏了审计」就被淹掉。
**单测看不到这类问题——它只存在于日志里。**

**3. 【真缺陷】预览与 commit 的匹配口径分裂。**

`preview.matched_count` 数的是「匹配上的 IP 个数」，`commit.linked_auto` 数的是
「关联成功的漏洞条数」。同一个文件预览显示「可关联 2」、提交后报「自动关联 4 条」，
用户只会认为系统算错了。已统一为**漏洞条数**，并加了一条断言把等式钉死。

**4. 【口径错误，最危险的一类】等级词表缺「高危」。**

`中危` / `低危` 在表里，`高危` 漏了 → 中文表格里的「高危」被**静默降级**为默认
「中危」。不报错、不告警，只是把高危漏洞系统性低估。现已补齐 `高危` / `危急`。

> 四条的共性：**没有一条是单元测试能抓到的**。错误码语义、日志、跨阶段口径、
> 查表对称性——都要「把真实请求打进去、把真实日志读出来」才看得见。
> 这是每阶段配一个端到端脚本的根本理由。

### 14.3 实施期修正

**1. 【真缺陷，守门脚本抓到】`top_items` 从未排序。**

契约与 `Preview` 的注释都写着「风险值最高的风险项，最多 20 条」，
但 `build()` 只排序了**资产汇总**，风险项一直是数据库返回顺序（按 asset_id、vuln_id）。
执行页上所谓的"最该先看的 20 条"其实是前 20 条——不报错，结果也不"错"，
只是**展示的是别的东西**。已修 `build()` 末尾排序，并**重建 `TopItemIndex`**
（它存的是切片下标，`Calculate` 要用它取自增 ID；不重建会让 `top_item_id` 指错行）。
守门脚本加了「`top_items` 按 R 非递增」与「报告按 R 非递增」两条断言把它钉住。

**2. 【契约与实现不符，守门脚本抓到】`POST /vulnerabilities` 返回 200，契约写 201。**

`assets` / `dictionaries` / `asset-groups` 三个创建接口都是 201，只有漏洞创建用了
`response.OK`。P3 脚本恰好没断言这一码的具体值，所以从 P3 一直带过来。

**3. 【运行时崩溃风险】`preview` 的 `scope_ref` 在 `all` 范围下是 `null` 而不是 `[]`。**

Go 的 `nil` 切片序列化成 JSON 是 `null`。契约写的是「`all` 时为空数组」，
前端 `scope_ref.length` 会当场崩——而**编译期发现不了**（当时契约没标 `required`）。
服务层已显式非 nil 化；契约把一批必然返回的字段标为 `required`
（可空指「值可以是 `null`」，不是「key 可能缺席」）。

**4. 【已知语义，非缺陷】重算后风险项 ID 全部变化。**

`calculate` 是事务内「先清后写」，重算后是新插入的行。任何缓存风险项 ID 的地方
在重算后都必须重新拉取——前端结果页重算后重新加载列表是**必须**而非可选。
守门脚本把这条语义也钉成了断言。

**5. 【设计修正】风险项不建外键。**

`000004` 曾设想「P4 接入引用检查」（资产 / 漏洞被引用时禁止删除）。
实现时改为**逻辑引用 + 快照列**：一份三个月前的评估不该阻止用户删掉一条误录入的漏洞，
删掉它也不该改写已发出的报告结论。两者不可兼得时选了「报告不可变」。

> 五条的共性：**1、2 两条单元测试抓不到**。排序缺失不报错、响应码偏差没有断言就是绿。
> 都要「把真实请求打进去、把真实数据比出来」才看得见——这是每阶段配一个端到端脚本的根本理由。

### 15.3 实施期修正

**1. 【真缺陷，守门脚本抓到】excelize 的类型断言写成了恒假式。**

单测与守门脚本都断言 `cellType == CellTypeNumber`，**恒不成立**。根因：`GetCellType`
直接返回 OOXML 的 `t` 属性，而**数值单元格在 OOXML 里根本不写 `t`** —— excelize 写数值时
显式置 `c.T = ""`，落到映射表零值上返回 `CellTypeUnset(=0)`；字符串才走 `t="s"`。
改用「**不属于文本类型集合**」并补一条**阳性对照**（同一张表的等级列必须被认成
`CellTypeSharedString`），后者用来证明断言机制本身有效。两个文件各修一处。

**2. 【环境缺陷，代价最大】`internal` 网络会**静默丢弃**端口映射。**

给只挂 `internal: true` 网络的服务加 `ports`，Docker 不报错、不警告、直接丢掉 ——
`docker port` 为空、`docker ps` 的 PORTS 列为空。事后 `docker network connect` 补一张
普通网络也**补不回来**（端口绑定在容器创建那一刻决定）。症状极具误导性：配置看起来正确、
容器健康、`make dev` 不报错，只有点导出才 503。

修法：dev 覆盖文件 `deploy/compose.dev.yml` 让两个渲染服务同时挂「普通网 + internal 网」
并映射回环端口；覆盖文件**不能**叫 `docker-compose.override.yml`（compose 会自动加载它，
从而让「暴露内部服务端口」在 `make up`（生产）时一并生效）。守门脚本把上游宿主可达性
放在第 0 节先查。

**3. 【设计修正】取数拆出无审计版本 `buildExportData`。**

若 `ReportService` 直接调 `ExportData`（带审计），审计表里会多出一条**没有发生过的**
`assessment.export`。改为 `ExportData = buildExportData + 审计`，报告走前者。
这同时钉死了「两条取数路径是同一份实现」。

**4. 【设计修正】`configForAssessment` 改为返回快照时间。**

原签名只返回 `riskengine.Config`。报告里要写「配置在计算时刻即被快照冻结，快照时间：X」，
用 `time.Now()` 去补会让这句话**在事实上说谎且不报错** —— 一份几个月后导出的报告
会声称它的配置是几分钟前冻结的。改为返回 `(Config, time.Time, error)`。

**5. 【设计修正】`ReportData.FooterText` 字段被删除。**

页脚是「这份文件何时生成」，只能由 `footerText(d)` 从 `GeneratedAt + 评估名` 推导。
暴露成字段意味着调用方可以传一个不一致的值，而那种错误不会报错。

**6. 【既有代码修正】`contentDisposition` 的兜底名写死为资产导入模板。**

它对文件下载与报告导出都不对（下载报告的人会拿到名为「资产导入模板」的文件）。
改为 `contentDisposition(name, asciiFallback)`，三个调用点各自给出正确的兜底名。

**7. 【前端结构修正】`api` 层新增 `download` 方法。**

计划里写的是「`exportReport` 解析 Content-Disposition」，隐含要用底层 http 实例。
实现时把请求核心拆成 `send()`（CSRF + 401 静默刷新 + 错误收敛）与 `request()`（拆信封）
两层，`api.download` 直接复用 `send` —— 否则 `reports.ts` 要手写 CSRF 并失去 401 重试，
用户长时间停留后点导出会看到「登录状态已失效」而不是自动续期后把文件给他。

> 1、2 两条的共性：**单元测试与「看起来对不对」都抓不到**。恒假的断言是绿的（换个方向
> 写成恒真也是绿的）；被静默丢弃的端口映射在容器层看不出任何异常。都要「把真实请求打进去、
> 把真实产物拆开来比」才看得见 —— 这是每阶段配一个端到端脚本的根本理由，也是 P5 的
> 脚本要解包 docx / xlsx / pdf 内部而不仅仅判断 HTTP 200 的原因。

### 16.3 实施期修正

**1. 【注释与代码不符，守门脚本抓到】`status` 与 `active` 同时给出时的优先级。**

`RemediationHandler.List` 的注释写着「以 active 为准」，而代码在 `status` 有值时把 `ActiveOnly` 置为 `false` —— **实际是 `status` 优先**。守门脚本按注释的语义写了断言（`?status=accepted&active=true` 应返回未闭环数），实测返回 `accepted` 的条数，把这个矛盾照了出来。

最终**保留代码行为、修正注释**：`status` 是元素级精确筛选，用户既然指名了一个状态，再叠一个集合级条件就是自相矛盾（`status=accepted` + `active=true` 没有交集）；遇到矛盾条件时无论保留哪个都会让用户看到「不是他要的结果」而查不出原因，而 `status` 更精确，以它为准是可解释的规则。守门脚本的断言同步改为「结果等于只按 `status` 筛」。

> 这条的价值在于：若只按实现写断言（而不按注释/计划的语义写），这个矛盾**永远不会被发现** ——
> 一条「按错误语义写的断言」与一条「按实现写的断言」都是绿的，区别只在于前者会失败。
> 详见 `docs/13` §9.1。

**2. 【约定修正】批量建单对草稿评估返回 409 而不是 400。**

草稿任务没有任何风险项。最初的直觉是「400 参数不合法」，但用户真正需要知道的是「先去算一次」，而 409 `REMEDIATION_BATCH_EMPTY`（「当前状态不允许」）的文案能承载这个信息。守门脚本按 409 断言。

**3. 【前端修正】`vue-echarts` 的样式是 unlayered 的，工具类高度类永远不生效。**

`vue-echarts/style.css` 给 `x-vue-echarts` 补 `display:block; width/height:100%`，它不受 `vite-plugin-css-layer` 的 `packages: ['element-plus']` 治理。后果有两个：① 必须**显式** `import` 该样式，否则自定义元素是 `inline`、图塌成 0 高度；② 在 `<VChart>` 上加 `h-64` 这类工具类**永远不生效**（工具类进 `@layer`，而 unlayered 规则优先级更高），高度一律设在外层 `<div>` 的内联 `style` 上。

**4. 【前端修正】`Me` 类型的主键字段是 `user_id` 而不是 `id`。**

「我的整改单」筛选最初写 `auth.user?.id`，`vue-tsc` 报 `TS2339`。改用 `auth.user?.user_id`（沿用后端契约命名），并且**不拉用户清单** —— 「我是谁」不需要多打一次请求。

**5. 【前端修正】`loadActiveRemediationMap` 的分页终止条件。**

初版用 `res.items.length < pageSize` 判断到底了；当总数**恰好是整页**（100 条 / `pageSize=100`）时会多跑一次空请求。改为 `map.size >= res.total`，并用 `maxPages` 兜底避免死循环（`eslint` 的 `no-useless-assignment` 顺带抓到了配套的未使用初值）。

**6. 【脚本修正】守门脚本里「管理员的 CSRF 令牌」必须单独保存。**

`SESSION_CSRF` 会被 `login()` 反复覆盖成「最后一次登录的账号」的令牌，而 `json()` 恒用管理员会话。脚本在创建审计员 / 评估员账号之后再调 `json()` 就会带上别人的令牌 → 403 `AUTH_CSRF_INVALID`，**看起来像权限问题**。更糟的是它会让「失败的流转不留下审计」这条断言因为请求根本没进业务层而**假绿**。修法是新增 `ADMIN_CSRF` 与 `SESSION_CSRF` 分开维护。

### 16.6 补记：命令式 API 样式缺失（P6 后修复）

P6 收口后接到一个用户侧缺陷报告：**退出登录的确认框没有样式**。定位结果是一处
从 P0 起就存在、且**一直被漏过**的按需引入盲区，不属于 P6 引入的问题，但落在
前端的样式治理范围内，在此留档。

**根因**：按需引入只解析**模板标签**。`<el-dialog>` 会顺带把 `el-dialog` 的样式带进来，
而 `ElMessageBox.confirm(...)` / `ElMessage.success(...)` 是**函数调用**，
走 `import { ElMessage } from 'element-plus'` 这条普通具名导入 ——
`unplugin-auto-import` 的 `ElementPlusResolver` 只在标识符**未被显式导入**时才注入，
代码里已经手写了 import，它就什么都不做，样式 import 从来没被生成过。

**为什么长期没被发现**：它不报错、不告警、不白屏。项目上百处用到几十种模板组件都正常，
只有命令式调用的两类组件是坏的 —— 而「退出登录」这种入口一天未必点一次。
实测证据（修复前）：`dist/assets/*.css` 里 `.el-message`、`.el-message-box` 相关类
**一个都没有**，而 `.el-overlay` 存在（被 `el-dialog` 顺带引入），
于是在浏览器里看到的正是「一层灰遮罩 + 一堆没有样式的裸 DOM」。

**修复**（3 处代码 + 1 份文档）：
| 文件 | 改动 |
|---|---|
| `web/src/main.ts` | 显式补 `message/style/css` 与 `message-box/style/css` 两条 import（含为什么的注释） |
| `web/scripts/verify-css-layer.mjs` | 新增第 ④ 项断言：**从源码扫出**实际用到的命令式 API，逐一对产物做存在性断言 |
| `web/src/views/dev/StyleCheckView.vue` | 新增第 10 项运行时断言：真的弹一个 `ElMessageBox`，量计算样式 |
| `docs/08-前端样式规范.md` | 新增 §2.4（落点 + 症状 + 新增命令式 API 的清单）；§4.4 三项→四项；§7 故障排查加两行 |

**守门设计与其可证伪性**：第 ④ 项的取材方式是关键 —— 它不写死「必须存在的类名清单」，
而是先扫出 `src/**/*.{ts,vue}` 里所有 `from 'element-plus'` 的具名导入再对照产物。
写死清单挡不住新坑：将来有人用 `ElNotification` 却忘了引样式，清单里没有它，校验器一声不吭。
两条负向验证都实测过：

```
# A. 源码里新用一个命令式 API 但不引样式 → 必须失败
printf "import { ElNotification } from 'element-plus'\n..." > web/src/__probe_guard.ts
node web/scripts/verify-css-layer.mjs
# → ✖ ElNotification 的样式不在产物中（找不到 `.el-notification__content`）  退出码 1

# B. 把产物里的规则抹掉 → 必须失败
perl -pi -e 's/\.el-message-box__content/_el-message-box__content/g' web/dist/assets/index-*.css
node web/scripts/verify-css-layer.mjs
# → ✖ ElMessageBox 的样式不在产物中（找不到 `.el-message-box__content`）    退出码 1
```

**顺带修正一处记账错误**：`docs/10` 与本文 §16 原先记的「**34 个** CSS 产物」是错的，
干净构建的实测值是 **32 个**。多出来的 2 个是**陈旧残留文件** ——
本沙箱的运行环境有一道「单次批量删除保护」，会拦下 `vite build` 清空 `dist` 的那一步，
构建仍然成功，但上一轮的产物会留在 `dist/assets` 里，`verify:css` 于是把残留也算进去。
`docs/10` §8.2 已补上「怎么判断 `dist` 是否干净」与「取准确数量的办法」两段。

### 17.3 实施期修正

**1. 【守门脚本】`BAD_RC` / `MCP_RC` 后紧跟中文标点导致 `unbound variable`。**

`ok "…（退出码 $BAD_RC，反向对照）"` 在非 C locale 下会把全角逗号的首字节并进变量名，
报 `BAD_RC�: unbound variable`。**症状具有严重误导性**：它不是断言失败，而是脚本在
MCP 那一节中途崩掉 → 后面的 4 条断言根本没跑，汇总表也没打出来。
修法是把 `${BAD_RC}` 加上花括号（这条陷阱项目里早就记过，写成 `$VAR` 时又踩了一次）。

**2. 【守门脚本】三处「断言本身写错了」，与实现无关。**

| 现象 | 真因 |
|---|---|
| 「列表一次返回全部集成」红了，期望 ≥5 实际 4 | 写死了魔法数字，而该节实际只建了 4 个集成。改为「条数 == 库里行数 且 > 1」 |
| 「全成功时 `last_status = success`」红了 | 读的是 §6 留在该集成上的**失败**运行态。运行态记的是「最后一次执行」而不是历史累计 —— 补一次全成功拉取后再断言 |
| 「列表里如实给出了变量名」红了 | `contains` 的第二个参数传成了**文件路径** `$BODY` 而不是文件内容。其余同类断言都写了 `"$(cat "$BODY")"`，只有这一处漏了 |

三条的共同形状：**它们红的都不是被测代码，而是断言自己写错了**。
一条会因无关原因变红的断言，作用只是训练人忽略红色 —— 这与 §12.1 记的是同一件事。

**3. 【守门脚本 + 单测】一处断言被标错了层，导致第二层防护没人测。**

§6 ⑧ 的标签原文是「**第二层**出站防护」，但它做的是「把库里的 `base_url` 直接改成内网」——
那条路径上地址本来就在内网，**第一层 `CheckEndpoint` 就先拒了**，根本走不到 `connect`。
也就是说 `net.Dialer.Control`（防 DNS rebinding 的那一层）**一条断言都没有**。

修法分两步：

- 改正脚本标签与 `docs/07` 的表述（标明它测的是「第一层在拉取路径上重跑」）；
- 给第二层补单测 `TestGuardedClientBlocksAtDialTime`：**直接让客户端**去连受限字面量地址
  （`CheckEndpoint` 不在这条路径上），断言错误是 `ErrEndpointBlocked` 而**不是**
  `connection refused` —— 后者意味着 `Control` 没生效。

**负向验证**（把 `Control` 的函数体改成 `return nil` 后立刻跑）：

```
--- FAIL: TestGuardedClientBlocksAtDialTime
    应当由 Dialer.Control 在 connect 之前拒绝（ErrEndpointBlocked），
    实际为 Get "http://127.0.0.1:9/": dial tcp 127.0.0.1:9: connect: connection refused；
    若为 connection refused，说明 Control 未生效 —— 那时 DNS rebinding 可以直接打到内网
```

这个负向验证正是本条的要点：**只断言「报错了」是不够的**，
端口没人监听同样会报错，那样即使 `Control` 整段被删掉也测不出来。

**4. 【MCP】`process.exit()` 会截断尚未落盘的 stderr。**

冒烟第 ⑤ 节有 4 条失败（`实际 null` 且 stderr 为空）。手工复现时原因输出**是正常的**
（只是耗时 11.62 秒，超过了当时 8 秒的护栏）—— 于是同时修了两处：

- `config.js` 的失败路径改用 `process.exitCode = 1; return`（与 `main().catch` 一致）。
  用 `exit()` 时「快速失败」这条设计只剩一半：进程确实挂了，但运维看不到原因；
- 冒烟重构：写开关真值矩阵与地址/超时矩阵改为**直接 import `loadConfig` 断言**（不起进程），
  真进程只留 1 条；超时护栏提到 60 秒并注明它是**护栏而非常性能阈值**（本机冷启动约 10 秒）。

**5. 【MCP】按契约修正了 `/auth/me` 的字段路径。**

原写法是 `me.user.username`，而契约里 `Me` 是**顶层**字段
（`user_id` / `username` / `roles` / `permissions` / `must_change_password`）。
这类错误不会报错，只会让启动日志里永远是 `undefined`。顺带补了一条
「服务账号仍处于『必须修改初始密码』状态」的告警 —— 该状态下绝大多数接口会被后端拒绝，
而症状是一堆莫名其妙的 403。

**6. 【文档】`docs/02` §11.3 第 3 条写错了。**

原文是「`ON DELETE CASCADE` 只出现在 `remediation_logs` 这一张表」——
实际 `user_roles` / `refresh_tokens` / `vuln_asset_links` / `risk_items` /
`assessment_assets` 都是 CASCADE。P7 收口时按
`grep -n "CASCADE\|RESTRICT" server/migrations/*.sql` 逐条核对后，改写成
**全库删除规则表 + 「谁是主体」的判据**（派生数据 CASCADE / 业务事实 RESTRICT）。
这类「把集合写死在正文里」的清单是文档最容易与实现分叉的地方。

**7. 【文档】`docs/05` §8 的「以下四类改动」与实际 7 条不符**，已改为「八类」并补上第 8 类
（**新增任何「让服务器主动向用户指定的地址发起请求」的能力** → 五件事一起做）。
第 8 类是本阶段最该被复用的产出：它把 P7 的全部约束压缩成一条可执行的检查表。

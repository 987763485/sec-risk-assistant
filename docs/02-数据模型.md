## 2. 实体关系

读法：`A ──< B` 表示 **B 持有指向 A 的外键**；`A >── B` 表示 A 持有指向 B 的外键。

```
【认证域】迁移 000002 / 000003 —— 逐字段见 §3–§6
  users ──< user_roles >── roles
    │
    └──< refresh_tokens              （按 family_id 成链，用于重放检测）

  audit_logs                         （刻意不与 users 建外键，见 §5）

【资产域】迁移 000004 —— 字段与理由见 docs/04
  asset_groups ──< asset_groups      （自引用 parent_id，ON DELETE RESTRICT）
        │
        └──< assets                    （assets.group_id → RESTRICT）
  dictionaries ⟵ assets.asset_type / assets.status
                                     （按字典 code 引用，**不建外键**，见 docs/04 §3）

【文件与漏洞域】迁移 000005 —— 字段见 §9，理由见 docs/06 §2
  scan_files ──< vulnerabilities     （source_file_id 可空 = 手工录入；RESTRICT）
                      │
                      └──< vuln_asset_links >── assets
                           UNIQUE(vuln_id, asset_id)；两侧 ON DELETE CASCADE

【风险评估域】迁移 000006 —— 字段见 §10，理由见 docs/11 §5
  assessments ──< risk_items         （assessment_id → CASCADE）
       │              UNIQUE(assessment_id, asset_id, vuln_id)
       ├──< assessment_assets        （assessment_id → CASCADE）
       │              UNIQUE(assessment_id, asset_id)
       └─ 持有 config_snapshot        （权重与阈值的时点快照，见 §10.1）

  risk_items >·· assets / vulnerabilities
        （**逻辑引用，刻意不建外键**：风险项是时点快照，
         展示走 asset_name / asset_ip / vuln_title 等快照列）

【整改跟踪域】迁移 000007 —— 字段见 §11，理由见 docs/13 §2
  remediations ──< remediation_logs    （remediation_id → CASCADE，唯一有外键的地方）
       │              （流转与变更记录：动作、from/to、说明、操作人快照）
       └─ UNIQUE(active_key)  ← 生成列，未闭环时 = "asset_id:vuln_id"，闭环后 NULL
                                （表达「同一 (资产, 漏洞) 只允许一张未闭环单」）

  remediations >·· assets / vulnerabilities / assessments / risk_items
        （**四个 ID 全部逻辑引用，不建外键**：整改单是**业务事实**，
         不随「又算了一遍」改变。asset_id + vuln_id 是业务身份，
         assessment_id + risk_item_id 只是**发现出处**，允许失效 ——
         因为 P4 的 calculate 是先清后写，重算一次 risk_items 的 id 整批换新。
         见 docs/13 D1，那是 P6 的头号陷阱）
```

**四处**「没有外键」是刻意的，不要顺手补上：

- `audit_logs.user_id` —— 审计留存优先于账号本身，见 §5.1。
- `assets.asset_type` / `assets.status` —— 存字典 `code` 而非字典主键，见 `docs/04` §3.2。
- `risk_items.asset_id` / `risk_items.vuln_id` —— 风险项是**时点快照**：
  建 CASCADE 会让「删一条漏洞」顺带改写历史报告，建 RESTRICT 又会让一份三个月前的
  评估挡住一条误录入漏洞的删除。见 §10.3 与 `docs/11` §5.4。
- `remediations` 的四个 ID —— 整改单是**业务事实**（「某台资产上的某个漏洞要修」），
  它的一部分（`assessment_id` / `risk_item_id`）本来就是允许失效的**出处**。
  建外键会让重算直接失败（RESTRICT）或静默抹掉出处（CASCADE），
  两种都在重算那一刻才暴露。见 `docs/13` §2.1。

## 3. `users` —— 账号

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键 |
| `username` | varchar(64) | 否 | **唯一**，登录名，创建后不可修改 |
| `display_name` | varchar(64) | 否 | 显示名 |
| `email` | varchar(128) | **是** | 唯一；未填时为 `NULL` |
| `password_hash` | varchar(255) | 否 | argon2id PHC 字符串 |
| `status` | varchar(16) | 否 | `active` / `disabled`，默认 `active`，有索引 |
| `must_change_password` | tinyint(1) | 否 | 默认 0；管理员设定初始密码后置 1 |
| `failed_login_attempts` | int unsigned | 否 | 连续失败计数 |
| `locked_until` | datetime(3) | 是 | 锁定到期时刻；未锁定为 `NULL` |
| `last_login_at` | datetime(3) | 是 | |
| `last_login_ip` | varchar(64) | 否 | |
| `password_changed_at` | datetime(3) | 是 | |
| `token_not_before` | datetime(3) | 是 | 访问令牌生效下界，见 §3.2 |
| `created_by` | bigint unsigned | 是 | 创建者；引导管理员为 `NULL` |
| `created_at` / `updated_at` | datetime(3) | 否 | 毫秒精度 |

### 3.1 `email` 为什么默认 `NULL` 而不是空串

唯一索引下**多个 `NULL` 互不冲突，而多个空串会互相冲突**。

若「未填邮箱」写成 `''`，那么第二个不填邮箱的账号就会撞唯一键，
报出一个「该邮箱已被占用」的错误——而用户根本填过邮箱。
这类报错会让人彻底找不到方向。

对应到代码：`model.User.Email` 是 `*string`，服务层在邮箱为空时显式写 `nil`
（`fields["email"] = nil`），而不是写 `""`。

### 3.2 `token_not_before` —— 补上 JWT 无状态的短板

JWT 是自包含的，签发后服务端无法撤回。这带来一个真实问题：

> 用户点了「登出」，但那枚 15 分钟有效的访问令牌**仍然能用**。

常规解法是引入令牌黑名单，但那等于把「无状态」这个唯一的收益又还回去了。
这里采用另一种做法：给每个账号记一个**时间下界**。

- 登出时：`token_not_before = now()`
- 每次认证时：`claims.iat_ms < principal.TokensValidFrom` → 拒绝

于是「登出 / 禁用 / 重置密码」都能让此前签发的令牌立即失效，
而正常请求的代价只是**一次已经在做的用户查询**（权限本来就要每请求现查）。

**毫秒精度不是洁癖**：JWT 的 `iat` 只有秒精度。如果在同一秒内先登出再登录，
新令牌的 `iat` 会等于 `token_not_before`，用「小于」判断就会把刚登录的人
当成已登出。因此令牌里额外带一个自定义声明 `iat_ms`（毫秒），
比较也用它。

### 3.3 `status` 为什么用字符串而不是枚举整数

`active` / `disabled` 需要人工读日志、写 SQL 排查。存字符串意味着
`SELECT * FROM users WHERE status='disabled'` 直接可读，
而存 `0/1/2` 就得回来翻代码确认含义——这类「翻译成本」在故障现场很贵。
代价是几个字节的存储，可以接受。

## 4. 角色与授权

### 4.1 `roles`

| 字段 | 说明 |
|---|---|
| `code` | 唯一，角色码：`admin` / `assessor` / `auditor` |
| `name` | 中文名：系统管理员 / 风险评估员 / 审计员 |
| `description` | 面向人的说明 |
| `is_builtin` | 内置角色，不可删除 |

内置角色在迁移里以种子数据插入，不依赖应用启动逻辑。
这样即使应用没能启动，数据库里的角色字典也是完整的——
排障时看到的数据结构不会因为「服务没起来」而缺一块。

### 4.2 `user_roles`

`(user_id, role_id)` 复合主键。没有独立 `id`：关联表本就不该有
自己的身份，复合主键顺带把「同一对出现两次」这件事从结构上排除了。

**不使用 GORM 的 many2many 关联**，由 repository 显式维护。理由是要对
实际执行的 SQL 完全掌握，并规避关联预加载在不经意间退化成 N+1 查询。

### 4.3 权限码**不入库**

角色的权限映射写在 `server/internal/auth/rbac.go` 的代码常量里，
表里只存「谁是什么角色」。

这是一个刻意的选择。若把「角色 → 权限」存成数据表，那么：

> 改一行数据 = 提权。

数据库被注入、备份文件泄漏、误执行一条 UPDATE——任何一种都能静默地把
审计员变成管理员。权限映射在代码里，则任何提权都必须**改代码并重新部署**，
门槛与可审计性完全不同。

代价是「调整权限需要发版」。对本项目（内置三角色、权限码稳定）来说，
这个代价远小于静默提权的风险。

## 5. `audit_logs` —— 审计日志

| 字段 | 说明 |
|---|---|
| `user_id` | 操作人；匿名操作（如登录失败）为 `NULL`，**不建外键** |
| `username` | 冗余存储的操作人登录名 |
| `action` | 动作码，如 `auth.login` / `user.create` |
| `resource` / `resource_id` | 资源类型与标识 |
| `method` / `path` / `status_code` | 请求信息 |
| `client_ip` / `user_agent` | 来源信息 |
| `detail` | JSON，变更明细（写入前已递归剔除敏感字段） |
| `request_id` | 与访问日志串联 |
| `created_at` | 毫秒精度，有索引（列表按时间倒序） |

### 5.1 为什么不建外键

**审计记录的留存优先级高于账号本身。**

若建了外键并级联删除，那么「删除一个账号」会连带抹掉这个账号做过的所有事——
这恰恰是审计最需要保留的部分。不建外键，账号可以删，
日志依然完整，`username` 冗余存储保证历史记录仍能对应到人。

### 5.2 只读

系统中**不存在**审计日志的写入接口与删除接口：

- 写入由中间件与 service 层完成
- 「可以被前端删掉的审计日志」在合规意义上等同于没有审计

### 5.3 `detail` 用 `*string` 而不是 `json.RawMessage`

空值必须是 SQL `NULL`，而不是会被 MySQL 拒绝的**非法 JSON 空串**。
GORM 写 `json.RawMessage(nil)` 的行为在不同驱动版本上并不一致，
用 `*string` 把「有明细 / 无明细」表达得一清二楚。

敏感字段剔除在写入前完成（`internal/pkg/sanitize`），
因此即便某个 handler 不小心把整个请求体塞进 `detail`，
明文口令也不会落库。

## 6. `refresh_tokens` —— 刷新令牌

| 字段 | 说明 |
|---|---|
| `token_hash` | char(64)，**唯一**；SHA-256 摘要 |
| `family_id` | char(36) UUID，一次登录 = 一条链 |
| `issued_at` / `expires_at` | 签发与到期 |
| `used_at` | 被使用过的时刻（轮换后回填） |
| `revoked_at` / `revoke_reason` | 吊销时刻与原因（`logout` / `rotated` / `reuse_detected` / `admin`） |
| `client_ip` / `user_agent` | 便于用户自查「我的登录设备」 |

### 6.1 明文不落库

库里只存 `SHA-256(token)`。数据库被读走时，攻击者拿到的是摘要，
无法用它换取会话。这一点与密码哈希同理，只是刷新令牌是**高熵随机串**，
不需要加盐和慢哈希——SHA-256 足够，而且每次请求都要查它。

### 6.2 轮换 + 重放检测

每次刷新都签发新令牌并作废旧的（`used_at` 回填）。
若收到一个**已经被用过**的令牌，说明它可能已经泄漏——
此时吊销整条 `family_id` 链：攻击者与被攻击者一起掉线，用户重新登录即可。

原子性靠条件 UPDATE 保证（`WHERE used_at IS NULL`），
而不是「先查再写」——后者在并发下会双放行。

### 6.3 这也解释了前端为什么必须做「单飞刷新」

见 `web/src/api/http.ts` 的 `refreshInFlight`。页面上并发的两个请求
若各自触发一次刷新，第二个到达的会带着已被使用的令牌，
后端判定为重放 → 吊销整链 → 用户被自己的页面踢下线。
前后端这两处是**成对的设计**，改一处必须同时考虑另一处。

## 7. 通用约定

| 约定 | 理由 |
|---|---|
| 时间统一 `datetime(3)`（毫秒） | 审计与令牌都要区分同一秒内的先后 |
| 表名显式指定（`TableName()`） | 不依赖 GORM 复数化推断，表名漂移只在运行时才暴露 |
| 可空列一律用指针类型 | 避免零值被误写为真实数据（如空的 `locked_until` 把账号永久锁死） |
| 模型不加 GORM 关联标签 | 换取 SQL 完全可见，规避预加载导致的 N+1 |
| 唯一约束在数据库层，不只在前置检查 | 并发下两个请求会双双通过前置检查，最终必须由数据库拦住 |
| 外键语义分两类：**事实来源用 `RESTRICT`，派生数据用 `CASCADE`** | 删文件不该悄悄抹掉「这些漏洞从哪来」，所以 `vulnerabilities → scan_files` 是 RESTRICT；而资产链接只是派生数据，主体没了它就该跟着走，所以 `vuln_asset_links` 两侧是 CASCADE。一刀切会让两种语义都表达不准 |
| 逗号分隔的「别名」不建子表 | `cve_ids`、`tags` 这类字段只用于展示与模糊筛选，不为它付一张关联表的连接与迁移成本；一旦出现「按它聚合统计」的需求，再改成关联表（触发条件写明，不留模糊 TODO） |

## 8. 已知取舍

| 取舍 | 现状 | 若将来要改 |
|---|---|---|
| 权限映射硬编码在代码里 | 改权限需发版 | 改为配置表时必须同时补上「变更权限」的审计与二次确认 |
| `refresh_tokens` 只增不删（靠定时任务清理过期行） | 表会缓慢增长 | 数据量大后改为分区表 |
| 审计日志无归档 | 单表持续增长 | 按月归档到冷存储；`created_at` 已有索引 |
| 用户不可删除，只能禁用 | 审计可追溯 | 保留；如需删除应设计为「匿名化」而非物理删除 |
| 漏洞的 `cve_ids` 存逗号分隔串 | 按单个 CVE 增删改查的场景不存在 | 出现「按 CVE 反查受影响资产」时改建 `vuln_cve` 关联表 |
| `scan_files` 只增不删（删除只发生在显式请求时） | 文件与漏洞是评估输入，默认留存 | 存储压力大时改为「按策略归档 + 归档表」，不要直接物理清理 |

## 9. 文件与漏洞三表（P3）

> **权威来源是迁移 `000005_file_vuln.up.sql`**，本节是字段级速查。
> 每条约束的**理由与反例**在 `docs/06-文件与解析设计.md` §2，改动前请先读那一节。
> 三张表分别回答三个问题：**报告从哪来**（`scan_files`）、**发现了什么**（`vulnerabilities`）、
> **影响谁**（`vuln_asset_links`）。

### 9.1 `scan_files` —— 上传的扫描报告

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键 |
| `sha256` | char(64) | 否 | **全局唯一**——上传去重的唯一判据，见 §9.4 |
| `original_name` | varchar(255) | 否 | 用户上传时的文件名，**只用于下载时的展示** |
| `storage_path` | varchar(255) | 否 | 落盘相对路径 `YYYYMM/<32位十六进制>`，**不含扩展名** |
| `size_bytes` | bigint unsigned | 否 | 字节数 |
| `mime_type` | varchar(64) | 否 | 嗅探出的 MIME（默认空串） |
| `format` | varchar(16) | 否 | `nessus` / `openvas` / `excel`；未解析时为空串 |
| `parse_status` | varchar(16) | 否 | `unparsed`（默认）/ `parsed` / `failed` |
| `parsed_at` | datetime(3) | 是 | 解析入库时间 |
| `vuln_count` | int unsigned | 否 | 该文件解析出的漏洞条数，commit 时写入 |
| `uploaded_by` | bigint unsigned | 是 | 上传者 ID；**只记 ID，不建外键**——全库 `created_by` / `uploaded_by` 类字段统一如此，业务上也不需要「阻止账号被禁用」 |
| `created_at` / `updated_at` | datetime(3) | 否 | 毫秒精度 |

约束与索引：`UNIQUE uk_scan_files_sha256(sha256)`、`idx(parse_status, id)`、`idx(uploaded_by)`、`idx(created_at)`。

### 9.2 `vulnerabilities` —— 漏洞清单

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键 |
| `source_file_id` | bigint unsigned | **是** | 来源文件；**`NULL` 即「手工录入」**，这是唯一的来源判据，不另设 `source` 列 |
| `title` | varchar(255) | 否 | 漏洞名称 |
| `cve_ids` | varchar(512) | 否 | CVE 编号，英文逗号分隔（一条漏洞可挂多个） |
| `severity_raw` | varchar(64) | 否 | **定级依据**：有 CVSS 存分值（如 `8.1`），否则存等级词（如 `High`） |
| `severity` | tinyint unsigned | 否 | 严重程度 **1–5**，对应风险模型的脆弱性 `V`；默认 3 |
| `description` | text | 是 | 漏洞描述 |
| `solution` | text | 是 | 修复建议 |
| `host_ip` | varchar(64) | 否 | 受影响主机 IP——**自动关联资产的唯一判据** |
| `port` | smallint unsigned | 是 | 受影响端口；**用 `NULL` 表示「与端口无关」，不用 0**（与 `assets.port` 同一条约定） |
| `protocol` | varchar(16) | 否 | `tcp` / `udp`；空串表示未注明 |
| `service` | varchar(64) | 否 | 服务名，如 `https` / `ssh` |
| `created_by` | bigint unsigned | 是 | 创建者；解析写入时为**发起解析的用户**，不是上传者 |
| `created_at` / `updated_at` | datetime(3) | 否 | 毫秒精度 |

约束与索引：`fk_vulnerabilities_source_file → scan_files(id) ON DELETE RESTRICT`、
`idx(source_file_id)`、`idx(severity, id)`、`idx(host_ip)`、`idx(title)`。

> `severity` 与 `severity_raw` **必须并存**：P4 的风险计算只认整数 `V`，
> 但丢掉了原始串就无法复核「映射是否合理」。映射规则写在解析器层
> （`internal/pkg/reportparser`），不在 SQL 里——这样改规则只需改代码 + 重跑解析。

### 9.3 `vuln_asset_links` —— 漏洞 ↔ 资产

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键 |
| `vuln_id` | bigint unsigned | 否 | 漏洞 ID |
| `asset_id` | bigint unsigned | 否 | 资产 ID |
| `matched_by` | varchar(16) | 否 | `auto`（按 IP 自动匹配，默认）/ `manual`（手动挂载） |
| `created_by` | bigint unsigned | 是 | 操作人；仅 manual 时有意义 |
| `created_at` | datetime(3) | 否 | 毫秒精度 |

约束与索引：`UNIQUE uk_vuln_asset(vuln_id, asset_id)`、`idx(asset_id)`，
两侧外键均为 `ON DELETE CASCADE`。

> **`matched_by` 决定「谁能改谁」**：手动关联是**整体替换**语义，但只删 `manual` 的行，
> 绝不动 `auto` 的行——否则「人工补一条关联」会顺手把机器匹配的结果抹掉。
> 这一条是服务层的行为约定，数据库层用 `UNIQUE` 保证「重挂不会产生重复行」，
> 让服务层可以走 `INSERT ... ON DUPLICATE` 而不需要「先查后插」的竞态窗口。

### 9.4 三条最容易踩的约束

1. **`sha256` 唯一 = 上传幂等**：同一份内容重复上传**不产生第二行**，服务层查到就直接返回已有记录。
   于是「同一文件被谁传了几次」由 `audit_logs`（`file.upload_duplicate`）记录，
   而不是由 `scan_files` 记——**审计的诚实性与表的整洁度在这里是分开的**。
2. **`storage_path` 不含扩展名、`original_name` 只用于展示**：
   「文件以什么名字存在磁盘上」与「文件以什么名字给用户下载」是两件事。
   合并这两件事就是路径穿越与内容嗅探的入口。
3. **文件删除默认被拒**：`vulnerabilities.source_file_id` 是 `RESTRICT`，
   有漏洞引用时删除返回 `409 FILE_IN_USE`。要连带删除必须显式 `?force=true`，
   由服务层在**一个事务里**先删漏洞再删文件——「默认不可级联，级联必须显式」是把
   破坏性操作变成一次有意为之的决定。

## 10. 风险评估三表（P4）

> **权威来源是迁移 `000006_assessment.up.sql`**，本节是字段级速查。
> 每条约束的**理由与反例**在 `docs/11-风险评估引擎设计.md` §5，改动前请先读那一节。
> 三张表分别回答三个问题：**这次评估用什么口径算**（`assessments`）、
> **每条风险是怎么来的**（`risk_items`）、**每台资产最坏到什么程度**（`assessment_assets`）。

### 10.1 `assessments` —— 评估任务

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键 |
| `name` | varchar(128) | 否 | 任务名称 |
| `description` | varchar(512) | 否 | 说明（默认空串） |
| `status` | varchar(16) | 否 | `draft`（草稿，未计算）/ `calculated`（已计算） |
| `scope_type` | varchar(16) | 否 | `all` / `group`（按资产组）/ `custom`（手工指定资产） |
| `scope_ref` | json | **是** | 范围明细：`group` 存组 ID 数组，`custom` 存资产 ID 数组；**`all` 时为 `NULL`**。接口层会把它统一成空数组 `[]` 下发（不是 `null`），见 `docs/11` §11.5 |
| `model_key` | varchar(64) | 否 | 风险模型标识，当前恒为 `gb_t_20984_multiplication` |
| `default_threat_code` | varchar(64) | 否 | 任务级默认威胁（字典 `category=threat` 的 `code`）；空串 = 未指定（按 T=3 算） |
| `config_snapshot` | json | **是** | **本表的核心**：计算时的权重与阈值快照。未计算时为 `NULL` |
| `assets_count` | int unsigned | 否 | 纳入计算的资产数（最近一次计算写入） |
| `risk_items_count` | int unsigned | 否 | 风险项条数 |
| `max_risk` | decimal(8,3) | **是** | 最大风险值 R。**未计算时为 `NULL` 而不是 `0`**——用 0 当哨兵会让「算了但风险为 0」与「根本没算」无法区分 |
| `level_counts` | json | **是** | 各等级条数，形如 `{"very_high":13,"high":7,…}`；**五个键一定都在**（没有的填 0） |
| `calculated_at` | datetime(3) | 是 | 最近一次计算时间 |
| `created_by` | bigint unsigned | 是 | 创建者 ID（只记 ID，不建外键，同 §9.1） |
| `created_at` / `updated_at` | datetime(3) | 否 | 毫秒精度 |

约束与索引：`idx(status, id)`、`idx(created_by)`、`idx(created_at)`。

**`config_snapshot` 的内容**（存人类可读真实值，不是定点整数——它是给人和审计看的）：

```json
{
  "model": "gb_t_20984_multiplication",
  "asset_weight": 1.5,
  "thresholds": { "very_high": 20, "high": 12, "medium": 6, "low": 2 },
  "captured_at": "2026-10-11T04:05:00Z"
}
```

### 10.2 `risk_items` —— 风险项（资产 × 漏洞）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键。**重算后整批变化**（先清后写），见 §10.4 |
| `assessment_id` | bigint unsigned | 否 | 所属评估；外键 **CASCADE** |
| `asset_id` | bigint unsigned | 否 | 资产 ID——**逻辑引用，刻意不建外键**（见 §10.3） |
| `vuln_id` | bigint unsigned | 否 | 漏洞 ID——**逻辑引用**；**`NOT NULL`**（可空会让唯一索引对 NULL 失效） |
| `asset_name` | varchar(128) | 否 | 资产名称**快照**——目标被删后报告仍完整可读 |
| `asset_ip` | varchar(64) | 否 | 资产 IP 快照 |
| `vuln_title` | varchar(255) | 否 | 漏洞名称快照 |
| `vuln_cve_ids` | varchar(512) | 否 | CVE 编号快照 |
| `vuln_severity_raw` | varchar(64) | 否 | 扫描器原始等级串快照（同 §9.2 的理由） |
| `threat_code` | varchar(64) | 否 | 威胁码；空串 = 未指定 |
| `threat_name` | varchar(128) | 否 | 威胁名称快照（字典里查不到时存原码，好让失效一眼可见） |
| `threat_source` | varchar(16) | 否 | `default`（取任务级）/ `manual`（逐项覆盖）；重算时保留 `manual` |
| `importance` | tinyint unsigned | 否 | 资产重要性原始档位 **1–5**（矩阵横轴，默认 3） |
| `severity` | tinyint unsigned | 否 | 漏洞严重程度原始档位 **1–5**（矩阵纵轴，默认 3） |
| `asset_value_a` | decimal(6,3) | 否 | **A**：资产价值 = 重要性 × 资产价值权重系数 |
| `threat_weight_t` | decimal(6,3) | 否 | **T**：威胁权重 |
| `vuln_weight_v` | decimal(6,3) | 否 | **V**：脆弱性权重（取自 `vulnerabilities.severity`，见 `docs/11` §2.1） |
| `risk_value_r` | decimal(8,3) | 否 | **R = A × T × V** |
| `risk_level` | varchar(16) | 否 | `very_high` / `high` / `medium` / `low` / `very_low` |
| `created_at` / `updated_at` | datetime(3) | 否 | 毫秒精度 |

约束与索引：

```sql
UNIQUE KEY uk_risk_items_target (assessment_id, asset_id, vuln_id)
KEY idx_risk_items_matrix (assessment_id, importance, severity)
KEY idx_risk_items_level  (assessment_id, risk_level)
KEY idx_risk_items_r      (assessment_id, risk_value_r)
CONSTRAINT fk_risk_items_assessment FOREIGN KEY (assessment_id)
  REFERENCES assessments (id) ON DELETE CASCADE
```

> **A / T / V / R 四列齐存，不只存 R**：下钻时用户要问「这台机器为什么是 20 分」，
> 必须能当场拆出 `4 × 5 × 1`。只存结果等于放弃可解释性，事后也无法复核规则本身是否合理
> ——与 §9.2 保留 `severity_raw` 是同一条理由。
>
> 四个量都是 `DECIMAL` **而不是 FLOAT**：R 要参与阈值比较（≥20 / ≥12 / ≥6 / ≥2），
> 浮点表示误差落在边界上就是一条错误的等级（`docs/11` §3.1）。

### 10.3 `assessment_assets` —— 资产级汇总

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | bigint unsigned | 否 | 主键 |
| `assessment_id` | bigint unsigned | 否 | 所属评估；外键 **CASCADE** |
| `asset_id` | bigint unsigned | 否 | 资产 ID（逻辑引用，同 §10.2） |
| `asset_name` | varchar(128) | 否 | 资产名称快照 |
| `asset_ip` | varchar(64) | 否 | 资产 IP 快照 |
| `importance` | tinyint unsigned | 否 | 资产重要性原始档位 1–5 |
| `asset_value_a` | decimal(6,3) | 否 | 该资产的 A 值 |
| `risk_value` | decimal(8,3) | 否 | 该资产的**最大** R（不是平均值） |
| `risk_level` | varchar(16) | 否 | 该资产的风险等级 |
| `risk_items_count` | int unsigned | 否 | 该资产下的风险项条数 |
| `top_item_id` | bigint unsigned | 是 | 最大 R 对应的风险项 ID，供**下钻直跳** |
| `created_at` / `updated_at` | datetime(3) | 否 | 毫秒精度 |

约束与索引：`UNIQUE uk_assessment_assets(assessment_id, asset_id)`、
`idx(assessment_id, risk_value)`、`assessment_id → CASCADE`。

> **取最大而不是平均**：一台机器能被打穿到什么程度，由它最弱的那一环决定。
> 平均值会把「一个致命漏洞 + 九条无关紧要」稀释成「中等风险」——这正是漏报的典型形态。

### 10.4 五条最容易踩的约束

1. **`config_snapshot` 是这张表的灵魂**：权重与阈值存在 `system_configs` 里且界面可改，
   不快照就会「改一次阈值 → 静默改写全部历史评估的档位」。已发出的报告与库里的数据
   对不上，而这是最难排查的一类事故（数据看起来都对，只是和昨天不一样了）。
2. **`asset_id` / `vuln_id` 不建外键，`assessment_id` 建 CASCADE**——看似矛盾，其实是
   把「事实来源」与「派生数据」分开：资产 / 漏洞是外部事实，删它们不该改写历史结论；
   评估任务的结果行是派生数据，跟着主体走是正确语义。
3. **`vuln_id` 必须是 `NOT NULL`**：MySQL 唯一索引把多个 `NULL` 视为互不相同，
   可空则 `uk_risk_items_target` 形同虚设，重复计算会堆出重复行。
   （初版计划写的是可空，实现期收紧，见 `docs/11` §5.5。）
4. **重算后风险项 ID 全部变化**：`calculate` 是事务内「先清后写」，重算后是新插入的行。
   任何缓存了风险项 ID 的地方（前端结果页、外部集成）在重算后都必须重新拉取，
   否则 PATCH 会得到 `404 RISK_ITEM_NOT_FOUND`。
   ⚠️ P6 的整改单**刻意不依赖 `risk_item_id` 存活**：它把该 ID 降级为「发现出处」，
   业务身份另用 `(asset_id, vuln_id)`。见 §11 与 `docs/13` §2.1 ——
   这是本系统里对「重算会换 ID」这条性质唯一一处**结构性**的应对，
   其余地方（如前端）用的都是「重算后重新拉取」这种约定式的应对。
5. **`max_risk` 未算时为 `NULL`**：与 §10.1 同一条——`0` 与「没算」必须可区分，
   否则列表页无法正确显示「—」，用户也判断不出这份评估到底跑没跑过。

### 11.2 `remediation_logs` —— 流转与变更记录

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|

| `remediation_id` | bigint unsigned | 否 | 所属整改单；外键 **CASCADE** |
| `action` | varchar(16) | 否 | `create` / `update` / `transition` |
| `from_status` | varchar(16) | 否 | 流转前状态；**空串 = 本次不是状态流转** |
| `to_status` | varchar(16) | 否 | 流转后状态；`create` 时 = 初始状态 |
| `note` | varchar(500) | 否 | 说明（打回与风险接受**必须**填写，见 `docs/13` §5.2） |

> **排序键为什么是 `(remediation_id, id)` 而不是 `(remediation_id, created_at)`**：
> 同一事务里写入的多条记录可能落在同一毫秒，时间戳相同时顺序不定 ——
> 而详情页的时间线必须有一个**全序**，否则同毫秒的两条记录会随机换位。

### 11.3 三条最容易踩的约束

1. **生成列只能引用在它之前定义的列**：`active_key` 必须排在
   `asset_id` / `vuln_id` / `status` 之后，否则迁移报 `Unknown column`。
2. **「未闭环状态」这个集合有 3 个落点**（生成列的 SQL 字面量、逾期判定的 `status IN ?`、
   `model.RemediationActiveStatuses`）。第 1 处写在 SQL 里，改 Go 代码改不到它 ——
   三者分裂会让「唯一索引认为已闭环、服务层仍认为未闭环」。
   见 `docs/13` §3.2。
3. **`ON DELETE CASCADE` 只出现在这一张表**，与 §2「四处不建外键」不矛盾：
   流转日志是单子的**派生数据**，主体没了它没有独立存在意义。
   （同 §10.4 第 2 条对 `assessment_id` 的处理。）
